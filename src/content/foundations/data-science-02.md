# Data Science：AI 应用里的数据质量思维

![AI 应用的数据质量工作台](/images/foundations/data-science-02/data-quality-ai-cover.png)

“Garbage In, Garbage Out”听起来像数据科学家的老话。但在 AI 应用里，它变得更普遍，也更容易被忽略。

你不一定在训练模型，也不一定在写 pandas 脚本，但你每天都在处理数据：

- 写 Prompt 时，你在组织指令数据。
- 做 RAG 时，你在筛选上下文数据。
- 调 tool calling 时，你在约束工具输入和输出数据。
- 做 eval 时，你在定义评测样本和期望答案。
- 看用户反馈时，你在收集失败案例。
- 维护 Agent 时，你在决定哪些中间状态值得保留。

模型表现不好时，人们很容易把原因归结为“模型不够强”或“Prompt 不够好”。但很多真实问题的根因在数据层：输入混乱、上下文过期、示例互相矛盾、工具返回格式不稳定、评测样本太干净。

数据质量思维不是传统数据清洗的一个步骤，而是一种工程习惯：在让模型行动之前，先判断它拿到的材料是否可靠。

## AI 应用里的“数据”比你想得更广

在传统数据科学里，数据通常指表格、日志、事件、特征和标签。在 AI 应用里，数据范围更宽。

| 数据类型 | 例子 | 常见质量问题 |
| --- | --- | --- |
| 指令数据 | system prompt、任务说明、格式要求 | 目标冲突、约束太多、措辞含糊 |
| 上下文数据 | RAG chunk、文件内容、聊天历史 | 过期、重复、缺关键段落 |
| 示例数据 | few-shot 示例、参考答案 | 示例不一致、覆盖场景太少 |
| 工具数据 | API 返回、数据库查询、搜索结果 | schema 不稳定、字段缺失、错误未结构化 |
| 评测数据 | benchmark、golden set、失败样本 | 太干净、太少、和真实用户不一致 |
| 反馈数据 | thumbs down、客服记录、人工修正 | 没有归类、缺输入原文、无法复现 |

当你把这些都视为数据，很多 AI 工程问题就有了新的处理方式。

## 数据质量的五个维度

![输入质量审查的五个维度](/images/foundations/data-science-02/input-quality-review.png)

AI 应用里最实用的数据质量维度有五个。

| 维度 | 诊断问题 | 例子 |
| --- | --- | --- |
| 相关性 | 这份数据和当前任务有关吗？ | RAG 返回了相同领域但不是同一问题的文档 |
| 完整性 | 关键信息是否缺失？ | 让模型改代码，却没有提供错误日志 |
| 一致性 | 不同来源是否互相冲突？ | 文档写 v1，示例代码用 v2 API |
| 新鲜度 | 信息是否仍然有效？ | 旧 SDK 用法混进当前回答 |
| 可解析性 | 模型或程序能否稳定读取？ | 工具返回自由文本，下一步却期待 JSON |

一个输入不需要完美，但必须足够适合当前任务。工程上要问的不是“数据干净吗”，而是“这份数据能支撑这个判断吗”。

## Prompt 问题常常是数据问题

很多 Prompt 优化其实是在修数据。

比如你给模型这样的任务：

> “请帮我写一份可靠的发布说明。”

模型写得泛，是因为输入数据太少。更好的输入应该包含：

- 变更列表。
- 用户可见影响。
- 是否有破坏性变更。
- 迁移步骤。
- 已知问题。
- 验证命令。
- 不应该提到的内部细节。

当这些信息齐全时，Prompt 不需要变得神秘。它只需要清晰地告诉模型如何组织已有材料。

所以调 Prompt 前，先问五个问题：

1. 我是否提供了足够事实？
2. 事实之间是否冲突？
3. 有没有过期信息？
4. 有没有无关噪声？
5. 输出标准是否可验证？

如果这些问题没有处理，继续加形容词式指令通常收益很低。

## RAG 的质量取决于知识库，而不只是检索算法

RAG 系统的输入不是用户问题本身，而是“用户问题 + 被检索出来的上下文”。上下文质量直接决定回答上限。

知识库常见问题：

- 文档太旧，和当前 API 不一致。
- 同一主题有多个版本，互相冲突。
- 文档太碎，chunk 失去上下文。
- 文档太长，检索命中但证据埋得太深。
- 标题很清楚，正文没有可引用细节。
- 重要决策只存在聊天记录里，没有沉淀为文档。

RAG 不是把所有文档塞进向量库就结束。它更像维护一个可检索的知识产品。

最小健康检查：

1. 收集 20 个真实用户问题。
2. 人工标注每个问题应该命中的文档。
3. 跑一次检索，记录 top-k。
4. 标出没命中的问题。
5. 判断原因是缺文档、chunk 问题、查询太泛，还是排序问题。

这个过程比盲目换向量数据库更有价值。

## 评测数据必须包含失败和噪声

![从失败日志生长出来的评测数据集](/images/foundations/data-science-02/failure-log-eval-dataset.png)

很多 AI 应用的评测集太“干净”。问题写得完整，输入格式标准，答案边界清楚。这样的评测可以作为起点，但不能代表真实用户。

真实用户会：

- 写错别字。
- 粘贴半截日志。
- 混用中文、英文、日文。
- 省略上下文。
- 使用内部缩写。
- 一次提出多个目标。
- 修改前一个请求。
- 给出互相冲突的要求。

如果评测集不包含这些噪声，系统上线后会突然变脆。

更好的做法是让评测集从失败日志里长出来。

每次遇到失败，记录：

- 原始输入。
- 当时上下文。
- 期望输出。
- 实际输出。
- 失败分类。
- 修复方式。
- 是否加入回归评测。

攒到 30 条，你就有了一个比通用 benchmark 更贴近产品的 golden set。

## Agent 系统尤其依赖结构化数据

普通聊天出错，用户还能追问。Agent 出错，可能会调用工具、修改文件、发送外部请求。数据质量要求更高。

Agent Workflow 中最容易出问题的数据包括：

- 计划步骤没有唯一 ID。
- 工具输出是自然语言，下一步无法稳定解析。
- 错误没有 code，只写“失败了”。
- 中间状态没有保存，重试时丢上下文。
- 人工审批结果没有结构化记录。
- 最终报告没有引用实际验证证据。

Agent 系统里，结构化数据不是洁癖，而是恢复能力。没有结构化状态，就很难局部重试、审计和回放。

## 案例：模型输出不稳定，根因是示例数据冲突

一个团队做客服回复生成。Prompt 写得很详细，要求语气友好、结论清楚、不要承诺超出政策。但模型仍然时好时坏。

检查后发现 few-shot 示例里有三个问题：

1. 示例 A 对退款政策很严格。
2. 示例 B 为了安抚用户，暗示可以特殊处理。
3. 示例 C 使用了旧的产品名称。

模型并不是“不听话”。它在不同示例之间学习到了互相冲突的模式。

修复方式：

- 删除旧政策示例。
- 为每个示例标注适用场景。
- 把“不能承诺特殊处理”写成明确负例。
- 加入真实失败案例作为评测样本。
- 对输出增加政策引用检查。

结果比继续堆 Prompt 约束更稳定。这就是典型的数据质量问题。

## 常见反模式

**反模式一：把所有失败都归因于模型能力。**

更强模型可以缓解一些问题，但无法稳定修复过期、冲突、缺失的数据。

**反模式二：只保留成功样本。**

成功样本让报告好看，失败样本让系统变强。真实评测集必须包含失败。

**反模式三：评测数据和真实用户脱节。**

如果评测只包含理想输入，线上噪声会让系统表现断崖式下降。

**反模式四：工具返回自由文本。**

自由文本适合给人读，不适合作为下一个工具调用的输入。Agent 工具应该优先返回结构化数据。

**反模式五：不记录输入原文。**

没有原始输入，就无法复现失败。没有复现，就没有可靠改进。

## 检查清单

- 输入是否包含完成任务所需的关键事实？
- 上下文是否过期、重复或互相矛盾？
- 示例是否覆盖正例和反例？
- 工具输出是否结构化，能被下一步稳定解析？
- 评测集是否包含真实噪声和失败案例？
- 每次失败是否记录原始输入、期望输出和实际输出？
- 改进是否进入回归评测，而不是只改当前 Prompt？
