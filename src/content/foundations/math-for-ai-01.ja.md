# AI のための数学：まず「どれだけ似ているか」から考える

![ベクトル空間と類似度の概念図](/images/foundations/math-for-ai-01/math-vector-similarity-cover.png)

Embedding、ベクトルデータベース、コサイン類似度という言葉を見ると、線形代数を最初から学び直す必要があるように感じるかもしれません。けれども AI アプリケーションを作るうえで最初に必要なのは、手計算の能力ではなく、システムの挙動を判断するためのモデルです。

AI 検索、ナレッジベース Q&A、推薦、重複検知、クラスタリングでは、システムは何度も同じ問いに答えています。

**この入力は、どの情報に近いのか。**

ここでいう「近い」は感覚的な表現ではありません。多くの AI アプリケーションでは、モデルがテキスト、画像、コード、音声を数値の配列に変換し、その配列の方向や距離を比較しています。

この層を理解すると、問題の切り分けが変わります。

- RAG の回答がずれる原因は Prompt ではなく、検索段階で間違った文脈を取っていることかもしれない。
- 検索結果が広すぎる原因は、モデルが理解していないことではなく、クエリの意味方向が曖昧なことかもしれない。
- 類似度しきい値を上げたら品質が下がるのは、有用な補助証拠まで捨てているからかもしれない。
- ナレッジベースを増やしたのに品質が落ちるのは、重複、古い文書、低密度な文書で空間が汚れているからかもしれない。

この文章では、ベクトル空間とコサイン類似度を、日常の AI システム診断に使える形で説明します。

## ベクトルとは何か

ベクトルは「モデルが対象に与える座標」と考えると分かりやすいです。

文章はそのままベクトルデータベースに入るわけではありません。まず Embedding モデルを通り、次のような数値配列になります。

```txt
[0.018, -0.042, 0.113, ..., 0.007]
```

配列の各次元が、人間に名前を付けられる概念に対応しているとは限りません。全体として、モデルが学習データから得た意味上の位置を表します。

極端に複雑な地図を想像するとよいです。

- 「FastAPI の依存性注入」と「リクエストライフサイクル」は近い位置にある。
- 「uv のプロジェクト管理」と「Python パッケージ解決」は近い位置にある。
- 「テニスのサーブ動作」と「GitHub Actions のデプロイ」は遠い位置にある。

実際のベクトル空間は二次元ではなく、数百から数千次元です。人間には描けませんが、類似度スコアを通じて観察できます。

## コサイン類似度：長さではなく方向を見る

ベクトル検索でよく使われる比較方法の一つがコサイン類似度です。これは二つのベクトルの方向がどれだけ近いかを見ます。

$$
\cos(\theta) = \frac{a \cdot b}{\|a\| \|b\|}
$$

式を丸暗記する必要はありません。実務上の意味は次の一文です。

**コサイン類似度は、二つの内容が同じ意味方向を向いているかを問う。**

この考え方で、いくつかの現象を説明できます。

短い質問が長い文書に一致することがあります。12 文字の質問と 2000 字の文書は長さがまったく違いますが、同じ主題を向いていれば高い類似度になります。

重複文書は高いスコアになりやすいです。原文、要約、言い換え、翻訳は方向が近いため、似ていると判定されます。

曖昧な質問は曖昧な結果を呼びます。「AI アプリの品質を上げるには」のようなクエリは、評価、Prompt、RAG、監視、データ品質など多くの主題に近づくため、検索結果が散らばります。

## 類似度スコアをどう読むか

モデル、ベクトルデータベース、正規化方法によってスコアの分布は変わります。次の表は絶対的な基準ではなく、読み方の目安です。

| スコア | よくある意味 | エンジニアリング上の判断 |
| --- | --- | --- |
| 0.90 以上 | ほぼ重複、または強い同義 | 重複検知や原文検索に向くが、複雑な回答には狭すぎる場合がある |
| 0.75 から 0.90 | 強い関連 | RAG で使いやすい範囲。ただし chunk の中身を見る |
| 0.55 から 0.75 | 中程度の関連 | 候補にはなるが、直接信頼するには弱いことがある |
| 0.35 から 0.55 | 弱い関連 | クエリ改写、キーワード補助、知識追加を検討する |
| 0.35 未満 | 関連が低い | ナレッジベース不足、またはクエリが曖昧すぎる可能性が高い |

信頼できるやり方は、万能なしきい値を信じることではありません。実際の業務クエリを 30 から 50 件集め、人間が正しいと思う文書とスコア分布を記録します。その分布が、最も重要な基準になります。

## 曖昧なクエリが RAG を弱くする理由

![曖昧なクエリと具体的なクエリの検索空間の違い](/images/foundations/math-for-ai-01/query-specificity-vector-search.png)

よくある例を考えます。

FastAPI、uv、CI/CD、可観測性、Agent Runtime、コンテンツサイトのデプロイを含むナレッジベースがあります。ユーザーが次のように入力します。

> 「これはどう作るのがよいですか？」

会話の文脈を知っている人間なら「これは FastAPI の構成のことだ」と分かるかもしれません。しかしベクトル検索に渡る文字列だけを見ると、意味情報が足りません。向きが曖昧なので、空間上の位置も曖昧になります。

次のように変えると、検索品質は上がりやすくなります。

> 「FastAPI プロジェクトでルーター、依存性注入、DB session、バックグラウンドタスクをどう分割すると、後からマイクロサービスへ切り出すときの手戻りを減らせますか？」

このクエリには対象、操作、制約、失敗リスクがあります。意味方向が明確になり、関連文書に近づきます。

多くの RAG システムが検索前に query rewriting を行うのは、このためです。文章をきれいにするためではなく、ベクトル空間上の位置を正確にするためです。

## RAG 診断：生成より先に検索を見る

RAG が失敗すると、まず Prompt を直したくなります。より安全な順序は次の通りです。

1. ユーザーの質問を見る。
2. 検索された chunk を見る。
3. 類似度分布を見る。
4. 最後に生成モデルの回答を見る。

検索で渡された文脈が間違っていれば、生成モデルは間違った証拠の上で頑張るしかありません。文章は流暢でも、正しい材料がなければ答えは安定しません。

実務で使える診断表です。

| 現象 | ベクトル層の可能な原因 | 優先アクション |
| --- | --- | --- |
| 関係ない文書を引用する | クエリが広い、または chunk が混在している | クエリを改写し、chunk を切り直す |
| 同じ文書の断片ばかり出る | 重複文書、overlap が大きすぎる | 重複削除、overlap 調整、多様性 rerank |
| 正しい文書が下位にある | キーワードが重要だが意味類似度で目立たない | hybrid search を入れる |
| 類似度が全体的に低い | 知識不足、領域不一致 | 高品質な文書を追加する |
| 類似度は高いのに答えが違う | chunk が短い、文脈不足、証拠が矛盾 | 文脈を広げ、引用チェックを入れる |

## ベクトル検索を全文検索の代替にしない

ベクトル検索は意味的に近い内容を探すのが得意です。しかし万能ではありません。

ユーザーがエラーコード、バージョン番号、設定名、関数名を探している場合、キーワード検索のほうが強いことが多いです。

- `PydanticUserError`
- `OPENAI_API_KEY`
- `upload-pages-artifact@v3`
- `asyncio.CancelledError`

これらの価値は文字列としての一致にあります。Embedding モデルは技術領域を推測できても、必ず正確に命中させるとは限りません。

そのため本番システムでは hybrid search がよく使われます。

- ベクトル検索は意味検索を担当する。
- キーワード検索は正確な検索を担当する。
- reranker や業務ルールが最終順位を決める。

これは、より強い Embedding モデルだけを求めるより現実的です。

## ナレッジベースの健康状態を類似度分布で見る

![RAG 検索健康度と類似度分布](/images/foundations/math-for-ai-01/rag-retrieval-health-map.png)

RAG 用のナレッジベースを運用するなら、定期的にサンプル診断を行うとよいです。

実際の質問を集め、各質問の top-k 検索結果と類似度分布を記録します。見るべき信号は四つあります。

| 信号 | 可能な解釈 | 対応 |
| --- | --- | --- |
| 高スコア結果が少ない | 知識のカバー不足 | 核心文書を追加する |
| 0.95 以上が多すぎる | 重複が多い | 重複削除、権威版への統合 |
| top-1 と top-5 の差が小さい | 主題境界が曖昧 | chunk 戦略と metadata を見直す |
| 高スコアが古い文書に偏る | 新旧文書が混ざっている | 時間重み、旧文書のアーカイブ |

このチェックは CI やオフライン評価に向いています。毎回すべての文書を人間が読む必要はありませんが、ナレッジベースが明確になっているのか、汚れているのかは観察できます。

## ケース：Prompt 問題に見えた検索失敗

工程支援アシスタントに、ユーザーがこう聞いたとします。

> 「デプロイ後に画像が表示されないのはなぜですか？」

モデルは CDN、キャッシュ、ファイル権限について長く説明しましたが、解決しません。チームは Prompt に「パス問題を丁寧に分析せよ」と追記しましたが、安定しません。

検索ログを見ると、top-3 は次の文書でした。

1. CDN キャッシュ戦略。
2. 画像圧縮フロー。
3. Markdown の画像構文。

本来必要だった文書は「GitHub Pages の base path と Astro のアセット解決」でしたが、9 位でした。ユーザーの短いクエリは多くの主題に近く、正しい文書のタイトルには `base`、`subpath`、`asset resolution` が含まれていたためです。

修正は Prompt 追加ではなく、次の三つでした。

1. 検索前に「静的サイトを GitHub Pages のサブパスへデプロイした後、`/images/...` や相対パスのアセットがなぜ失敗するのか」に改写する。
2. `base`、`subpath`、`asset`、`GitHub Pages` をキーワード検索で強める。
3. 回答生成前に、検索されたパス設定の断片を引用させる。

結果として回答が安定しました。RAG の第一の問題は「モデルが書けるか」ではなく、「正しい証拠を取れているか」であることが多いのです。

## よくあるアンチパターン

**アンチパターン 1：しきい値を高くしすぎる。**

高すぎるしきい値は、ほぼ重複した文章だけを残します。複雑な問いには、同義文ではなく補完的な証拠が必要です。

**アンチパターン 2：top-1 だけを見る。**

top-1 が外れても、検索全体が失敗とは限りません。top-k に正しい証拠があるか、rerank で上げられるかを見ます。

**アンチパターン 3：捨てた結果を記録しない。**

最終的にモデルへ渡した chunk だけを保存すると、失敗時に検索、順位付け、生成のどこが悪いか判断できません。

**アンチパターン 4：chunk を小さくすれば安全だと思う。**

小さすぎる chunk は文脈を失います。関数名や見出しだけは近くても、説明段落がなければ回答は弱くなります。

## テンプレート：ベクトル検索診断ログ

工程ログや評価表にそのまま使える形式です。

```md
### Query

元の質問：

検索用に改写したクエリ：

### Expected Evidence

人間が正しいと考える文書または段落：

### Retrieval Result

Top 1:
- 文書：
- 類似度：
- 関連あり：

Top 2:
- 文書：
- 類似度：
- 関連あり：

Top 3:
- 文書：
- 類似度：
- 関連あり：

### Diagnosis

- クエリが広すぎるか？
- chunk 戦略に問題があるか？
- キーワードが正確に検索できていないか？
- ナレッジベースに内容が足りないか？
- 古い文書が混ざっているか？

### Action

- クエリ改写：
- chunk 調整：
- metadata / filter 調整：
- hybrid search 調整：
- 追加または整理すべき文書：
```

> **記入例（RAG diagnosis case）**
>
> 元の質問：project space ごとに document search を制限できますか？
> 検索用に改写したクエリ：project space permission filter metadata RAG
> 人間が正しいと考える文書または段落：docs/rag-permissions.md#workspace-filter
> Top 1：文書=docs/vector-store-setup.md；類似度=0.82；関連あり=部分的に関連します
> Top 2：文書=docs/rag-permissions.md；類似度=0.78；関連あり=関連します
> Top 3：文書=docs/old-auth-notes.md；類似度=0.74；関連あり=関連しません
> Diagnosis：クエリが広すぎるか=no；chunk 戦略に問題があるか=yes、権限 rule が次の段落に分かれています；キーワード検索の問題=no；内容不足=no；古い文書混入=yes
> Action：クエリ改写=workspace_id filter を入れます；chunk 調整=権限小節単位で切り直します；metadata / filter 調整=product_area=search を追加します；hybrid search 調整=exact keyword を強めます；追加または整理すべき文書=old-auth-notes を archive します

## チェックリスト

- クエリに対象、操作、制約、文脈が入っているか？
- top-k の中に、人間が認める証拠が少なくとも一つあるか？
- 検索結果、フィルタ結果、最終文脈をすべて保存しているか？
- バージョン番号、エラーコード、API 名にはキーワード検索を併用しているか？
- 重複、古い文書、低密度な文書を定期的に確認しているか？
- 実ユーザーの質問から小さな検索評価セットを作っているか？
