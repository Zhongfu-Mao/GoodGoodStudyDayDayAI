# なぜトークンから始めるのか

LLM アプリケーションの開発において、一見プロンプト（Prompt）の問題に見える不具合の多くは、実はその背後にある**トークン（Token）**の問題に起因しています。入力が長すぎる、会話履歴が多すぎる、検索結果が細切れすぎる、出力が途中で截断（セクション）される、コストが急騰する、あるいはモデルが中間の重要な情報を見落とす。これらはすべて、モデルが文字ではなくトークン列として世界を処理しているために起こります。トークンは、モデルが読み書きする最小の工程単位なのです。

モデルを一つの関数として捉えると、その入力は「文章」や「チャット履歴」ではなく、トークンのシーケンスです。トークナイザー（Tokenizer）がテキストをトークンに分割し、語彙表上の整数へと変換します。言語、記号、空白、コードの断片によって分割のルールが異なるため、「1000 文字の日本語」「1000 単語の英語」「1000 行の JSON」は、モデルにとっては全く異なる長さとして認識されます。

## コンテキストウィンドウとは

コンテキストウィンドウ（Context Window）とは、モデルが一度の計算で受け取れる最大トークン数のことです。これは長期記憶でもデータベースでもありません。ウィンドウ内の情報は現在の回答に直接影響を与えますが、ウィンドウの外に落ちた情報はモデルから完全に「忘れ去られ」ます。

この仕様は、実務において 3 つの大きな制約をもたらします。

1. **ウィンドウは希少資源である**：システムプロンプト（System Prompt）、ユーザー入力、会話履歴、ツール実行結果、RAG（検索拡張生成）の断片、出力形式の制約。これらすべてが限られたウィンドウ枠を奪い合います。優れたエージェント（Agent）を設計するには、推論能力だけでなく、いかに重要な情報をウィンドウ内に留め続けるかが鍵となります。
2. **ウィンドウが長いほど安定するわけではない**：長いコンテキストはより多くの材料をモデルに提供しますが、同時に情報の希釈、重複、指示の衝突、検索ノイズも増やします。多くの場面では、**コンテキストを広げることよりも、削ぎ落とすことの方が重要**です。
3. **コストと遅延に直結する**：入力トークンが多いほど、モデルの読み込みとアテンション（Attention）計算の負荷が増し、出力トークンが多いほど生成時間が伸びます。トークン予算（Token Budget）は、データベースのインデックス設計や API のレート制限と同じように、あらかじめ設計されるべきものです。

## 調査・診断時の視点

モデルが期待通りの回答をしないとき、まず以下の 4 つのトークン関連の問題を疑ってください。

1. **必要な情報は本当にウィンドウ内に存在するか？**（切り捨てられていないか、検索漏れはないか）
2. **重要な情報が不要な文脈に埋もれていないか？**（ノイズによるモデルの混乱）
3. **指示、データ、出力形式がウィンドウ内で矛盾していないか？**
4. **出力上限（Max Tokens）や停止条件によって、回答が途中で終了していないか？**

これらの確認は、闇雲にモデルを上位版に替えるよりも低コストで、再現性のある改善につながります。

## 実験のすすめ

`token-lab` という簡単なスクリプトを作成してみましょう。同じ意味のテキストを日本語、英語、Markdown、JSON、コード、ログ形式で用意し、それぞれのトークン数を比較します。さらに、一つのタスクに対して「全文入力」「要約入力」「構造化メモ入力」の 3 パターンで実行し、回答の質、トークン消費量、遅延、コストを比較してください。

この目的は正解を見つけることではなく、「どの情報をウィンドウに入れ、どの情報を圧縮、検索、または破棄すべきか」という**エンジニアとしての直感**を養うことにあります。

## 実務判断：いつトークンを節約すべきか

すべての場面でトークンを最小化すればよいわけではありません。カスタマーサポートの要約、分類、簡易抽出のようなタスクでは、短いプロンプトと出力、そして安価なモデルを組み合わせるのが正解です。しかし、法務レビュー、コードのリファクタリング、複雑な調査タスクでは、コンテキストを削りすぎると回答精度が落ち、結果として人間の確認コスト（手戻り）を増大させます。

判断基準は「少ないほどよい」ではなく、**「そのトークンを消費することで、成功率がどれだけ上がるか、または人間の工数をどれだけ削減できるか」**に置くべきです。

トークン予算は、以下の 4 つに分解して管理すると見通しが良くなります。
- **システムプロンプト**：短く、かつ安定させる。
- **ユーザー入力**：原文の意味を損なわない。
- **外部資料（RAG 等）**：重複排除とリランク（Rerank）で密度を高める。
- **期待する出力**：フィールド制限と形式指定で長さを制御する。

## 手を動かして試す：予算管理表（Budget 表）の作成

開発中の AI 機能に対して、`token_budget.md` を作成してみましょう。

| 区画 | 予想 Token | 圧縮可能か | 方針 |
| --- | ---: | --- | --- |
| System Prompt | 300 | 可 | 重複ルールの削除 |
| User Input | 800 | 不可 | 原文を維持 |
| Context (RAG) | 4000 | 可 | Chunk 重複除去 + リランク |
| Output | 800 | 可 | 形式とフィールドの制限 |

20 個程度のテストケースで実際に表を埋め、平均値だけでなく P95（上位 5% の値）を確認します。コストや体験の悪化は、平均的なケースではなく、極端に長い文書や履歴、あるいはツールのエラーによって突然発生するためです。
