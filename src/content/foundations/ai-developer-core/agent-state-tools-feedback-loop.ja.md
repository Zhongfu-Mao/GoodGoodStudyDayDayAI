# エージェントを神秘化しない

「エージェント」という言葉は抽象的で大げさに聞こえがちですが、実務における実体はよりシンプルです。エージェントとは、環境の中で「観察・行動・結果の受領・次アクションの決定」を繰り返すシステムを指します。モデルが次の一手を選択し、ツールが情報の取得や環境への働きかけを行い、状態が進捗を記録し、停止条件が暴走を防ぐ役割を担います。

エージェントを単なる「モデル + Prompt」と捉えると、すぐに信頼性の限界に直面します。しかし、「モデル + 状態マシン + ツールインターフェース + 評価（Eval） + 権限管理」の集合体として捉えることで、ソフトウェア工学として扱える領域になります。

## 五つの構成要素

1.  **目標 (Goal)**：エージェントにはタスクの説明だけでなく、明確な「完了条件」が必要です。目標が曖昧であるほど、人間による確認ポイント（Human-in-the-loop）が重要になります。
2.  **状態 (State)**：ユーザーの要求、完了したステップ、ツールの実行結果、仮説、エラー、今後の計画などが含まれます。状態管理を会話履歴だけに頼るべきではありません。長期的なタスクでは構造化された状態管理が不可欠です。
3.  **ツール (Tool)**：ツールは単なる関数一覧ではありません。明確な名称、入力 Schema、出力 Schema、失敗時の挙動、権限レベル、そして利用例が定義されている必要があります。インターフェースが曖昧なツールは、エージェントによる誤用を招きます。
4.  **フィードバック (Feedback)**：ツールの実行結果、テストやビルドの成否、検索結果の適合度、ユーザーによる確認、システムログなどがこれに当たります。適切なフィードバックがなければ、エージェントのアクションは単なる推測の連続になってしまいます。
5.  **停止条件 (Stop Condition)**：完了、失敗、ユーザー入力待ち、予算や試行回数の上限到達、リスクの検知など、明示的な停止条件を設けるべきです。信頼できるエージェントは、「いつ止まるべきか」を正確に把握しています。

## ワークフロー (Workflows) とエージェント (Agents) の違い

**ワークフロー**は、あらかじめ定義された経路に沿ってモデルを利用する形式です。対して**エージェント**は、経路を完全には固定せず、環境からのフィードバックに基づいてモデルが次のアクションを動的に決定します。前者は安定性が高く、低コストでテストが容易ですが、後者は柔軟性が高い反面、コストがかかり、ガードレール（Guardrails）による制御が強く求められます。

多くのプロダクトにおいて、完全自律型のエージェントは必ずしも必要ありません。まずは予測可能な処理をワークフローとして固め、手順を事前に列挙できない複雑な場面にのみ、エージェントによるループを導入するのが賢明です。

## 実務上の本質

エージェントの真の能力は「高度な思考」そのものではなく、「各ステップにおいて現実の環境から事実を得られること」にあります。コード生成エージェントであればファイルを読み書きしテストを実行できること、リサーチエージェントであれば検索・引用・検証ができること、データエージェントであればクエリの実行・可視化・異常検知ができることが重要です。

つまり、エージェント設計の要諦は Prompt の調整だけでなく、「どのようなツール、権限、フィードバックをシステムに与えるか」という環境設計にあります。

## 試してみること

3つのステップからなる小規模なエージェントを作成してみましょう：タスクの読み取り、読み取り専用ツールの呼び出し、構造化された状態の出力。次に、失敗時の再試行メカニズムを加え、2回失敗したら人間に確認を求めるバージョンを作成します。両者のログを比較することで、状態・フィードバック・停止条件がシステムのデバッグ性にどう寄与するかを実感できるはずです。

## 実務判断：エージェントには製品境界（Product Boundary）が必要

エージェントの自由度が高まるほど、製品としての境界線（Boundary）を明確にする必要があります。何を観察でき、何を変更できるのか。どのアクションに承認が必要で、どのエラーで停止すべきか。どのログを保持すべきか。これらが曖昧な状態では、ユーザーはエージェントを信頼してタスクを任せることができません。

すべての複雑なタスクを一つの巨大なエージェントに委ねる必要はありません。安定したワークフローでメインパスを処理し、小規模なエージェントが局所的な不確実性に対処し、高リスクなポイントで人間が介入する。このような構成のほうが保守性が高く、失敗原因の特定も容易になります。

## ワーク：エージェントの Runbook を書く

開発中のエージェントについて、以下の項目を含む Runbook（運用手順書）を書いてみてください。

- **目標 (Goal)**：完了をどのように観測するか。
- **入力 (Input)**：ユーザーが必ず提供すべき情報は何か。
- **ツール (Tools)**：各ツールの権限レベルと失敗時の挙動。
- **状態 (State)**：各ラウンドで記録すべきフィールド。
- **停止 (Stop)**：完了、失敗、ユーザー待ち、リスク検知の条件。
- **再現 (Replay)**：問題発生時にログからどのように状況を再現するか。

この Runbook がスムーズに書けない場合、エージェントの境界設計がまだ不十分である可能性が高いと言えます。
