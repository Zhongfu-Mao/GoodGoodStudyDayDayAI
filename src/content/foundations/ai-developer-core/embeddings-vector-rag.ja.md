# Embedding とは

Embedding（埋め込み）とは、テキストや画像などのデータを数値ベクトルへと変換する処理を指します。ベクトル空間上の幾何学的な距離は、データの「意味的な近さ」を表します。字面上の単語が異なっていても、表現している内容が同じであれば、それらのベクトルは空間内で近い位置に配置されます。

この仕組みは、LLM アプリケーションに「外部記憶」を持たせるための基盤となります。ユーザーの質問をベクトル化し、文書群から類似した断片を検索し、それらをコンテキスト（文脈）としてモデルに与えることで、事実に基づいた回答を生成させることが可能になります。これが RAG の基本形態です。

## RAG は「万能の処方箋」ではない

RAG（Retrieval-Augmented Generation）は、モデルに外部知識や社内文書、最新情報を取り扱わせる上で極めて有効です。しかし、導入すれば自動的に正解が保証されるわけではありません。実務における RAG の失敗は、主に以下のポイントで発生します。

1.  **チャンキング（文書分割）の不備**：重要な文脈が機械的に切断され、意味が通らなくなる。
2.  **検索（Retrieval）の精度不足**：必要な資料をデータベースから見つけ出せない。
3.  **ランキング（Reranking）の失敗**：ノイズとなる情報が上位に来てしまい、根拠が埋もれる。
4.  **生成（Generation）の制約不足**：モデルが与えられた根拠を無視し、ハルシネーション（幻覚）を起こす。

つまり RAG とは、単にベクトル DB を接続することではなく、データ整理、チャンキング、Embedding モデル選型、インデックス構築、検索、リランク、コンテキスト構築、引用、拒答（答えられない場合に断る）、そして継続的な評価（Eval）までを含む、一連のシステムパイプラインなのです。

## ベクトル類似度の限界

「意味的に近いこと」と「そのタスクを解決するために必要であること」は必ずしも一致しません。例えば、ユーザーが「法人アカウントに返金規定は適用されるか」と質問した際、ベクトル検索は「返金規定」に関する一般的な文書を多く拾うかもしれませんが、「法人アカウントに関する例外規定」をピンポイントで落としてしまう可能性があります。

短いクエリ、否定表現、数値、日付、権限管理、法律条文などは、純粋なベクトル検索のみでは扱いが難しい分野です。そのため、本番環境のシステムではキーワード検索（BM25等）、ベクトル検索、メタデータフィルタリング、リランカー、およびビジネスルールを組み合わせた「ハイブリッド検索」が一般的に採用されます。

## 実務上の原則

RAG の第一原則は、**「回答を追跡可能（Traceability）にすること」**です。出典が明示されない回答はデバッグが困難であり、適切な評価セット（Eval Set）のない RAG は改善の方向性を見失います。チャンクサイズ、Embedding モデル、Top-K 数、リランカーの有無、Prompt の表現などを変更する際は、常に同一の質問セットを用いて定量的・定性的に比較できる体制を整えてください。

優れた RAG とは、何でも知っているように振る舞うシステムではなく、「知っていることについては根拠を提示し、知らないことについては正直に『分からない』と言える」システムです。

## 試してみること

本サイトの Radar や Academy から 20 本程度の記事を選び、小規模な RAG を構築してみましょう。20 問のテストデータを用意します（10 問は文書内の直接回答、5 問は複数文書を跨ぐ統合回答、5 問は意図的に答えが含まれない問題）。Top-3、Top-8、および「キーワード+ベクトル」のハイブリッド検索を比較し、各手法の根拠性（Groundedness）を評価してみてください。

## 実務判断：コンポーネントを替える前に「評価」を行う

RAG 開発では、つい Embedding モデルやベクトル DB、チャンクサイズを次々と変更したくなりがちです。しかし、最初に行うべきは「質問セット」と「失敗の基準」を定義することです。評価基盤がないままコンポーネントを入れ替えても、検索結果の見た目が変わるだけで、製品としての品質が向上したかどうかを客観的に判断できません。

最低限チェックすべき 4 指標：正しい根拠が Recall（想起）されたか、それらが上位に並んだか、回答が根拠に忠実か、答えがない場合に適切に拒否できたか。

## ワーク：失敗の分類表を作成する

期待した回答が得られなかった場合、その原因を以下の表のようにラベル付けして蓄積しましょう。

| 失敗タイプ | 典型的な現象 | 優先的に改善すべき点 |
| --- | --- | --- |
| **No-Recall** | 正しい文書がそもそも検索できていない | チャンキング戦略、Embedding、ハイブリッド検索の導入 |
| **Low-Rank** | 根拠は含まれているが下位に沈んでいる | リランカーの導入、メタデータフィルタの最適化 |
| **Synthesis-Error** | コンテキストに根拠はあるが回答が誤っている | Prompt 改善、引用制約の強化、出力チェックの導入 |
| **Over-Answer** | 文中に答えがないのに、推測で答えてしまう | 拒否ルールの厳格化、Grounding 評価の導入 |

この分類表を埋めることで、「RAG の精度が低い」という漠然とした課題を、パイプラインのどの箇所を修正すべきかという具体的なエンジニアリング課題へと変換できます。
