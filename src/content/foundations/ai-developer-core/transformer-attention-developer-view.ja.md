# Attention は何を解決するのか

言語モデルが次のトークンを生成するとき、現在の位置が文脈（コンテキスト）中のどこを参照すべきかを判断する必要があります。初期のシーケンスモデル（RNN や LSTM など）は、すべての情報を一つの連続した状態ベクトルに圧縮しようとしたため、長距離の依存関係が失われやすいという欠点がありました。Transformer の最大のブレイクスルーは、**Attention（アテンションメカニズム）**を導入したことです。これにより、シーケンス内の各位置が、他のすべての位置と直接的な繋がりを持てるようになりました。

開発者視点では、Attention は「動的な問い合わせプロセス」と捉えると理解しやすくなります。現在のトークンが **Query（クエリ）** を発信し、文脈内の各トークンが **Key（キー）** と **Value（バリュー）** を提供します。Query と Key の類似度が「どこに注目するか」を決め、その結果として得られる Value が「どのような情報を取り出すか」を決定します。これはデータベースの検索とは厳密には異なりますが、この比喩は「なぜプロンプト（Prompt）が効果的なのか」を理解するのに非常に役立ちます。

## なぜ例示（Few-shot）が効くのか

Few-shot（少数の例示）は魔法ではありません。これらは本質的に、入力、出力、形式、文体、境界条件といったパターンをコンテキスト内に配置する作業です。生成時、モデルは Attention を通じて現在のタスクを提示された例と照らし合わせ、そのパターンを再利用します。例示が明確で、期待する出力分布に近いほど、モデルは正しい構造を安定して再現できるようになります。

これは逆に、「悪い例」が与える悪影響の強さも説明しています。曖昧な JSON、不要な解説、最終的な指示と矛盾するサンプルなどは、すべて Attention によって補足され、モデルが参照するパターンの一部になってしまいます。モデルは最後の一文だけを読んでいるのではなく、コンテキスト全体を評価し、重み付けしているのです。

## 言い回しよりも構造が重要な理由

優れたプロンプトには、タスク定義、入力データ、制約条件、出力形式、例示、評価基準といった明確な構造が備わっていることが多いです。構造が安定していれば、モデルは Attention を通じて情報の役割（ロール）を正しく識別しやすくなります。長い段落の自然言語で説明を詰め込むと、モデルは内容を理解できても、一貫性のある出力を安定して再現することが難しくなります。

これはプロンプトをガチガチのテンプレートにする必要があるという意味ではなく、コンテキスト内の情報関係を「見つけやすく」することを意味します。見出し、箇条書き、XML タグ、JSON Schema、区切り線などは、すべてモデルに「これはデータ」「これはルール」「これは例」「これは期待される出力」という役割を明示するための重要なツールです。

## 実務上の意味

Attention メカニズムが示唆しているのは、**「コンテキストは量よりも、アドレッサビリティ（検索・参照のしやすさ）が重要である」**ということです。
- RAG（検索拡張生成）の断片にはタイトルと出典を付与する。
- ツール実行結果には明確なフィールド名を持たせる。
- 会話履歴は構造化された状態に圧縮する。
- 長い文書には目次や要約を添える。

モデルが情報を特定しやすくなるほど、出力は安定します。モデルが指示を無視したときは、能力を疑う前に、指示の位置、形式、矛盾、重複を確認してください。多くの「指示に従わない」ケースは、コンテキスト設計が重要な制約に十分な「注意（Attention）」を向けさせていないことに起因します。

## 検証のステップ

同じ抽出タスクに対して、以下の 3 つのプロンプト形式を用意して比較してみましょう。
1. 自然言語のみの説明。
2. 見出しと箇条書きを使った整理された説明。
3. JSON Schema による厳密な定義。

それぞれのフィールド欠落率やフォーマットエラー率を計測します。さらに、わざと矛盾する例を一つ加え、出力がどれだけその誤りに引きずられるかを観察してください。この実験により、Attention は抽象的な概念から「モデルはコンテキスト内のパターンを再利用しようとしている」というエンジニアリング上の直感へと変わるはずです。

## 実務判断：情報の「アドレッサビリティ」を高める

開発者が Attention の数式を暗記する必要はありませんが、コンテキスト設計において「参照のしやすさ」を原則に据えるべきです。モデルは、タイトル、フィールド名、出典、論理的な順序がある情報を扱うのが得意です。一方で、段落に埋もれた制約、正解例に混ざった反例、互いに矛盾する自然言語の指示などは、出力を不安定にさせる要因となります。

複雑なタスクでは、コンテキストを「タスクの目的」「入力データ」「遵守すべきルール」「参考例」「出力 Schema」「チェックリスト」といった明確なブロックに分割しましょう。ブロック名を一貫させ、内容の混線を避ける。これは単なる整理整頓ではなく、生成時にモデルが見るべき場所を間違えないようにするための、確実な工夫なのです。

## 手を動かして試す：3 つの構造を比較する

同じ抽出タスクで、以下の 3 つを試してみてください。

1. 一つの長い段落で指示を出す。
2. Markdown の見出しと箇条書きで整理する。
3. XML または JSON 風の明確な区画（セクション）を作る。

20 件程度のサンプルで、フィールドの欠落、フォーマットエラー、人間の修正時間を比較します。構造化されたプロンプトは必ずしも短くはありませんが、安定性が高く、評価（Eval）も容易になることが実感できるでしょう。
