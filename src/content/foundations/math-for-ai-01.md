# Math for AI：从“像不像”开始理解向量空间

![向量空间与相似度的概念图](/images/foundations/math-for-ai-01/math-vector-similarity-cover.png)

很多人第一次看到 Embedding、向量数据库、余弦相似度时，会以为自己需要补一整门线性代数。其实对 AI 工程实践来说，最先需要的不是手算矩阵，而是一套能帮助你判断系统行为的心智模型。

当你做 AI 搜索、知识库问答、内容推荐、重复文档检测、聚类分析时，系统都在反复回答同一个问题：

**这个输入和哪些东西更像？**

“像”不是一个主观形容词。对大多数现代 AI 应用来说，它通常意味着：模型先把文本、图片、代码或音频表示成一串数字，再比较这些数字在高维空间里的方向和距离。

如果这一层想清楚了，很多问题会变得更容易定位：

- RAG 回答跑偏，不一定是 Prompt 太弱，可能是检索阶段拿错了上下文。
- 搜索结果太泛，不一定是模型“不懂”，可能是用户查询本身在向量空间里没有清晰方向。
- 相似度阈值调高后效果变差，不一定是检索变严格了，可能是你把有用但不完全重复的证据过滤掉了。
- 知识库越堆越大后质量下降，不一定是文档不够多，可能是重复、过期和低信息密度内容让向量空间变脏了。

这篇文章的目标很朴素：用足够工程化的语言解释向量空间和余弦相似度，让你能把它们用于日常 AI 系统诊断。

## 向量到底是什么

向量可以先理解成“模型给一个对象写下的一组坐标”。

一段文本不会直接被放进向量数据库。它会先经过 Embedding 模型，变成类似这样的数字数组：

```txt
[0.018, -0.042, 0.113, ..., 0.007]
```

数组里的每一维不一定对应一个人类可命名的概念。它们合在一起，表达的是模型从训练数据中学到的语义位置。

你可以把它想象成一张极其复杂的地图：

- “FastAPI 依赖注入”和“请求生命周期”应该靠得比较近。
- “uv 项目管理”和“Python 包解析”应该靠得比较近。
- “网球发球动作”和“GitHub Actions 部署”应该离得很远。

真实向量空间不是二维地图，而是几百到几千维的空间。我们很难画出它，但可以通过相似度分数观察它。

## 余弦相似度：比较方向，而不是长度

在向量检索里，最常见的比较方法之一是余弦相似度。它关注的是两个向量的方向是否接近。

$$
\cos(\theta) = \frac{a \cdot b}{\|a\| \|b\|}
$$

你不需要记住公式的每个细节，只要记住一个工程含义：

**余弦相似度在问：两个内容表达的语义方向是不是一致？**

这解释了几个常见现象。

第一，短查询可以匹配长文档。一个 12 字的问题和一篇 2000 字的文章长度完全不同，但如果它们指向同一主题，相似度依然可以很高。

第二，重复内容分数通常很高。原文、摘要、改写稿、翻译稿可能在方向上非常接近，所以会被判定为相似。

第三，泛泛的问题容易命中泛泛的内容。比如“怎么提升 AI 应用质量”这样的查询，可能同时靠近评测、Prompt、RAG、监控、数据质量等许多主题，结果自然会变散。

## 相似度分数应该怎么读

不同模型、不同向量库、不同归一化方式会让分数区间有所变化，所以不要把下面的数值当成绝对真理。它更像一个阅读方向。

| 分数区间 | 常见含义 | 工程判断 |
| --- | --- | --- |
| 0.90 以上 | 高度重复或几乎同义 | 适合去重、合并、找原文，不一定适合回答复杂问题 |
| 0.75 到 0.90 | 强相关 | RAG 常见可用区间，需要结合 chunk 内容判断 |
| 0.55 到 0.75 | 中等相关 | 可能有部分证据，适合作为候选而不是直接信任 |
| 0.35 到 0.55 | 弱相关 | 多半需要改写查询、补关键词或扩大知识库 |
| 0.35 以下 | 相关性很低 | 通常说明知识库缺内容，或查询方向严重不清 |

真正可靠的做法不是迷信一个全局阈值，而是针对业务建立自己的样本集。你可以抽取 30 到 50 个真实查询，记录人工认为应该命中的文档，再观察它们的相似度分布。这个分布比任何通用经验值都重要。

## 为什么模糊查询会拖垮 RAG

![模糊查询与具体查询在检索空间中的差异](/images/foundations/math-for-ai-01/query-specificity-vector-search.png)

来看一个常见场景。

你有一个工程实践知识库，里面包括 FastAPI、uv、CI/CD、可观测性、Agent Runtime、内容站点部署等文章。用户输入：

> “这个怎么做比较好？”

从人类对话上下文看，也许你知道“这个”指的是 FastAPI 项目结构。但向量检索系统看到的只是一句非常贫乏的文本。它没有足够语义坐标，只能在向量空间里落到一个模糊位置。

改成下面这样，检索质量通常会明显提升：

> “FastAPI 项目里如何拆分路由、依赖注入、数据库 session 和后台任务，避免后期迁移到微服务时重构过重？”

这个查询包含了明确对象、工程动作、约束条件和失败风险。向量方向更清晰，召回的文档也更可能集中。

这就是为什么很多 RAG 系统会在检索前做 query rewriting。它不是为了把问题写得更好看，而是为了让查询在向量空间里落到更准确的位置。

## RAG 诊断：先看检索，再看生成

RAG 系统出错时，人们常常第一时间改 Prompt。更稳妥的顺序应该是：

1. 先看用户问题。
2. 再看检索返回的 chunk。
3. 再看相似度分布。
4. 最后才看生成模型为什么这样回答。

如果检索返回的上下文本来就错了，生成模型只能在错误证据上努力。它可能会写得很流畅，但不会突然拥有正确材料。

一个实用的诊断表：

| 现象 | 向量层可能原因 | 优先动作 |
| --- | --- | --- |
| 回答引用了不相关文档 | 查询太泛，或 chunk 主题混杂 | 改写查询，重新切分 chunk |
| 检索结果全是同一篇文章的重复片段 | 文档重复，chunk overlap 过高 | 去重，降低 overlap，加入多样性 rerank |
| 正确文档排在很后面 | 关键词很关键但语义相似度不突出 | 使用 hybrid search，把关键词检索和向量检索结合 |
| 相似度整体偏低 | 知识库缺内容或领域不匹配 | 补充高质量文档，不要只调 Prompt |
| 相似度很高但答案仍然错 | chunk 过短、缺上下文或证据冲突 | 扩大上下文窗口，加入引用检查 |

## 不要把向量检索当成全文搜索的替代品

向量检索擅长找语义相近的内容，但它不擅长所有事情。

如果用户要找精确字符串、错误码、版本号、配置字段、函数名，关键词检索往往更可靠。比如：

- `PydanticUserError`
- `OPENAI_API_KEY`
- `upload-pages-artifact@v3`
- `asyncio.CancelledError`

这些词的价值在于“字面完全匹配”。向量模型可能知道它们大概属于某个技术领域，但不一定能保证精确命中。

所以生产系统里常见的方案是 hybrid search：

- 向量检索负责语义召回。
- 关键词检索负责精确召回。
- reranker 或业务规则负责最终排序。

这比单纯追求“更强的 Embedding 模型”更现实。

## 知识库健康度可以用相似度分布观察

![RAG 检索健康度与相似度分布](/images/foundations/math-for-ai-01/rag-retrieval-health-map.png)

如果你维护一个 RAG 知识库，可以定期抽样做健康检查。

选取一批真实问题，记录每个问题的 top-k 检索结果和相似度分布，然后看四类信号。

| 信号 | 可能解释 | 处理方式 |
| --- | --- | --- |
| 大量查询没有高分结果 | 知识库覆盖不足 | 补核心文档，而不是扩 Prompt |
| 大量结果集中在 0.95 以上 | 重复内容太多 | 去重、合并、保留权威版本 |
| top-1 与 top-5 分数差距很小 | 主题边界不清 | 改 chunk 策略，加入 metadata |
| 高分结果来自过期文档 | 新旧版本混杂 | 加时间权重，归档旧文档 |

这类检查很适合进入 CI 或离线评测流程。你不必每次上线都人工阅读全部文档，但至少可以让系统告诉你：知识库正在变清晰，还是正在变脏。

## 案例：一个看似 Prompt 问题的检索失败

假设团队做了一个内部工程助手，用户问：

> “部署后图片为什么不显示？”

模型回答了一大段浏览器缓存、CDN、文件权限相关内容，但没有解决问题。大家开始改 Prompt，要求模型“更认真地分析路径问题”。效果仍然不稳定。

后来检查检索日志，发现 top-3 文档是：

1. CDN 缓存策略。
2. 图片压缩流程。
3. Markdown 图片语法。

真正应该命中的文档是“GitHub Pages base path 与 Astro 资源路径”，但它排在第 9 位。原因是用户查询太短，关键词“部署后图片不显示”可以靠近很多主题，而正确文档标题里写的是 `base`、`subpath`、`asset resolution`。

修复方案不是继续加 Prompt，而是三步：

1. 检索前把查询改写为：“静态站点部署到 GitHub Pages 子路径后，`/images/...` 或相对资源路径为什么失效？”
2. 加入关键词检索，提升 `base`、`subpath`、`asset`、`GitHub Pages` 相关文档权重。
3. 在答案生成前要求模型引用检索到的路径配置片段。

结果是答案质量明显稳定。这个案例说明：RAG 的第一性问题常常不是“模型会不会写”，而是“证据有没有找对”。

## 常见反模式

**反模式一：把相似度阈值设得过高。**

阈值过高会让系统只召回几乎重复的文本。复杂问题需要的是互补证据，不只是同义句。

**反模式二：只看 top-1。**

top-1 错了不代表检索系统完全失败。你应该看 top-k 是否包含正确证据，以及 rerank 是否能把它提上来。

**反模式三：不记录被过滤掉的结果。**

很多系统只保存最终传给模型的 chunk。这样出错时无法判断是召回失败、排序失败，还是生成失败。

**反模式四：把 chunk 切得越小越安心。**

chunk 太小会丢失上下文。一个函数名或标题本身可能很相似，但缺少解释段落时，生成模型仍然无法回答。

```md
- 是旧文档污染了吗？

### Action

- 查询改写：

```

## 检查清单

- 查询是否包含明确对象、动作、约束和上下文？
- top-k 里是否至少有一个人工认可的证据？
- 是否同时保存了召回结果、过滤结果和最终上下文？
- 是否对版本号、错误码、API 名称使用关键词召回？
- 是否定期检查知识库重复、过期和低信息密度内容？
- 是否用真实用户问题建立过小型检索评测集？
