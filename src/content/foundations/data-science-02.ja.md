# Data Science：AI アプリにおけるデータ品質思考

![AI アプリのデータ品質ワークベンチ](/images/foundations/data-science-02/data-quality-ai-cover.png)

「Garbage In, Garbage Out」はデータサイエンスの古い格言に見えます。しかし AI アプリでは、より広く、より見落とされやすい原則になっています。

あなたはモデルを学習していないかもしれません。pandas のスクリプトを書いていないかもしれません。それでも日々データを扱っています。

- Prompt を書くとき、指示データを整理している。
- RAG を作るとき、文脈データを選んでいる。
- tool calling を調整するとき、ツール入力と出力データを制約している。
- eval を作るとき、評価サンプルと期待回答を定義している。
- ユーザー feedback を見るとき、失敗例を集めている。
- Agent を保守するとき、保存すべき中間状態を決めている。

モデルの振る舞いが悪いと、「モデルが弱い」「Prompt が悪い」と考えがちです。しかし多くの実問題はデータ層にあります。入力が混乱している、文脈が古い、例が矛盾している、ツール戻り値の形式が不安定、評価サンプルがきれいすぎる、といった問題です。

データ品質思考は、従来の前処理ステップではありません。モデルに行動させる前に、渡す材料が信頼できるかを見るエンジニアリング習慣です。

## AI アプリの「データ」は思ったより広い

従来のデータサイエンスでは、データは表、ログ、イベント、特徴量、ラベルを指すことが多いです。AI アプリでは範囲が広がります。

| データ種類 | 例 | よくある品質問題 |
| --- | --- | --- |
| 指示データ | system prompt、タスク説明、形式要求 | 目標衝突、制約過多、曖昧表現 |
| 文脈データ | RAG chunk、ファイル内容、会話履歴 | 古い、重複、重要段落がない |
| 例データ | few-shot 例、参考回答 | 例が矛盾、場面のカバー不足 |
| ツールデータ | API 戻り値、DB クエリ、検索結果 | schema 不安定、フィールド欠落、エラーが非構造化 |
| 評価データ | benchmark、golden set、失敗サンプル | きれいすぎる、少なすぎる、実ユーザーと違う |
| フィードバックデータ | thumbs down、問い合わせ、人工修正 | 分類なし、元入力なし、再現不能 |

これらをすべてデータとして見ると、AI エンジニアリング問題の扱い方が変わります。

## データ品質の五つの視点

![入力品質レビューの五つの視点](/images/foundations/data-science-02/input-quality-review.png)

AI アプリで特に実用的な品質視点は五つです。

| 視点 | 診断質問 | 例 |
| --- | --- | --- |
| 関連性 | このデータは現在のタスクに関係するか | RAG が同じ領域だが別問題の文書を返す |
| 完全性 | 重要情報が欠けていないか | コード修正を依頼したがエラーログがない |
| 一貫性 | 複数ソースが矛盾していないか | 文書は v1、サンプルコードは v2 API |
| 新鮮度 | 情報はまだ有効か | 古い SDK 用法が回答に混ざる |
| 解析可能性 | モデルやプログラムが安定して読めるか | ツールが自由文を返し、次工程は JSON を期待する |

入力は完璧でなくてもよいですが、現在のタスクを支えるだけの品質は必要です。実務上の問いは「きれいか」ではなく、「この判断を支えられるか」です。

## Prompt 問題はデータ問題であることが多い

多くの Prompt 改善は、実際にはデータ修正です。

例えば次の依頼があります。

> 「信頼できるリリースノートを書いてください。」

出力が一般的になるのは、入力データが少ないからです。より良い入力には次が必要です。

- 変更一覧。
- ユーザーに見える影響。
- 破壊的変更の有無。
- 移行手順。
- 既知の問題。
- 検証コマンド。
- 書いてはいけない内部詳細。

これらが揃えば、Prompt は神秘的である必要はありません。既存材料をどう整理するかを明確に伝えればよいだけです。

Prompt を増やす前に、五つの質問をします。

1. 十分な事実を渡しているか？
2. 事実同士が矛盾していないか？
3. 古い情報が混ざっていないか？
4. 無関係なノイズが多すぎないか？
5. 出力基準は検証可能か？

ここを処理しないまま形容詞的な指示を足しても、効果は限られます。

## RAG の品質は検索アルゴリズムだけで決まらない

RAG システムの入力は、ユーザー質問そのものではありません。「ユーザー質問 + 検索された文脈」です。文脈品質が回答の上限を決めます。

ナレッジベースのよくある問題です。

- 文書が古く、現在の API と一致しない。
- 同じ主題に複数バージョンがあり、互いに矛盾する。
- 文書が細かすぎ、chunk が文脈を失う。
- 文書が長すぎ、検索は命中するが証拠が埋もれる。
- タイトルは明確だが、本文に引用できる詳細がない。
- 重要な意思決定がチャットにだけあり、文書化されていない。

RAG は全文書をベクトルデータベースに入れたら終わりではありません。検索可能な知識プロダクトの保守です。

最小の健康診断です。

1. 実ユーザー質問を 20 件集める。
2. 各質問で命中すべき文書を人間がラベル付けする。
3. 検索を実行し、top-k を記録する。
4. 命中しない質問をラベル付けする。
5. 原因が文書不足、chunk 問題、クエリの広さ、順位付けのどれかを判断する。

この作業は、ただベクトルデータベースを交換するより価値があります。

## 評価データには失敗とノイズを入れる

![失敗ログから育つ評価データセット](/images/foundations/data-science-02/failure-log-eval-dataset.png)

多くの AI アプリの評価セットはきれいすぎます。問題文が完全で、入力形式が標準化され、答えの境界が明確です。これは出発点として有用ですが、実ユーザーを代表しません。

実ユーザーは次のように入力します。

- 誤字を書く。
- ログを半分だけ貼る。
- 中国語、英語、日本語を混ぜる。
- 文脈を省略する。
- 内部略語を使う。
- 複数の目標を一度に出す。
- 前の依頼を途中で変更する。
- 矛盾した要求を出す。

評価セットにこうしたノイズがなければ、公開後にシステムは急に脆くなります。

より良い方法は、評価セットを失敗ログから育てることです。

失敗が起きるたびに記録します。

- 元の入力。
- 当時の文脈。
- 期待出力。
- 実際の出力。
- 失敗分類。
- 修正方法。
- 回帰評価に入れたか。

30 件たまると、一般的な benchmark よりプロダクトに近い golden set になります。

## Agent システムは構造化データに強く依存する

通常のチャットが失敗しても、ユーザーは聞き直せます。Agent が失敗すると、ツール呼び出し、ファイル変更、外部リクエストが起きる可能性があります。データ品質の要求は高くなります。

Agent Workflow で壊れやすいデータです。

- 計画ステップに一意な ID がない。
- ツール出力が自然文で、次工程が安定して解析できない。
- エラーに code がなく、「失敗」とだけ書かれている。
- 中間状態が保存されず、再試行で文脈が失われる。
- 人間承認の結果が構造化されていない。
- 最終報告に実際の検証証拠がない。

Agent システムにおいて、構造化データは単なる形式主義ではありません。復旧能力です。構造化状態がなければ、局所リトライ、監査、リプレイは難しくなります。

## ケース：出力不安定の原因は例データの矛盾

あるチームがカスタマーサポート返信生成を作りました。Prompt は詳しく、丁寧な語調、明確な結論、ポリシー外の約束禁止を指定しています。それでも出力は安定しません。

調べると、few-shot 例に三つの問題がありました。

1. 例 A は返金ポリシーに厳格。
2. 例 B はユーザーを安心させるため、特別対応を示唆。
3. 例 C は古い製品名を使っている。

モデルは「指示を聞いていない」のではありません。矛盾する例から矛盾するパターンを学んでいました。

修正です。

- 古いポリシー例を削除する。
- 各例に適用場面を付ける。
- 「特別対応を約束しない」を明確な負例にする。
- 実失敗例を評価サンプルに入れる。
- 出力にポリシー引用チェックを追加する。

Prompt 制約を積み増すより、ずっと安定しました。これは典型的なデータ品質問題です。

## よくあるアンチパターン

**アンチパターン 1：すべての失敗をモデル能力のせいにする。**

強いモデルは一部を緩和できますが、古い、矛盾した、欠けたデータを安定して直すことはできません。

**アンチパターン 2：成功サンプルだけを残す。**

成功サンプルは報告をきれいにします。失敗サンプルはシステムを強くします。評価セットには失敗が必要です。

**アンチパターン 3：評価データが実ユーザーと離れている。**

理想入力だけで評価すると、公開後のノイズで性能が急落します。

**アンチパターン 4：ツールが自由文を返す。**

自由文は人間には読みやすいですが、次のツール入力には向きません。Agent ツールは構造化データを優先します。

**アンチパターン 5：元入力を記録しない。**

元入力がなければ失敗を再現できません。再現できなければ、信頼できる改善はできません。

## チェックリスト

- 入力に、タスクに必要な重要事実が含まれているか？
- 文脈は古い、重複、矛盾を含んでいないか？
- 例は正例と反例をカバーしているか？
- ツール出力は構造化され、次工程が安定して解析できるか？
- 評価セットに実ノイズと失敗例が含まれているか？
- 各失敗で元入力、期待出力、実際の出力を記録しているか？
- 改善は現在の Prompt 修正だけでなく、回帰評価に入っているか？
