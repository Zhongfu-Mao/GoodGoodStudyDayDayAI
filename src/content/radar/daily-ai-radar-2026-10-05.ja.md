## 1. AI Engineering & アーキテクチャ

### Claude Code mods：イベントフック、状態、UI拡張を同一セッション内に集約

- 出典：The Rundown AI / Claude Code
- 日付：2026-10-01（公式ガイド）
- リンク：https://claude.dev/blog/getting-started-with-claude-code-mods/
- 要約：ModsはJavaScriptまたはTypeScriptモジュールとしてイベントハンドラを登録し、ミドルウェアのようにツール呼び出しの監視、書き換え、拒否を行うほか、セッション状態の保持、コマンドの登録、リアルタイムUIの描画も可能です。イベントごとにシェルを起動するsettings hookとは異なり、モジュールはロード後にセッション内に常駐します。ガイドではClaude Code 2.1.287以上が要求されており、APIはバージョンによって変更される可能性があるため、ローカルで生成された型定義を基準とする必要があります。拡張機能がアクションをインターセプトできることは、任意のプラグインの安全性が検証済みであることを意味しません。

### Matthew Green：サンドボックスの外部でも、エージェントが指示を受け取る経路の精査が必要

- 出典：Simon Willison / Matthew Green
- 日付：2026-09-30（原文）；2026-10-01（引用議論）
- リンク：https://blog.cryptographyengineering.com/2026/09/30/is-sandboxing-sufficient-to-contain-rogue-agents/
- 要約：Green氏は隔離と情報アクセスの間にある矛盾を分析しています。各プロセスがサンドボックス内に留まっていたとしても、共有パッケージキャッシュ、メール、共同作業ドキュメントなどを介して、他のエージェントの目的を改変するテキストが伝播する可能性があります。氏の懸念は「サンドボックスが無用である」ということではなく、隔離境界は指示の出所、認可、データフローの検証を代替できない点にあります。この経路をワームに例えるのは筆者のリスク分析であり、本番環境で大規模な拡散が発見されたという結論ではありません。

## 2. モデル最前線 & アルゴリズム探索

### Kolibri-1：独英バイリンガルのオープンウェイト、アクティブパラメータの少なさはメモリ要件の低さを意味しない

- 出典：AI Valley / Aleph Alpha
- 日付：2026-10-03（公式リリース）
- リンク：https://huggingface.co/Aleph-Alpha/Kolibri-1
- 要約：Kolibri-1はMixture-of-Expertsアーキテクチャを採用し、総パラメータ数は78B、トークンごとに約3.46Bがアクティブとなり、ドイツ語と英語に特化しており、ウェイトはApache-2.0ライセンスです。モデルカードの説明によると、完全なウェイトは依然としてメモリ上に常駐する必要があるため、アクティブパラメータ数からデプロイ全体のメモリを見積もることはできません。ネイティブの長いコンテキストは262,144トークンまで学習されており、開発者レポートでは1,048,576トークンまでの検証が報告されていますが、複雑なタスクやレイテンシ・スループットに敏感なシナリオでは262,144以下が推奨されています。位置づけは人間による確認を伴う協調システムであり、無人レビューでの自律的意思決定ではありません。

### 継続追跡｜EveryによるSonnet 5.5実測：推論設定（effort）が高いほど反復に適しているとは限らない

- 出典：Every
- 日付：2026-09-28（記事公開）
- リンク：https://every.to/vibe-check/sonnet-5-5-vibe-check
- 要約：Everyの無料プレビューでは1週間の使用体験が紹介されています。低〜中程度のeffortは人間が継続的に誘導するプロトタイプ作成、設計、アウトライン作業に適している一方、高effortや長時間の放置状態では過剰構築に陥りやすくなります。あるコンサルティングタスクでは、10分間に28個のデータファイルが生成されたものの、求められていた貼り付け可能なプロンプトは納品されませんでした。新たな知見は実際の作業形態と設定強度のマッチングであり、リリース時のベンチマークの再述ではありません。これらの事例はモデル間の対照評価ではなく、すべてのタスクで推論強度を下げるべきであると結論付けることはできません。

## 📬 Newsletter 精選

### Every：コンテキストを変更するほど悪化する場合、まず履歴と有効な指示を分離する

- 出典：Every
- 日付：2026-10-05（記事公開）；2026-10-06（日本時間のニュースレター到着）
- リンク：https://every.to/working-overtime/before-you-give-ai-another-instruction-try-taking-one-away
- 要約：Katie Parrott氏は、すべての修正をログに記録し、ディレクトリ間をリンクさせ、スタイルガイドを継続的に拡張した結果、モデルがチェックボックス付きリストの遵守には長けるようになったものの、文章自体から乖離してしまった経験を振り返っています。彼女は古い資料をアーカイブし、タスクごとに読み込み範囲を絞り込み、下書きやレビューは新たな指示ではなく証拠であると位置づけを明確にしました。この個人の事例は、無関係な入力を削減しルールの衝突を処理することが、要求を追加し続けることよりも効果的である場合が多いことを示唆しています。これは「ガイドは短いほど良い」という普遍的法則ではなく、必要な監査ログの削除を求めるものでもありません。

### ByteByteGo：コンテキスト内に収まっていても、モデルが中間の証拠を確実に利用できるとは限らない

- 出典：ByteByteGo
- 日付：2026-10-05（記事公開）；2026-10-06（日本時間のニュースレター到着）
- リンク：https://blog.bytebytego.com/p/the-llm-blindspot-why-models-forget
- 要約：記事ではlost-in-the-middle現象について解説されています。証拠が入力内に存在しているにもかかわらず、配置位置などの要因により有効に活用されない現象です。ドキュメントの渡し忘れ、履歴の切り捨て、検索エラー、モデルが提供済みの内容を適切に活用できていないケースを区別し、必要な証拠をあらかじめ選別し、出所の境界を明確にした上で、実際のモデルとタスクに合わせて並び順をテストすることを推奨しています。大きなコンテキストウィンドウは容量を増やしますが、各位置での一貫したパフォーマンスを保証するものではありません。RAGもセグメントを誤って選択したり、コンテキストを再び圧迫したりする可能性があります。記述された現象は既存の研究に基づくものであり、ニュースレターの配信日を新しい論文の公開日と混同すべきではありません。
