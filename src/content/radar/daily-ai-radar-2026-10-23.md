### ThinkingBox：训练“真的完成”，也要同时看稳定性与覆盖面

<a id="radar-thinkingbox-training"></a>

- 来源：Hugging Face / Microsoft
- 来源渠道：博客
- 证据性质：作者研究
- 原始日期：2026-10-22
- 链接：https://huggingface.co/blog/microsoft/thinkingbox-training
- 摘要：ThinkingBox 不靠智能体最后一句“已完成”判分，而是检查任务结束后的数据库记录和副作用。作者把这种校验用作训练奖励，在基准之外选出 187 个训练任务，对 Qwen3.8-27B 做 50 步 GRPO，再在独立的 507 个 ThinkingBox-Bench 任务上各运行 20 次。

原文的反例很直观：模型做了九次看似称职的工具调用，把客户工单关为“已解决”，底层承运商异常记录却仍开着。终态校验看的是应当改对的记录，而不要求一种固定调用顺序。大多数任务能直接给出可执行的 0/1 结果；少数难以仅由数据库判断的要求，仍借助模型回答二元评分问题，不能一概叫完全确定性的裁决。

| 指标及分母 | 训练前 | 训练后 |
| --- | ---: | ---: |
| 每个任务 20 次全成功的任务数（507 项中） | 38 | 107 |
| 单次平均成功率（10140 次尝试） | 51.70% | 60.78% |
| 20 次至少成功一次的任务数（507 项中） | 453 | 446 |

结果显示重复可靠性提高，但至少能解一次的覆盖面少了七项。训练选题也有原因：八次尝试全失败或全成功的组，在 GRPO 组内比较中没有差异，学习信号弱；作者先按基础模型的成功概率挑中间难度任务，再固定训练池。这个难度只在训练前估计，不是动态保证。

507 项评测没有进入训练池，但两者共享任务框架、模拟用户和终态评分方式，迁移范围不能被说成任意企业流程。公开样例也不是实验使用的全部 187 项私有训练任务。这里最值得复用的是把“有没有完成”连接到业务状态，并同时保留改善与退步的指标。

### Granite 时序集成：区间更窄不等于预测更可靠

<a id="radar-granite-forecast-ensemble"></a>

- 来源：Hugging Face / IBM Research
- 来源渠道：博客
- 证据性质：作者研究
- 原始日期：2026-10-22
- 链接：https://huggingface.co/blog/ibm-research/granite-timeseries-ensemble-r1
- 摘要：Granite 把四种预训练时序架构接到统一预测接口：分块 Transformer、分块 Conformer、状态空间模型和 MLP Mixer。它们对趋势、季节性和局部变化的误差不一定相同，组合预测可减少事先猜哪一个模型最适合数据的负担。

默认方案在概率空间均匀合并各成员的分位数预测，再取合并分布的中位数和所需分位数，不为新数据拟合组合权重。IQR 方案是另一条可比较的分支：预测四分位距越窄，权重越大，权重随样本、目标和预测步变化，并用保序回归避免分位数交叉。问题是过度自信的模型也可能给出很窄的区间，因此 IQR 不能直接读成“按准确率加权”。

97 个 GIFT-Eval 数据配置的汇总中，默认组合 MASE 为 0.683，最强单成员 PatchTST-FM-r2 为 0.685，优势很小；概率误差 CRPS/MWQL 则是单成员 0.467 优于组合 0.471。平均误差与平均名次也不是一个指标。作者提供的是一个稳妥起点，不是所有序列、跨度与指标上的冠军。

接口默认输出 0.1 到 0.9 分位数，两个端点构成名义 80%的预测区间，但实际覆盖率需要在有代表性的历史窗口回测。配方文件保存配置，首次运行还要下载四个成员，并非一份已合并的权重；评估时也要计入延迟、内存和新增成员的许可证条件。

### 多模态 RAG：先判断足不足以回答，再把不足接到人工流程

<a id="radar-jev-rag-review"></a>

- 来源：Daily Dose of Data Science
- 来源渠道：Newsletter
- 证据性质：观点推演
- 原始日期：2026-10-22
- 链接：https://blog.dailydoseofds.com/p/build-a-jev-powered-agentic-rag
- 摘要：文章用“Jev 驱动 RAG”介绍有界决策的思路，但实际示例采用 Liquid AI 的 d1-3B 作相关性与可回答性判断，EmbeddingGemma 2 作多模态嵌入，InsForge 承接数据库、认证和人工复核，模型另在 Lightning 托管。概念示例与实际部署模型不能混为一谈。

检索同时索引约 220 词的文本块和整页 PNG。保留整页是为了不丢掉矢量图表、图注与周围文意；查询也可带截图，分别搜索文字和页面，再合并同一页的结果。决策模型判断相关性之外，还要判断证据能否支持回答，文字与图像阈值分开存于数据库，便于按实例调整。

没有候选通过时，先扩大搜索；仍不足则不调用生成模型，而是建支持工单。数据库触发器把工单送到客服面板，人工能看到被拒页面与得分，邮件回复离开聊天的客户，还能将已确认的问答存成新知识。生成端使用 Claude Haiku 5.5，只从给定证据回答并附引用；这套约束仍需实际测试，不是模型名称带来的保证。

作者在相同候选集上用 75 个标注问题比较三种管线，涵盖文字可答、仅截图可答、带截图提问和应转人工四类。结果支持这个示例中决策门的用途，但不能把小样本教程当广泛生产准确率。真正补齐的环节是“证据不够以后怎么办”，而不是再调一次提示词。

### Decisions API：把高频小判断变成预定义答案，而非每次生成一段解释

<a id="radar-decisions-api-ga"></a>

- 来源：OpenAI
- 来源渠道：官方
- 证据性质：官方宣称
- 原始日期：2026-10-22
- 链接：https://openai.com/index/decisions-api
- 摘要：基于 GPT-6 Luna 的 Decisions API 正式可用。开发者先定义问题与允许答案，再交入文字、图片或原生 JSON，得到条件成立的概率、预定义选项或量表分数。它适合分类、路由、是否重试等反复出现的有界决策。

三个返回类型的作用不同：predicate 估计条件成立的概率；choice 从给定值中选择，并返回概率与置信信息；score 是量表等级索引的概率加权平均，不能自动当成已经校准的业务损失。每次请求最多 400 个问题，更新还包括复用上下文的提示缓存、美欧推理驻留与 GPT-Live 原生集成。

实时语音示例用转写更新触发表情选择，应用读取 decision.event 后真正驱动角色动画。这个分工与前面的 RAG 类似：模型给结构化判断，软件执行下一步。官方“最高十倍更快”对比的是通过 Responses API 调用同一 Luna 模型；文档没有披露内部解码机制，不能由“只收输入费用”推导出只计算少数答案，或任意任务的计算量都大幅下降。

### Modal：把三年容量合同切成按需任务，难点不只在自动扩容

<a id="radar-modal-elastic-capacity"></a>

- 来源：Latent.Space / Modal
- 来源渠道：播客、Newsletter
- 证据性质：官方宣称
- 原始日期：2026-10-22
- 链接：https://latent.space/p/modal-d/
- 摘要：Erik Bernhardsson 把固定 GPU 数量、固定租期的合同称为“矩形”，真实需求却有昼夜波动、突发批处理和模型更替。Modal 在底层取得长期容量，汇集多客户的不同曲线，再向上切成细粒度弹性使用。这是调度问题，也是长约与按需收入之间的期限转换。

访谈中，长约常在未来数月交付并锁定三年，采购还涉及不同地区供应商。汇集需求能提高利用率，但如果 GPU 价格、使用量与转售机会同时下降，提前买下的容量会成为风险。融资或收入规模没有消除这一错配，也不证明某个用户一定用它更划算。

工程上，弹性调用要加载很大的模型权重，容器启动、CPU/GPU 快照、自建文件系统、调度和 KV 路由就共同影响等待时间。受访者设想的测试场景是先安装环境并做快照，再克隆多个隔离沙箱并行运行，而不是让每份测试都重复准备依赖。快照能减少重复初始化，仍不能把共同依赖和串行部分凭空变没。

原文还讨论以完整虚拟机补充沙箱的内核兼容性，以及很短生命周期的任务需求。这里保留的是团队对结构与取舍的说明；访谈没有给出自建文件系统的具体命中率，也不能把期望的百毫秒唤醒目标写成所有实例都已达到的实测服务指标。

- 来源渠道：播客、Newsletter
- 证据性质：官方宣称
- 原始日期：2026-10-22
- 链接：https://latent.space/p/moshi/
- 摘要：Moshi 创始人 Anekha Sokhal 从能源衍生品交易转向信息产品，想解决的不是缺少新闻流，而是交易员无法及时连接与自己关注领域间接相关的变化。她把产品描述成市场资料、AI 交互与推荐系统的组合，不是单纯再造一个仪表盘。

她举的例子是，能源股票公司的变化可能间接影响石油市场，孤立新闻流未必能及时提醒对应用户；系统试图用连接图与推荐，把相关信息带到原有工作里。底层还要处理可信来源、企业上传的杂乱 PDF 和内部系统连接，文章讨论了自建视觉语言模型做文档理解，以及数据交给第三方处理时需要什么协议。

这里的可借鉴之处是先明确使用者已经怎样工作、什么关联值得提醒，再选模型或买工具。访谈是创始人的产品解释，没有可独立核验的交易收益或推荐准确率；“相关”不能直接升级成“应当买卖”的结论。

### FDE：先找出真实部署缺口，再把可以通用的部分还给产品

<a id="radar-fde-deployment-gap"></a>

- 来源：OpenAI
- 来源渠道：官方
- 证据性质：官方宣称
- 原始日期：2026-10-22
- 链接：https://openai.com/index/forward-deployed-engineering-means
- 摘要：OpenAI 将驻场工程的作用分成两条：模型已经能做的工作，和客户一起做成可重复方案；还做不到的工作，将具体失败与评测反馈给研究团队。目标不是让每个客户永远依赖一套定制外壳。

半导体案例中，约 15 名 FDE 参与十余用例，先与客户工程师一起学习领域、做定向测试生成和故障诊断的评测，再构建专用工作流。随着 Codex 能力改进，团队将定制应用改成共享的技能与插件，称各项目约 90%的定制代码得以移除；一个案例从首次部署两个月，到第二团队扩展一天。这个对比是供应商描述的具体项目经历，不是所有项目都能 90%减码的通用定律。

另一个电信语音案例初期关键评测约 60%，团队没有靠包装宣称可投产，而是与研究侧继续改进调用和指令遵循，半年内从约 60%升至 80%，再到 90%以上。它提醒交付团队分清产品集成缺口与模型能力缺口，分别改进。农业案例里“除草剂最多节省 70%”则来自既有 See & Spray 视觉技术，不能全归因于后来接入的语言模型支持。

<a id="radar-every-frontier-team"></a>

- 来源：Every / Laura Entis
- 来源渠道：Newsletter
- 证据性质：官方宣称
- 原始日期：2026-10-22
- 链接：https://every.to/context-window/keeping-up-with-ai-is-a-full-time-job
- 摘要：Every 用一个小组集中试新模型和工作方式，让其余团队继续推进路线图。真正的交付不只是“又发现一个新工具”，而是把试验整理成文章、产品与可复用方法，降低同事跟进每次变化的成本。

作者举了两个具体例子。负责评测的 Mike 把零散讨论与会议中的产品想法压成简短说明，再制作带截图标注的解释视频；写作工具则加入目标读者文件，用它检查哪些段落会让读者跟不上。这些做法把原本只在制作者脑中的上下文，转成其他人能使用和批评的材料。

同一期还介绍一个反复出错的内部看板：先让一个编码智能体审架构并列优先修复计划，再让另一模型提供者的智能体批评计划，最后把批评带回修改后再动代码。它没有证明不同模型就一定正确，但把制作、独立质疑和实际修正拆成可见步骤，比让同一个执行者再自信确认一次更有检查价值。以上是团队经验，不是跨团队的对照实验。

### Andrew Ng 的四个 P：AI 原生团队的瓶颈，已经不只在写代码

<a id="radar-ai-native-four-ps"></a>

- 来源：The Batch / DeepLearning.AI
- 来源渠道：Newsletter
- 证据性质：观点推演
- 原始日期：2026-10-23
- 链接：https://www.deeplearning.ai/the-batch/tag/oct-23-2026/
- 摘要：Andrew Ng 将工程团队转型分成人员（People）、项目（Projects）、平台（Platforms）、流程（Processes）。四个部分连在一起：个人会用工具，没有项目选择与数据基础，也不自动形成能交付的 AI 团队。

人员方面，他建议管理者自己至少偶尔动手构建，借此形成技术和业务判断；项目不应只盯效率，还要选能创造产品和增长的机会。平台工作则很具体：让代理在恰当安全边界下取得代码、设计决策、支持记录与内部工具，并有评审、CI 和运行环境。

流程需要围绕新瓶颈重排。明确规格后的构建变快，决定做什么、理解用户和协调依赖就更显眼；高上下文、能参与产品判断的工程团队，才有可能利用这段速度。作者倡导在泄露、重大中断、数据丢失等风险上保留适当保护，并未主张取消所有检查。它是一套管理观察与行动框架，不是已经测得生产率提升百分比的研究。
