## 今日のシグナル

Azure が Agent Runtime のプレビュー版を公開しました。これは Agent の実行環境が「開発者のローカルスクリプト」から「クラウドホスティング・サービス」へと進化することを象徴しています。主な変更点は以下の 3 点です。

1. **状態の永続化（State Persistence）**：会話履歴、タスクの進捗、ツール呼び出しのログがクラウド上に自動的に保存されます。これにより、ローカルメモリへの依存を完全に排除できます。
2. **ツール登録センター**：統一されたフォーマットでツールを登録でき、Agent による能力の自動発見（Auto-discovery）が可能になります。
3. **実行監視（Monitoring）**：実行ごとのツール呼び出しチェーン、トークン消費量、エラー詳細が可視化され、システムの観測可能性（Observability）が向上します。

## なぜ注目すべきか

これまで Agent システムを構築する際、開発者は状態管理やツールのオーケストレーション、ログ監査といったインフラ部分を自前で実装する必要がありました。これは多大な工数がかかるだけでなく、チームごとに実装が異なり、標準化が難しいという課題がありました。

Azure Agent Runtime は、これらの共通エンジニアリング機能をプラットフォーム層に統合します。

| 比較項目 | 以前（自前構築） | 以降（プラットフォーム提供） |
| --- | --- | --- |
| 会話状態 | 開発者が個別に永続化ロジックを実装 | プラットフォームによる自動的な永続化 |
| ツール管理 | ハードコードによる呼び出しロジック | 標準化された登録と自動発見メカニズム |
| 監査・追跡 | ログが分散し、追跡が困難 | 統一された実行トレーシング |
| デプロイ | 環境ごとに手動設定が必要 | 宣言的なワンクリック・デプロイ |

## 注視すべき論点

- **エコシステムの互換性**：ツール登録形式が MCP（Model Context Protocol）とどの程度の互換性を持つか。非互換の場合、エコシステムの分断を招くリスクがあります。
- **状態管理の粒度**：提供される状態管理メカニズムが、高度に複雑な Agent の要件を充足できるか。単純な Key-Value ストアでは多層的なタスクへの対応が難しい可能性があります。
- **パフォーマンスとコストのバランス**：クラウド実行に伴うレイテンシとコストの増加が、リアルタイム性が要求される産業用途や対話シーンで許容されるか。
- **モデルのオープン性**：現在は Azure OpenAI Service との親和性が高いですが、将来的にサードパーティ製やオープンソースモデルもサポートされるか。
