**Claude Code** は、コードベースの読み取り、編集、テストの実行、コマンド操作をシームレスに行う CLI 型の AI コーディング環境です。その真価は単に「コードを生成させる」ことだけでなく、既存のコンテキストを深く理解させ、複雑な変更を小さなステップに分解し、人間と協力して検証を進めるワークフローにあります。

## このノートのポイント

- **明確な指示出し**：Claude Code には、目的、制約、変更の許容範囲、および検証用のコマンドを具体的に提示します。
- **タスクの段階的分解**：大規模なタスクは、探索（Exploration）、設計（Design）、実装（Implementation）、検証（Verification）のフェーズに分けて進行します。
- **ヒューマン・イン・ザ・ループ**：AI が生成した差分は必ず人間がレビューし、テスト結果に基づいて最終的な採用を判断します。
- **セキュリティとガバナンス**：権限、秘匿情報（Secrets）、および破壊的コマンドの実行に関するルールを事前に定義します。

## Claude Code が真価を発揮するシナリオ

Claude Code は、以下のような「文脈理解」を必要とするタスクにおいて強力な支援を提供します。

- **コード探索**：既存のコードベースから関連するロジックや依存関係を特定する。
- **デバッグ**：テストの失敗ログを解析し、根本原因を突き止めて修正案を出す。
- **リファクタリング**：既存のパターンを維持しつつ、コードの構造を改善する。
- **ドキュメント更新**：コードの変更に合わせて README や API 仕様書を同期させる。

一方、設計意図が不明確なまま大規模なアーキテクチャ変更を任せると、予期しない抽象化が導入されるリスクがあるため、変更範囲（バウンダリ）を絞ることが重要です。

## 効率的なタスク設計

AI への依頼を成功させるためには、以下の情報を意識的に含めます。

1. **期待する最終状態**：ユーザーから見てどのような変化が起きるべきか。
2. **スコープの限定**：編集してよいディレクトリや、逆に「触ってはいけない」ファイル。
3. **既存パターンの遵守**：プロジェクト特有の命名規則や実装スタイル。
4. **検証手順**：修正が正しいことを確認するためのテストコマンド（`npm test` 等）。

タスクが大きい場合は、「まず関連するファイルを調査して方針を提案して」と依頼し、人間の合意を得てから実装に進むステップを踏むことで、手戻りを最小限に抑えられます。

## 安全な運用とレビューの原則

- **秘匿情報の保護**：API キーやトークン、`.env` ファイルの内容がプロンプトやコミットに含まれないよう厳重に管理します。
- **破壊的コマンドの制御**：ファイル削除やデータベースのマイグレーションなど、影響の大きい操作は必ず手動で承認（Approval）する設定にします。
- **厳格な差分レビュー**：`git diff` を活用し、意図しないコードの混入や、テストが「不適切なパス」をしていないかを確認します。

## 読者向け補足：タスクの「境界線」を明確にする

Claude Code への依頼を最適化するコツは、境界を明確にすることです。「このリポジトリを全体的に良くして」といった抽象的な依頼ではなく、「このテスト失敗の原因を特定し、最小限の修正を行い、型チェックをパスさせる」といった具体的なゴールを設定します。

Claude Code の強みは、編集能力そのものよりも、**調査 → 計画 → 実行 → 検証のサイクルを一貫したコンテキストで回せる点**にあります。人間は「監督者」として途中で介入し、設計の方向性を修正したり、過剰な変更を差し止めたりする役割を担います。

| 提示すべき情報 | 役割 |
| --- | --- |
| **期待する挙動** | 修正が完了したと判断するための客観的な基準 |
| **再現手順** | AI が現状の不具合を自律的に確認するための手がかり |
| **変更の制約** | 既存のアーキテクチャや依存関係を破壊させないためのガードレール |
| **完了条件** | 成功とみなすためにパスすべき具体的なテストやコマンド |

### ミニ演習

現在抱えている小さなバグを一つ選び、Claude Code に渡すための依頼文を作成してみましょう。その際、以下の 3 点を明示してください。
1. 修正の目的
2. 参照すべきファイル
3. レビュー時に特に注意してチェックするポイント

## 実務ワークフローの提案

1. **現状確認**：タスク開始前に `git status` で作業ディレクトリをクリーンにし、前提条件を整理する。
2. **調査と提案**：まずは `Read` や `Grep` ツールを使ってコードを探索させ、実装方針を簡潔にまとめさせる。
3. **段階的実装**：合意した方針に基づき、小さな単位でファイルを編集・保存させる。
4. **統合検証**：最後に静的解析（Linter/Typecheck）とテストを走らせ、変更がプロジェクト全体と整合しているかを確認する。
