Claude Code は、コードベースを読み、編集し、テストを実行しながら開発を進める CLI 型の AI コーディング環境です。便利さの中心は「コードを書かせる」ことより、既存の文脈を読ませ、変更を小さく切り、検証まで一緒に進めることにあります。

## このノートで押さえること

- Claude Code には、目的、制約、変更してよい範囲、検証コマンドを明確に渡す。
- 大きなタスクは探索、設計、実装、テスト、レビューに分けると失敗しにくい。
- AI が編集した差分は必ず人間がレビューし、テスト結果と照らして判断する。
- 権限、秘密情報、破壊的コマンドの扱いをルール化しておく。

## Claude Code が得意な仕事

既存コードの探索、関連ファイルの特定、テスト失敗の原因調査、小さなバグ修正、リファクタリング候補の整理に向いています。

一方で、曖昧なまま大規模変更を任せると、設計意図を外したり、不要な抽象化を増やしたりします。最初に変更範囲を絞ることが重要です。

Claude Code には、コードだけでなく README、テスト、設定、過去のエラーを読ませると判断が安定します。

## 良い依頼の切り方

依頼文には「達成したいユーザー-visible な結果」「触ってよいファイル」「触らないファイル」「既存パターン」「検証コマンド」を入れます。

大きい機能は、まず探索だけ、次に実装、最後にテスト修正のように分けます。探索結果を読んでから実装に進むと、AI が見当違いの変更をしにくくなります。

差分が出たら、`git diff` を読み、想定外のファイルが入っていないか、テストが意味ある失敗をしていないかを確認します。

## 安全な運用ルール

秘密情報をプロンプトに貼らない、`.env` や token をコミットしない、破壊的コマンドは承認制にする、生成されたコードを必ずレビューする。この四つは最低限のルールです。

また、AI が修正したファイルにユーザーの未コミット変更がある場合は、勝手に戻さないようにします。既存の作業と自分の変更を分けて扱うことが大切です。

## 読者向け補足：良いタスク境界を渡す

Claude Code に向いた依頼は、「この巨大なコードベースを良くして」ではなく、「この failing test を読み、原因を説明し、最小修正を入れ、関連テストを走らせる」のように境界が見える依頼です。作業範囲、触ってよいファイル、避けたい変更を明示すると、レビューしやすくなります。

また、Claude Code の強みは編集だけではありません。調査、計画、diff の説明、テスト実行、失敗ログの読み直しを同じ会話でつなげられることです。人間は途中で判断を挟み、不要なリファクタや大きすぎる変更を止めます。

| 渡す情報 | 理由 |
| --- | --- |
| 期待する挙動 | 何を直すかの基準になる |
| 再現手順 | 失敗を確認できる |
| 触ってよい範囲 | 余計な変更を防ぐ |
| 検証コマンド | 完了条件を共有できる |

### ミニ演習

小さな bug fix を一つ選び、Claude Code に渡す依頼文を書きます。最後に「変更してほしくないこと」を 3 つ足し、レビュー時に見る diff の観点も列挙します。

## 実務で試すワークフロー

1. タスク開始時に `git status` を見て、作業範囲と既存変更を確認する。
2. まず関連ファイルを読ませ、実装方針を短く出してから編集に入る。
3. 最後に unit / typecheck / UI test など、変更に見合う検証を走らせる。

## Prompt pack

- このリポジトリで次のバグを直したいです。まず関連ファイルと既存パターンを調査し、編集前に方針を短くまとめてください。
- この差分をコードレビューしてください。バグ、回帰リスク、足りないテストを優先して指摘してください。
- この機能を安全に小さなコミットへ分割するなら、どの順序がよいか提案してください。

## 自分で確認する

- AI に任せる変更範囲を明示できる。
- 生成差分を自分でレビューしてからコミットしている。
- 検証コマンドと結果を説明できる。
