Claude API を活用した開発において、単に SDK でメッセージを送信するだけでは不十分です。モデルの適切な選択から、プロンプト設計、構造化出力、ストリーミング、エラーハンドリング、評価、そしてコスト管理に至るまで、「プロダクション品質の呼び出し」を包括的に設計する必要があります。

## このノートのポイント

- **リクエスト設計の多角化**：API リクエストを、ユーザー入力、システム指示（System Prompt）、ツール定義、モデルパラメータ、および出力制約の組み合わせとして最適化します。
- **レジリエンスの確保**：成功時のレスポンス処理だけでなく、タイムアウト、レート制限（Rate Limit）、再試行ロジック、監査ログなどの例外処理を徹底します。
- **目的別モデル選定**：品質、速度、コスト、コンテキスト長、ツール利用の適正といった多面的な観点から最適なモデルを選択します。
- **構造化出力と評価（Eval）**：LLM の出力を JSON などの構造化データとして扱い、評価サイクルを回すことで、アプリケーションのコンポーネントとしての信頼性を高めます。

## API リクエストの基本設計

Claude API の中核は **Messages API** です。リクエスト時には、ユーザー入力に加えて以下の要素を適切に組み合わせます。

1. **System Instruction**：モデルの役割、制約、振る舞いを定義します。
2. **Conversation History**：過去のやり取りをコンテキストとして含めます。
3. **Tool Definition**：モデルが利用可能な外部関数を定義します。
4. **Output Constraints**：最大トークン数や停止シーケンスを指定します。

実務においては、ユーザー入力をそのまま渡すのではなく、アプリケーション側で「目的」「利用可能なコンテキスト」「禁止事項」「期待するフォーマット」を補完してリクエストを組み立てることで、入力の揺れに対する堅牢性を向上させます。

## プロダクション環境に求められる周辺設計

LLM 呼び出しは外部サービスへの依存であるため、**「失敗を前提とした設計」**が不可欠です。

- **エラーハンドリング**：ネットワークエラー、API のレート制限、コンテンツフィルタリングによる拒否、予期しない形式の出力などを適切にキャッチし、ユーザー体験を損なわない形で処理します。
- **可観測性（Observability）**：リクエスト ID、モデル名、レイテンシ、使用トークン量、エラー種別、そして独自の評価結果をログに記録します。※プロンプトに含まれる機密情報の扱いやプライバシーには十分注意してください。
- **ストリーミングの考慮**：UX 向上のためのストリーミングと、機械処理のための構造化出力は、要件に応じて使い分けます。ストリーミング中の切断や不完全なデータのハンドリングも重要です。

## モデル選択と継続的な評価

「常に最上位モデルを使う」ことが正解とは限りません。タスクの性質（分類、要約、複雑な推論、コード生成など）に応じて、求められる品質と許容できるコスト・速度のバランスは異なります。

1. **評価セット（Eval Set）の作成**：代表的な入力パターンを集め、期待される出力を定義したテストケースを作成します。
2. **モデル比較**：コストだけでなく、失敗パターンの違い（ハルシネーションの傾向など）を比較します。
3. **ハイブリッド戦略**：高速で安価なモデルで処理可能な箇所と、高度な推論を必要とする箇所を切り分けることで、全体のコスト効率を最大化します。

## 読者向け補足：API 呼び出しを「製品機能」として捉える

Claude API の実装は簡単ですが、それを「製品」として成立させるには、入力バリデーション、タイムアウト設定、リトライ戦略、レート制限管理、詳細なロギング、継続的評価、そしてエラー時のフォールバック表示までを含めたライフサイクル設計が必要です。

特に後続のシステムにデータを渡す場合は、自由記述形式よりも **JSON Schema** による構造化を優先してください。必須フィールドの定義や列挙値（Enum）の活用により、機械的な処理の確実性を高めることができます。

| 設計レイヤー | 主要な検討項目 |
| --- | --- |
| **Request** | システム指示、ユーザー文脈の補完、モデル選択 |
| **Runtime** | タイムアウト、リトライ、レート制限管理、コスト集計 |
| **Output** | スキーマ検証、引用の有無、禁止表現チェック、フォールバック |
| **Eval** | ゴールデンケース（正解集）、失敗の分類、デグレード確認 |

### ミニ演習

既存のアプリケーションに「ドキュメント要約機能」を追加する想定で、成功の定義、想定される失敗パターン、記録すべきログ項目、およびエラー時にユーザーに提示するフォールバックメッセージを設計してみましょう。

## 実務ワークフローの提案

1. **テストデータの準備**：実装前に 20 件程度の代表的な入力ケースを用意し、期待される結果と失敗条件を定義する。
2. **Wrapper クラスの実装**：API 呼び出しを抽象化し、モデル名、レイテンシ、トークン消費、エラーログを統一的に管理できるようにする。
3. **スキーマの先行定義**：構造化出力が必要な場合は、プロンプトを書く前に JSON Schema とバリデーション失敗時のリトライルールを決定する。

## Prompt pack

- 「この LLM API 呼び出しをプロダクション環境へデプロイする前に検討すべきエラー処理、ロギング、評価観点のチェックリストを作成してください。」
- 「以下のタスクを分解し、安価なモデルで十分なフェーズと、高性能モデルが必要なフェーズを特定してください。」
- 「このプロンプトの出力を指定の JSON Schema に確実に適合させるための制約事項と、バリデーション失敗時のリトライ方針を提案してください。」
