Subagents は、ひとつの大きな AI に全部を任せるのではなく、調査、実装、レビュー、検証などの役割を分けて進める考え方です。人間のチームと同じように、分担は便利ですが、統合と責任の設計が必要です。

## このノートで押さえること

- Subagent は、特定の役割や観点に集中する AI 作業単位である。
- 役割分担により文脈を整理できるが、情報の断片化や重複作業に注意する。
- 親エージェントまたは人間が、最終統合と判断責任を持つ必要がある。
- 小さく明確なタスク、独立した調査、レビュー観点の分離に向いている。

## Subagents が役立つ場面

大きなタスクでは、調査、設計、実装、テスト、レビューが混ざりがちです。Subagent を使うと、それぞれの観点に集中できます。

たとえばコード変更では、ひとつの agent が実装し、別の agent がテスト観点を確認し、さらに別の agent がドキュメント影響を調べる、といった分担ができます。

ただし、分ければ必ず良くなるわけではありません。タスクが小さい場合や、情報共有が難しい場合は、単一の流れで進めた方が速いこともあります。

## 設計のコツ

Subagent には、目的、入力、出力、触ってよい範囲、期待する粒度を明確に渡します。曖昧な依頼を複数に投げると、曖昧な結果が複数返ってくるだけです。

書き込みを伴う作業では、担当ファイルや責任範囲を分けます。同じファイルを複数 agent が編集すると、統合コストが高くなります。

最終判断は、親 agent か人間が行います。Subagent の出力は材料であって、統合された結論ではありません。

## 失敗パターン

よくある失敗は、同じ調査を複数 agent が重複して行うこと、互いの前提が違うこと、統合時に矛盾が見つかることです。

もう一つの失敗は、責任が分散して最終品質を見る人がいなくなることです。Subagents を使うほど、統合レビューの重要性は上がります。

## 読者向け補足：Subagent は分業の単位を間違えない

Subagent は、作業をたくさん並べれば賢くなる仕組みではありません。うまく動くのは、入力、担当範囲、成果物、判断基準が分かれており、最後に統合する主体がはっきりしている場合です。

失敗しやすいのは、全員に同じ大きな依頼を投げることです。探索、実装、検証、要約のように役割を分け、互いの成果物が衝突しないようにします。コード編集なら、担当ファイルやモジュールの境界も先に決めます。

| 役割 | 向いている仕事 |
| --- | --- |
| Explorer | コードベース調査、選択肢整理、リスク確認 |
| Worker | 明確な範囲の実装、テスト追加、文書更新 |
| Reviewer | 差分確認、失敗ケース、抜け漏れ指摘 |
| Integrator | 結果の統合、最終判断、リリース準備 |

### ミニ演習

「大きな機能追加」を一つ想定し、subagent に渡せる仕事と自分が持つべき統合作業を分けます。すぐに統合判断が必要な作業は、subagent に丸投げしないようにします。

## 実務で試すワークフロー

1. タスクを、独立して進められる調査・実装・検証に分ける。
2. 各 Subagent に期待出力を明確に指定する。
3. 最後に統合担当が矛盾、重複、未解決点をレビューする。

## Prompt pack

- このタスクを Subagents に分担するなら、役割、入力、出力、担当範囲をどう切るべきか提案してください。
- 次の複数 agent の報告を統合し、矛盾点、重複、まだ判断できない点を整理してください。
- この作業は Subagents に分けるべきか、単一 agent で進めるべきか、判断基準を示してください。

## 自分で確認する

- Subagent ごとの責任範囲が重なりすぎていない。
- 最終統合の担当が明確である。
- 出力形式が揃っていて比較しやすい。
