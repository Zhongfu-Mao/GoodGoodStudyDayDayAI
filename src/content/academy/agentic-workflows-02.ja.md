# Agentic Workflows：行動する AI を制御可能なシステムにする

![Agentic Workflow の状態機械の概念図](/images/academy/agentic-workflows-02/agentic-state-machine-cover.png)

Agentic Workflow を作り始めると、多くの人は自然にこう考えます。目標をモデルに渡し、モデル自身に計画させ、ツールを呼ばせ、結果を確認させればよい。魅力的な考え方ですが、そのまま実務に入れると三つの問題が出やすくなります。

第一に、過程が見えません。モデルは忙しそうに動いていますが、何を終えたのか、どこで詰まったのか、なぜ方針を変えたのか分かりません。

第二に、失敗から戻れません。あるツール呼び出しが失敗したとき、全体を最初からやり直すか、壊れた状態を抱えたまま進むことになります。

第三に、境界を制御できません。確認なしにメールを送る、データベースを変更する、コードをコミットする、予算を使い続ける、無限に再試行する、といったリスクがあります。

Agentic Workflow の核心は「モデルをもっと自由にする」ことではありません。**モデルが行動できる軌道を設計すること**です。状態機械、タスク分解、依存関係、チェックポイント、コンテキスト管理は、AI の行動を観測可能、復旧可能、監査可能にするためのものです。

## 最小ループ：Plan、Act、Review

最小の Agentic Workflow は三つの状態から始められます。

```ts
type AgentStep = 'plan' | 'act' | 'review';
```

単純な言葉ですが、重要な役割分担があります。

| 状態 | 入力 | 出力 | 典型的な失敗 |
| --- | --- | --- | --- |
| `plan` | ユーザー目標、環境状態、制約 | 実行手順、リスク、検証方法 | 計画が広すぎる、制約漏れ、検証不能 |
| `act` | 現在の手順、ツール権限、文脈 | ツール結果または成果物 | ツール失敗、引数ミス、権限不足 |
| `review` | 計画、実行結果、受け入れ基準 | 合格、再試行、計画修正、人間へのエスカレーション | 自己評価が甘い、証拠を無視、無限リトライ |

この最小ループの価値は、「回答を生成する」を「計画、実行、検査」に分けることです。ここまで分けて初めて、ログ、再試行、コスト制御、人間の承認を設計できます。

## 状態機械は形式主義ではない

![Plan、Act、Review とリトライチェックポイント](/images/academy/agentic-workflows-02/plan-act-review-loop.png)

状態機械の価値は、各ステップに入口、出口、遷移条件を持たせることです。

本番に近い状態機械は、次のようになります。

| 状態 | 責任 | 遷移条件 |
| --- | --- | --- |
| `init` | 目標、権限、環境、利用可能ツールを解析 | 目標が十分に明確なら `plan` へ |
| `plan` | タスク分解、依存関係、リスク、検証を定義 | 実行可能なら `act` へ |
| `act` | 現在のタスクまたはツール呼び出しを実行 | 実行完了後 `review` へ |
| `review` | 受け入れ基準に照らして結果を確認 | 合格なら次へ、失敗なら `retry` へ |
| `retry` | 局所修正、引数調整、文脈補強 | 上限未満なら `act`、上限超過なら `escalate` |
| `escalate` | 人間の判断や権限確認を要求 | 承認後に継続、拒否なら停止 |
| `done` | 証拠をまとめ、結果を保存する | 終了状態 |

複雑に見せるためではありません。次の三つを解決するためです。

- システムが今どこにいるか分かる。
- 失敗した局所ステップだけを再試行できる。
- 高リスク遷移の前に制御点を入れられる。

状態機械のない Agent でも demo ではうまく動くことがあります。しかしタスクが長くなり、ツールが増え、文脈が複雑になるほど、予測不能なブラックボックスに近づきます。

## タスク分解：各ノードは検証できるべき

「このプロジェクトを改善して」は良いタスクノードではありません。大きすぎ、曖昧すぎ、受け入れ基準がありません。

より良い分け方は次の通りです。

1. ビルドとテストの入口を調べ、検証コマンドを出す。
2. 現在失敗しているチェック項目とエラー原文を記録する。
3. 一種類の失敗だけを修正する。
4. 対応する検証を再実行する。
5. 変更、残リスク、未検証部分をまとめる。

良いタスクノードには四つの条件があります。

| 条件 | 問い | 良い例 |
| --- | --- | --- |
| 検証可能 | 完了をどう判断するか | `npm run check` が通る |
| 復旧可能 | 失敗後どこから再開できるか | 失敗したファイル生成だけを再試行する |
| 記録可能 | 過程を証拠として残せるか | 入力、出力、エラー、時間を保存する |
| 受け渡し可能 | 次のノードに何を渡すか | 構造化 JSON または明確なファイルパス |

大事なのは、モデルに「完了したように見える」を完了扱いさせないことです。完了には外部証拠が必要です。

## コンテキスト管理：すべての履歴を渡さない

Agentic Workflow はコンテキスト汚染を起こしやすいです。履歴が多すぎると、現在の目標、古いエラー、破棄された計画、最新のユーザー意図が混ざります。

より安定するのは、状態ごとに必要な文脈だけを渡す方法です。

| 状態 | 渡すべきもの | 渡すべきでないもの |
| --- | --- | --- |
| `plan` | ユーザー目標、制約、利用可能ツール、環境要約 | 大量の古いログ、無関係な全文 |
| `act` | 現在の手順、必要入力、ツール権限、受け入れ基準 | 計画外の大きな未解決タスク |
| `review` | 受け入れ基準、実際の出力、証拠 | モデルの長い自己弁護 |
| `retry` | 失敗理由、前回引数、調整可能範囲 | 失敗と無関係な会話履歴 |
| `done` | 最終成果物、検証結果、残リスク | 中間草稿や無効な試行 |

コンテキストは多ければよいわけではありません。関数の引数のように、境界、型、ライフサイクルを持つべきです。

## 人間のチェックポイントは安全機構

![人間のチェックポイントと高リスク操作の制御面](/images/academy/agentic-workflows-02/human-checkpoint-control-plane.png)

Agentic Workflow は「人に聞かないこと」を目標にすべきではありません。実際のシステムでは、人間のチェックポイントは安全機構であり、プロダクト体験の一部でもあります。

人間確認を入れるべき場面です。

- 外部に見える操作：メール送信、投稿、コメント、公開。
- 不可逆操作：削除、上書き、キューの消去、デプロイ取り消し。
- コスト操作：長時間タスク、大量 API 呼び出し、メディア大量生成。
- 権限昇格：新しいデータソース、機密ファイル、本番環境。
- 低信頼判断：連続失敗、証拠の衝突。

チェックポイントは Agent を止めるためではなく、受け入れられないリスクを実行前に止めるためのものです。良いシステムは、本当に重要な確認だけをユーザーに求めます。

## ミドルウェア：横断的な能力を状態の外側に置く

ログ、トレース、権限、予算、レート制限、脱識別、リトライ戦略を各状態の中に散らすべきではありません。状態実行を包むミドルウェアに置くほうが安定します。

簡略化すると次のようになります。

```ts
type WorkflowMiddleware = (
  context: WorkflowContext,
  next: () => Promise<WorkflowResult>,
) => Promise<WorkflowResult>;
```

ミドルウェアは次のようなことを担当できます。

- 状態に入る前に入力要約を記録する。
- ツール権限と予算を確認する。
- ツール呼び出しに trace id を付ける。
- エラーを構造化された失敗へ変換する。
- 出力に機密情報がないか確認する。
- 状態遷移を監査ログへ書き込む。

Web バックエンドのミドルウェアと同じです。すべてのリクエストが通る統制ロジックを、業務関数に散らさず、共通の通路に置きます。

## 依存チェーン：LangChain の Chain と FastAPI の依存性注入

Agentic Workflow では「このステップは前の結果を必要とする」という問題がよく出ます。ここで二つの類推が役立ちます。

LangChain の Chain は、複数の処理を A、B、C とつなぐ考え方です。FastAPI の依存性注入は、現在のルートに必要なユーザー、DB session、設定を明示的に宣言する考え方です。

Agentic Workflow でも依存関係を明示します。

```ts
type StepSpec = {
  id: string;
  dependsOn: string[];
  inputSchema: unknown;
  outputSchema: unknown;
  verify: string;
};
```

これにより、二つの失敗を避けられます。

- 上流結果がないのに下流ステップを実行する。
- あるステップの出力形式が変わっても、下流が古い構造として読んでしまう。

依存関係が明示されると、並列実行できるもの、直列にすべきもの、失敗時に局所影響で済むものを判断できます。

## ケース：ドキュメントサイト改修 Agent

多言語コンテンツサイトを保守する Agent を考えます。目標は単に「記事を書く」ことではなく、古い記事を公開可能な品質へ改修することです。

制御可能なワークフローは次のように設計できます。

1. `inspect`
   - 中国語、日本語ファイル、frontmatter、画像参照、内部リンクを読む。
   - 不足部分を洗い出す：分量、画像、日本語同期、古い用語、リンク切れ。
2. `plan`
   - 改修計画を作る。
   - 必要な画像、確認すべき公式資料、保持すべき slug を示す。
3. `draft`
   - セクション単位で本文を改稿する。
   - 中国語と日本語の構造をそろえる。
4. `asset`
   - 文字なし画像を生成または接続する。
   - 画像パス、サイズ、SVG 参照の有無を確認する。
5. `review`
   - 内部向けに書かれた形跡、未確認の断定、構造の不一致を確認する。
6. `verify`
   - 内容 QA、ビルド、ページプレビューを実行する。
7. `done`
   - 変更、検証結果、残リスクを出す。

この Agent に必要なのは完全な自律性ではありません。必要なのは、追跡可能な状態と明確な検証証拠です。

## よくあるアンチパターン

**アンチパターン 1：巨大な Prompt 一つで済ませる。**

規則、ツール、目標、形式を一つに詰め込むと、復旧が難しくなります。失敗時に計画、ツール引数、最終回答のどこを直すべきか分かりません。

**アンチパターン 2：完了判定をモデルだけに任せる。**

自己評価は有用ですが、外部検証の代わりにはなりません。コードはテストを走らせ、内容はビルドを通し、操作はログを残します。

**アンチパターン 3：失敗したら最初からやり直す。**

長いタスクで全体再起動は危険です。状態を保存し、失敗したノードだけを再試行します。

**アンチパターン 4：人間確認を結果の後に置く。**

高リスク操作は実行前に確認すべきです。実行後の review では遅すぎます。

**アンチパターン 5：停止条件がない。**

Agent には最大リトライ回数、予算上限、時間上限、エスカレーション経路が必要です。停止条件のない自動化は、やがて運用コストになります。

```md
### Workflow Goal

このワークフローが完了すること：

責任を持たないこと：

### States

| State | Input | Output | Verification | Next |
| --- | --- | --- | --- | --- |
| init | | | | |
| plan | | | | |
| act | | | | |
| review | | | | |
| retry | | | | |
| escalate | | | | |
| done | | | | |

### Tools

| Tool | Permission | Risk | Logging |
| --- | --- | --- | --- |
| | read/write/external | low/medium/high | yes/no |

### Checkpoints

- 人間確認が必要な操作：
- コスト確認が必要な操作：
- 権限確認が必要な操作：

### Failure Policy

- 単一ノードの最大リトライ回数：
- 総予算上限：
- 人間へエスカレーションする条件：
- 直接停止する条件：

### Observability

- 状態遷移ごとに記録するもの：
- ツール呼び出しごとに記録するもの：
- 最終提出に添える証拠：
```

> **記入例（Customer ticket triage workflow）**
>
> このワークフローが完了すること：新規 ticket を分類し、context を補い、返信 draft を提案します
> 責任を持たないこと：自動返金、account 状態変更、返信の直接送信はしません
> States：init=ticket を読みます；plan=必要な証拠を決めます；act=order/profile/policy tools を呼びます；review=分類と証拠を検証します；retry=不足 field を再取得します；escalate=高 risk を人間へ渡します；done=triage card を出します
> Tools：ticket_read=read/low/log yes；order_lookup=read/medium/log yes；refund_action=禁止します；draft_reply=write/low/log yes
> Checkpoints：人間確認が必要な操作=返金、account 停止、compliance complaint；コスト確認が必要な操作=上位 model review；権限確認が必要な操作=workspace 横断検索です
> Failure Policy：単一ノードの最大リトライ回数=2；総予算上限=90 秒または 0.20 USD；人間へエスカレーションする条件=証拠矛盾または VIP user；直接停止する条件=権限不足です
> Observability：状態遷移ごとに ticket_id/state/reason を記録します；ツール呼び出しごとに tool/input_hash/result_status を記録します；最終提出に分類、証拠リンク、返信案、confidence を添えます

## チェックリスト

- 各状態に明確な入力と出力があるか？
- 各状態遷移に記録可能な条件があるか？
- 各タスクノードは独立して検証できるか？
- ツール呼び出しに権限、予算、ログがあるか？
- 高リスク操作は実行前に人間確認を入れているか？
- 失敗時に全体再起動ではなく局所リトライできるか？
- 最終結果はモデルの説明だけでなく検証証拠を含むか？
