## なぜ状態マシンが必要か

AI エージェントに複数ステップのタスクを任せる際、明確なプロセス・フレームワークがなければ、途中でタスクが脱線したり、同じ操作を繰り返したり、完了済みのステップを忘れてしまうといった問題が起きやすくなります。

**状態マシン（State Machine）**の考え方を導入することで、タスクを離散的なフェーズに分割し、各フェーズにおける入力・出力・遷移条件を明文化できます。

最小構成の状態マシンは、以下の 3 つの状態から成り立ちます。

```ts
const steps = ['plan', 'act', 'review'];
```

- **Plan（計画）**：タスクの目標と現在の環境情報を読み取り、具体的な実行計画を出力する。
- **Act（実行）**：計画に沿ってツールを呼び出す、あるいはコンテンツを生成する。
- **Review（評価）**：実行結果が目標に合致しているかを確認し、「完了」「継続」「ロールバック（やり直し）」を判断する。

## 実践的なシステムへの拡張

実用レベルの Agentic Workflow では、より詳細な状態管理が求められます。

| 状態 | 役割 | 遷移条件 |
| --- | --- | --- |
| `init` | リクエストの解析、タスクスコープの確定 | スコープ確定 → `plan` へ |
| `plan` | 詳細な実行ステップ（ToDo リスト）の生成 | 計画完了 → `act` へ |
| `act` | 現在のサブタスクを実行 | ステップ完了 → `review` へ |
| `review` | 実行結果の品質確認 | パス → 次の `act` へ / 失敗 → `retry` へ / 全完了 → `done` へ |
| `retry` | 方針の修正と再試行の準備 | 修正完了 → `review` へ / 試行上限超え → `escalate` へ |
| `escalate` | 人間による介入・レビューへ転送 | 人間が承認 → `act` または `done` へ |
| `done` | 最終結果の出力と納品 | 終了状態 |

**運用の鉄則**：すべての状態遷移はログに記録されるべきです。ログのない遷移は、原因究明のできない「ブラックボックス」となってしまいます。

## タスク分割の 4 つの原則

大きなタスクをサブタスクに分解する際は、以下の原則を意識してください。

1. **独立した検証基準**：「コードをきれいに書く」といった曖昧な目標ではなく、「特定の 3 つのテストをパスする」といった客観的な検証基準を持たせます。
2. **依存関係の明示**：どのタスクを並列化でき、どのタスクが他の完了を待つ必要があるか（直列）を整理します。
3. **構造化データによる受け渡し**：サブタスクの出力は、次のタスクの入力となります。自然言語による要約ではなく、JSON などの構造化形式を用いることで、情報の欠落を防ぎます。
4. **局所的なリトライ**：特定のサブタスクが失敗した場合、ワークフロー全体をやり直すのではなく、そのステップだけを独立してリトライできるように設計します。

## 人間によるチェックポイント（Human-in-the-loop）

エージェントを完全に放置（自律動作）させるのではなく、クリティカルな局面では人間の確認を挟む設計が重要です。

- **外部への影響が及ぶ前**：メール送信、コードのコミット、データベースの更新など。
- **コストの閾値を超えた時**：消費トークンや API コストが予算を超えそうな場合。
- **ループの停滞**：エージェントが同じエラーで 2 〜 3 回以上リトライを繰り返している場合。
- **不可逆な操作**：データの削除や金銭の発生を伴う操作。

チェックポイントを設けることは「AI を疑うこと」ではなく、**「エンジニアリングとしての適切なリスク管理」**です。熟練のエンジニアであってもコードレビューが必要なのと同様に、エージェントにもレビューは不可欠です。

## 実験してみよう

1. **ワークフローの再現**：ChatGPT や Claude に対し、「まず計画を立て、次に実行し、最後に自分でチェックして結果を報告して」という 3 ステップを明示して依頼してみてください。
2. **レビューのテスト**：計画段階でわざと曖昧な指示を混ぜてみて、エージェントが Review 段階でその不備を指摘できるか観察してください。
3. **動的な修正**：Review 段階で「もし不備があれば計画を修正して再実行して」という指示を加え、自己修正能力を確認してください。
