## 为什么需要状态机？

当你让 AI Agent 处理一个多步骤任务时，如果没有明确的流程框架，模型很容易在执行中途偏离方向、产生重复操作，甚至遗忘已完成的进度。

**状态机（State Machine）**的思想是将任务拆分为离散的阶段，每个阶段都有明确的输入要求、输出结果和转换条件。

最小化的 Agent 状态机通常包含三个核心状态：

```ts
const steps = ['plan', 'act', 'review'];
```

- **Plan（规划）**：模型读取原始任务目标和当前环境信息，输出具体的执行计划。
- **Act（执行）**：模型根据计划调用工具或生成特定的内容。
- **Review（评审）**：检查执行输出是否符合目标，并据此决定是“完成任务”、“继续迭代”还是“回退重试”。

## 从理论原型到工程实践

一个生产级别的 Agentic Workflow 通常需要更细腻的状态划分：

| 状态 | 核心职责 | 触发转换（Transition）的条件 |
| --- | --- | --- |
| `init` | 解析用户请求，界定任务边界 | 范围确认后 → 进入 `plan` |
| `plan` | 生成详细的执行步骤清单 | 计划就绪后 → 进入 `act` |
| `act` | 执行当前的子任务步骤 | 步骤完成后 → 进入 `review` |
| `review` | 验证执行结果的质量 | 通过验证 → 进入下一轮 `act` 或 `done`；失败 → 进入 `retry` |
| `retry` | 调整策略，修复错误并重试 | 修复成功 → 返回 `review`；重试超限 → 进入 `escalate` |
| `escalate` | 触发人工介入审核 | 人工审批通过 → 进入 `act` 或 `done` |
| `done` | 整合并交付最终成果 | 到达终态 |

**工程准则**：每一个状态的转换都必须记录详细的日志。没有日志记录的状态转换等同于无法审计的“黑盒”。

## 任务拆分的核心原则

在将大任务解构为子任务时，应遵循以下实用原则：

1. **可验证性**：每个子任务必须有独立的、客观的验证标准。相比“写好代码”，更有效的标准是“代码必须通过这三个特定的 Unit Test”。
2. **依赖明晰**：理清子任务间的先后顺序。哪些步骤可以并行执行以提升效率？哪些步骤必须串行以保证逻辑正确？
3. **结构化传递**：子任务的输出应作为下一个子任务的输入，建议使用 JSON 等结构化格式，避免自然语言复述导致的信息熵增和关键信息丢失。
4. **局部重试**：当某个子任务失败时，系统应支持仅对该节点进行独立重试，而非重启整个庞大的工作流。

## 人工检查点（Human-in-the-loop）

不要追求 Agent 的绝对自治，在关键的业务节点设置“检查点”是保障系统安全的关键：

- **高风险操作前**：如发送外部邮件、提交核心代码、修改生产数据库前。
- **成本预警**：当任务消耗的 Token 或 API 调用成本超过预设阈值时。
- **陷入僵局**：当 Agent 连续重试次数超过预设限制（通常为 2-3 次）时。
- **不可逆操作**：涉及删除数据或真实的资金交易时。

检查点并非对 AI 的不信任，而是必要的工程风控手段。正如资深开发者也需要 Code Review 一样，Agent 的行为同样需要监督。

## 动手试试：模拟实验

1. **工作流模拟**：尝试在 ChatGPT 或 Claude 中手动引导一个三步工作流：要求它先写出计划、再分步执行、最后根据你的要求进行自查。
2. **压力测试**：故意在计划阶段植入一个模糊的步骤，观察 Agent 在 Review 阶段是否具备识别并质疑该步骤的能力。
3. **反馈闭环**：在 Review 阶段加入指令：“如果结果不达标，请动态修改后续计划并重新执行”，观察 Agent 的自我修正行为。
