# Agentic Workflows：把“会做事的 AI”变成可控系统

![Agentic Workflow 的状态机概念图](/images/academy/agentic-workflows-02/agentic-state-machine-cover.png)

很多人第一次做 Agentic Workflow，会从一个很自然的想法开始：把目标交给模型，让它自己规划、自己调用工具、自己检查结果。这个想法很有吸引力，但直接放进真实工程里，通常会遇到三类问题。

第一，过程不可观察。模型看起来一直在忙，但你不知道它完成了什么、卡在哪里、为什么换了方向。

第二，失败不可恢复。某一步工具调用失败后，系统要么从头再来，要么继续带着错误状态前进。

第三，边界不可控制。模型可能在没有确认的情况下发邮件、改数据库、提交代码、花掉预算，或者进入无限重试。

Agentic Workflow 的核心不是“让模型更自由”，而是**给模型一个可以行动的轨道**。状态机、任务拆解、依赖链、检查点、上下文管理，都是为了让 AI 的行动可观察、可恢复、可审计。

## 从最小循环开始：Plan、Act、Review

一个最小可用的 Agentic Workflow 可以从三个状态开始。

```ts
type AgentStep = 'plan' | 'act' | 'review';
```

这三个词看似简单，但背后是非常重要的工程分工。

| 状态 | 输入 | 输出 | 典型失败 |
| --- | --- | --- | --- |
| `plan` | 用户目标、环境状态、约束 | 可执行步骤、风险点、验证方式 | 计划太泛、遗漏约束、步骤不可验证 |
| `act` | 当前步骤、工具权限、上下文 | 工具调用结果或内容产物 | 工具失败、参数错误、权限不足 |
| `review` | 计划、执行结果、验收标准 | 通过、重试、修正计划、升级人工 | 自检过松、忽略证据、无限重试 |

最小循环的价值是把“生成一段回答”拆成了“规划、执行、检查”。这一步之后，系统才有机会做日志、重试、成本控制和人工审批。

## 状态机不是形式主义

![Plan、Act、Review 与重试检查点](/images/academy/agentic-workflows-02/plan-act-review-loop.png)

状态机的价值在于：每一步都必须有明确入口、出口和转换条件。

一个更接近生产系统的状态机可能是：

| 状态 | 责任 | 转换条件 |
| --- | --- | --- |
| `init` | 解析目标、权限、环境、可用工具 | 目标足够清楚后进入 `plan` |
| `plan` | 拆任务、标依赖、列风险、定义验证 | 计划可执行后进入 `act` |
| `act` | 执行当前任务或工具调用 | 执行完成后进入 `review` |
| `review` | 对照验收标准检查结果 | 通过进入下一步或 `done`，失败进入 `retry` |
| `retry` | 局部修复、调整参数、补上下文 | 未超限返回 `act`，超限进入 `escalate` |
| `escalate` | 请求人工判断或权限确认 | 获得确认后继续，拒绝后停止 |
| `done` | 汇总证据、输出结果、保存日志 | 终态 |

这不是为了把系统画复杂。它解决的是三个现实问题：

- 你能知道系统当前在哪里。
- 你能只重试失败的局部步骤。
- 你能在高风险转换前插入控制点。

如果一个 Agent 没有状态机，它仍然可能在 demo 中表现很好。但当任务变长、工具变多、上下文变复杂时，它会越来越像一个不可预测的黑盒。

## 任务拆解：每个节点都要能验收

“帮我优化这个项目”不是一个好任务节点。它太大、太模糊、没有验收标准。

更好的拆法是：

1. 扫描构建与测试入口，输出可执行验证命令。
2. 找出当前失败的检查项，并记录错误原文。
3. 只修复一个失败类型。
4. 重新运行对应验证。
5. 汇总变更、剩余风险和未验证部分。

好的任务节点应该满足四个条件。

| 条件 | 问题 | 好例子 |
| --- | --- | --- |
| 可验证 | 做完后怎么知道对了？ | `npm run check` 必须通过 |
| 可恢复 | 失败后能从哪里继续？ | 只重试当前文件生成，不重启整个流程 |
| 可记录 | 过程能不能留证据？ | 保存工具输入、输出、错误、耗时 |
| 可交接 | 下一个节点需要什么？ | 产出结构化 JSON 或明确文件路径 |

这里的关键是：不要让模型把“看起来像完成”当成完成。完成必须有外部证据。

## 上下文管理：不要把所有历史塞给模型

Agentic Workflow 很容易被上下文污染。模型拿到太多历史，会混淆当前目标、旧错误、已经废弃的计划和最新用户意图。

更稳的方式是按状态传递上下文。

| 状态 | 应该传入 | 不应该传入 |
| --- | --- | --- |
| `plan` | 用户目标、约束、可用工具、当前环境摘要 | 大量旧日志、无关文件全文 |
| `act` | 当前步骤、必要输入、工具权限、验收标准 | 整个计划外的开放任务 |
| `review` | 验收标准、实际输出、关键证据 | 模型自我解释的长篇辩护 |
| `retry` | 失败原因、上次参数、可调整范围 | 与失败无关的历史对话 |
| `done` | 最终产物、验证结果、剩余风险 | 中间草稿和无效尝试 |

上下文不是越多越好。上下文应该像函数参数一样，有边界、有类型、有生命周期。

## 人工检查点：系统安全的一部分

![人工检查点与高风险操作控制面](/images/academy/agentic-workflows-02/human-checkpoint-control-plane.png)

Agentic Workflow 不应该追求“永远不问人”。真实系统里，人工检查点是安全机制，也是产品体验的一部分。

应该触发人工确认的场景包括：

- 外部可见动作：发送邮件、发帖、提交评论、发布页面。
- 不可逆动作：删除数据、覆盖文件、清空队列、撤销部署。
- 成本动作：长时间任务、大量 API 调用、批量生成媒体。
- 权限升级：访问新数据源、读取敏感文件、调用生产环境。
- 低置信度判断：模型连续重试失败，或证据互相冲突。

检查点不是打断 Agent，而是把不可接受的风险停在执行前。优秀的系统会让用户只确认真正重要的事，而不是每一步都弹窗。

## 中间件模式：把横切能力放在状态外层

很多能力不应该写进每个状态的业务逻辑里。比如日志、追踪、权限、预算、速率限制、脱敏、重试策略。这些更适合用中间件包住状态执行。

一个简化结构：

```ts
type WorkflowMiddleware = (
  context: WorkflowContext,
  next: () => Promise<WorkflowResult>,
) => Promise<WorkflowResult>;
```

中间件可以做这些事：

- 在进入状态前记录输入摘要。
- 检查工具权限和预算。
- 给每次工具调用加 trace id。
- 捕获错误并转成结构化失败。
- 对输出做敏感信息扫描。
- 把状态转换写入审计日志。

这和 Web 后端中间件的价值很像：把所有请求都会经历的治理逻辑，放到统一通道上，而不是散落在业务函数里。

## 依赖链：从 LangChain 的 Chain 联想到 FastAPI 的依赖注入

做 Agentic Workflow 时，经常会遇到“某个步骤需要前一步结果”的问题。这里可以借用两个熟悉类比。

LangChain 里的 Chain 强调把多个处理步骤串起来：输入经过 A，再进入 B，再进入 C。FastAPI 的依赖注入强调把请求所需资源显式声明出来：当前路由需要用户、数据库 session、配置对象，就把这些依赖列出来。

Agentic Workflow 也应该显式声明依赖：

```ts
type StepSpec = {
  id: string;
  dependsOn: string[];
  inputSchema: unknown;
  outputSchema: unknown;
  verify: string;
};
```

这能避免两类常见错误：

- 模型在没有上游结果时提前执行下游步骤。
- 某个步骤输出格式变化后，下游仍按旧结构理解。

依赖显式化之后，系统才能判断哪些步骤可以并行，哪些步骤必须串行，哪些失败只影响局部。

## 案例：文档站内容翻修 Agent

假设你要构建一个 Agent，帮助维护一个多语言内容站。它的目标不是“写文章”，而是把一篇旧文章翻修到可发布状态。

一个可控的工作流可以这样设计：

1. `inspect`
   - 读取中日文文件、frontmatter、图片引用、内部链接。
   - 输出当前缺口：篇幅、图片、日文同步、过期术语、断链。
2. `plan`
   - 生成翻修计划。
   - 标出需要新增的图片、需要查证的官方资料、需要保留的 slug。
3. `draft`
   - 分段改写正文。
   - 输出中日文结构对齐版本。
4. `asset`
   - 生成或接入无文字图片。
   - 检查图片路径、尺寸和是否引用 SVG。
5. `review`
   - 检查是否有内部创作痕迹、是否有未证实结论、是否中日文结构失衡。
6. `verify`
   - 运行内容 QA、构建、页面预览。
7. `done`
   - 输出变更、验证结果、剩余风险。

这个 Agent 不需要“完全自主”。它需要的是可追踪的状态和清晰的验证证据。

## 常见反模式

**反模式一：只有一个巨大 Prompt。**

把所有规则、工具、目标、格式都塞进一个 Prompt，会让系统难以恢复。出错时你不知道应该修计划、修工具参数，还是修最终回答。

**反模式二：让模型自己判断所有事情是否完成。**

自检有价值，但不能替代外部验证。代码要跑测试，内容要过构建，操作要有日志。

**反模式三：失败后从头开始。**

长任务最怕整轮重启。正确做法是保存状态，让失败节点局部重试。

**反模式四：把人工确认放在结果之后。**

高风险操作必须在执行前确认。执行后再让人 review，已经太晚。

**反模式五：没有停止条件。**

Agent 必须有最大重试次数、预算上限、时间上限和升级路径。没有停止条件的自动化，迟早会变成运行成本问题。

## 落地模板：Agentic Workflow 设计卡

```md
### Workflow Goal

这个工作流要完成什么：

不负责什么：

### States

| State | Input | Output | Verification | Next |
| --- | --- | --- | --- | --- |
| init | | | | |
| plan | | | | |
| act | | | | |
| review | | | | |
| retry | | | | |
| escalate | | | | |
| done | | | | |

### Tools

| Tool | Permission | Risk | Logging |
| --- | --- | --- | --- |
| | read/write/external | low/medium/high | yes/no |

### Checkpoints

- 需要人工确认的操作：
- 需要成本确认的操作：
- 需要权限确认的操作：

### Failure Policy

- 单节点最大重试次数：
- 总预算上限：
- 何时升级人工：
- 何时直接停止：

### Observability

- 每次状态转换记录什么：
- 每次工具调用记录什么：
- 最终交付需要附带什么证据：
```

> **示例填法（Customer ticket triage workflow）**
>
> 这个工作流要完成什么：把新 ticket 分类、补齐上下文、给出建议回复草稿
> 不负责什么：不自动退款、不修改账号状态、不直接发送回复
> States：init=读取 ticket；plan=判断所需证据；act=调用 order/profile/policy tools；review=校验分类和证据；retry=缺字段重查；escalate=高风险转人工；done=输出 triage card
> Tools：ticket_read=read/low/log yes；order_lookup=read/medium/log yes；refund_action=禁止；draft_reply=write/low/log yes
> Checkpoints：需要人工确认的操作=退款、封号、合规投诉；需要成本确认的操作=高级模型复核；需要权限确认的操作=跨 workspace 查询
> Failure Policy：单节点最大重试次数=2；总预算上限=90 秒或 0.20 USD；何时升级人工=证据冲突或 VIP 用户；何时直接停止=权限不足
> Observability：每次状态转换记录 ticket_id/state/reason；每次工具调用记录 tool/input_hash/result_status；最终交付需要附带分类、证据链接、建议回复和置信度

## 检查清单

- 每个状态是否有明确输入和输出？
- 每个状态转换是否有可记录的条件？
- 每个任务节点是否能独立验证？
- 工具调用是否有权限、预算和日志？
- 高风险动作是否在执行前触发人工确认？
- 失败是否能局部重试，而不是整轮重启？
- 最终结果是否包含验证证据，而不只是模型解释？
