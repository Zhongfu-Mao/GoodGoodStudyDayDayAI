**说明：** 本文整理数据分析场景，强调 ChatGPT 是分析助手，不是最终审计工具。

## 这节课解决什么问题

很多数据工作卡在第一步：不知道表里有什么、哪些列重要、哪里异常、应该继续问什么。ChatGPT 可以帮助快速探索数据、生成图表建议、写出可读结论。

## 分析前先写决策问题

不要从“分析这个表”开始，而是从：

```text
我想判断 [业务问题]，手头数据是 [来源/时间范围]。
请先做 EDA，总结关键字段、缺失值、异常点和可能的分析路径。
不要直接给最终结论，先列出你需要确认的假设。
```

## 五步流程

1. 明确决策或问题。
2. 提供数据和字段说明。
3. 先要分析方法，再要结果。
4. 明确需要哪些图表或切分维度。
5. 输出可复用表格、摘要和后续问题。

## 官方页面强调的使用时机

页面里反复强调：ChatGPT 特别适合数据分析早期阶段。也就是你还不知道数据里有什么、哪些地方异常、应该从哪个角度继续看。

这和成熟 BI dashboard 不一样。Dashboard 适合重复监控固定指标；ChatGPT 更适合探索、解释、追问和把结果翻译成别人能读懂的摘要。

## 练习

上传一份 CSV 后，按顺序问：

1. 这个数据集有哪些字段，可能代表什么？
2. 哪些字段缺失或异常？
3. 可以从哪 3 个角度分析？
4. 请先做一个最小分析，并说明不确定性。
5. 把结果写成给非数据同事看的摘要。

## 风险

模型可能误解列含义、忽略数据质量问题、过度解释相关性。涉及财务、实验、医疗或商业决策时，需要人工复核公式、样本和统计判断。



## 完整版学习稿

### 学习定位

这一页可以当作 **Analyzing Data with ChatGPT** 的系统学习稿。它面向想用自然语言辅助数据探索、解释和汇报的人，重点不是背官方术语，而是把页面里的能力、场景和边界转成可以反复使用的工作方法。

### 学习目标

- 从决策问题出发，而不是从“分析这个表”出发。
- 先做 EDA 和数据质量检查，再做结论。
- 把洞察转成行动建议和后续分析问题。

### 官方内容拆解

| 模块 | 学习重点 | 可产出材料 |
| --- | --- | --- |
| Data orientation | 字段、口径、时间范围、缺失值 | 数据字典、质量报告 |
| EDA | 分布、异常、分组、趋势 | 初步观察和可视化建议 |
| Hypothesis | 为什么出现这些模式 | 待验证假设 |
| Action summary | 给非数据同事看的解释 | 优先观察、下一步分析 |

### 实操工作流

1. 说明要支持的业务决策。
2. 提供数据和字段定义。
3. 先要求数据质量检查和分析计划。
4. 再要求图表和分组分析。
5. 最后输出结论、限制、后续问题。

### 可复用 Prompt

```text
我想基于这份数据判断[决策]。请先做数据质量检查和 EDA，列出异常、缺失、字段解释风险，再给 4-6 条观察、可能原因、建议图表和下一步分析问题。
```

### 复核清单

- 输出是否只使用已提供或可追溯的信息，不把推断写成事实。
- 是否标出不确定性、待确认项和需要人工判断的地方。
- 是否给出可执行的下一步，而不是只生成漂亮文字。
- 是否符合团队、学校、公司或行业的隐私与合规要求。

### 学完应该留下什么

学完这一页，最好不要只留下摘要，而是留下 一份可复用的学习笔记、prompt 模板和实践清单。如果以后要补自己的课程心得，可以在这份材料后面继续追加：真实使用场景、失败案例、改进后的 prompt、以及哪些判断必须由人完成。

## 官方示例拆解

Data Analysis 页的官方示例不是只让模型“分析数据”，而是要求它围绕决策、上下文和可复用输出工作。

| 任务 | 输入上下文 | 适合产出 | 复核重点 |
| --- | --- | --- | --- |
| Exploratory data analysis | CSV/Excel、字段解释、时间范围 | 字段概览、缺失值、异常点、初步观察 | 列含义是否误解，异常是否真实 |
| Funnel review | 活动或产品漏斗数据 | 漏斗模式、原因假设、实验建议 | 分母口径、样本量、归因逻辑 |
| Channel/product performance | 渠道、产品、转化、收入数据 | 排名、低表现区域、后续分析问题 | 是否把相关性写成因果 |
| Visualization planning | 指标、分组、时间维度 | 图表建议、轴标签、分面方式 | 图表是否误导，单位是否清楚 |
| Executive summary | 分析结果和限制 | 4-6 条观察、行动建议、待确认项 | 是否夸大置信度 |

实际使用时，我会先要求“不要下最终结论，只列数据质量和可分析路径”，再逐步推进到图表和结论。这样可以减少模型一上来就给漂亮但不可靠结论的风险。

### 虚构案例

你拿到一份活动数据，要先理解质量，再给出给业务方看的洞察摘要。 你可以把输入材料设定为：数据文件、字段说明、时间范围、业务问题、指标口径。最后产出 EDA 摘要、异常清单、可视化建议、业务洞察和后续分析问题。

### 原创 Prompt Pack

1. 请先检查数据字段、缺失值、异常和口径风险。
2. 请做 EDA，并用非技术语言解释最重要的 5 个发现。
3. 请设计 4 张图表说明这个问题，包含轴和分组。
4. 请区分相关性、可能原因和需要验证的假设。
5. 请把分析结果写成给业务负责人的行动摘要。

## 亲测记录模板

> 这一段用于后续真正学完官方材料、跑过练习后继续追加。公开发布时，建议保留方法、过程和复盘，隐藏敏感输入、账号信息、客户资料、未验证结论和不可公开的内部材料。

### 最小实测任务

- 场景类型：团队业务流程
- 建议任务：选择一个真实但可以脱敏的团队任务，从输入整理到交付复盘跑一遍
- 输入材料：业务目标、受众、现有资料、品牌/流程约束、指标
- 目标产物：brief、memo、表格、复盘或下一步行动清单
- 关键边界：事实准确性、团队口径、客户/公司敏感信息

### 记录表

| 记录项 | 建议填写方式 |
| --- | --- |
| 我为什么学这一页 | 写清它和当前工作、学习或项目的关系 |
| 我实际用了什么输入 | 列出材料类型，避免公开敏感原文 |
| 第一版 prompt | 保留自己的写法，方便以后比较 |
| 第一版输出问题 | 记录含糊、遗漏、编造、格式不对或不适用之处 |

| 可公开内容 | 只发布脱敏后的流程、经验、失败案例和自己的理解 |

### 复盘问题

1. 这页内容在真实任务中最有用的一点是什么？
2. 第一次输出为什么不够好，是输入问题、模型问题，还是任务本身不清楚？
3. 哪个约束最能提升质量：角色、上下文、来源、格式、示例，还是评价标准？
4. 如果让朋友照着做，哪些步骤需要写得更明确？
5. 这次实测后，我会如何改写本文的个人心得部分？
