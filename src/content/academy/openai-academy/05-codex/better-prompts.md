**说明：** 本文深入探讨 Codex 提示词 (Prompt) 的撰写艺术，核心在于将工程思维注入自然语言指令。

## 核心差异：从“讨论”转向“委派”

ChatGPT 的提示词通常侧重于开放式讨论或创意激发，而 Codex 的提示词本质上是一份**工程任务单**。由于 Codex 具备读写文件与执行系统命令的能力，指令的结构化程度直接决定了任务交付的稳定性与安全性。

## 标准任务模版

```text
任务目标：[清晰描述需要达成的工程结果]

执行范围：
- 允许修改：[具体的目录路径或文件列表]
- 参考上下文：[相关的 Schema 定义或现有代码模式]

核心要求：
- 功能逻辑：[具体的行为描述]
- 编码风格：[对齐现有项目的命名、注释规范]
- 负面约束：[明确禁止的操作，如：不要重构无关模块、不要引入新依赖]

验证机制：
- 自动化指令：运行 [具体命令]
- 验收标准：[预期的输出结果或状态变化]

交付说明：
- 请摘要列出所有改动的文件。
- 简述验证过程及结果。
- 标出潜在的架构风险或需人工复核的逻辑。
```

## 典型避坑指南

| 常见错误 | 潜在后果 | 优化建议 |
| --- | --- | --- |
| **范围界定模糊** | 导致 Codex 误改或删除无关的业务逻辑。 | 使用白名单机制，明确指定 `src/components/` 等路径。 |
| **缺失验证闭环** | 无法第一时间发现代码语法错误或逻辑失效。 | 必须强制要求运行 `npm test` 或编译指令。 |
| **忽略禁止事项** | 产生大量非必要的重构，增加 Review 成本。 | 增加“Do NOT”列表，锁定修改边界。 |
| **需求高度抽象** | 生成的代码逻辑偏离真实业务意图。 | 提供具体的输入输出示例 (Few-shot) 或 API 定义。 |

## 完整版学习稿

### 课程定位

本篇为 **Write Better Prompts for Codex** 的系统化进阶指南。专为希望通过 Codex 实现高质量代码交付的开发者打造。重点在于通过精确的指令设计，将 AI 打造为高可靠性的研发代理。

### 学习目标

- 建立“提示词即规格说明书 (Spec)”的工程习惯。
- 掌握如何通过定义目标、范围、约束与验证机制来构建稳健的 Prompt。
- 能够将复杂的重构或研发任务拆解为可被 AI 精准执行的原子化步骤。

### 核心方法论拆解

| 模块 | 核心重点 | 实践产出 |
| --- | --- | --- |
| **目标设定 (Goal)** | 明确功能变更的核心价值 | 结构化验收条件 |
| **边界控制 (Scope)** | 严格限定可操作的代码平面 | 修改边界矩阵 |
| **语境注入 (Context)** | 提供背景知识、关联依赖与设计意图 | 上下文增强包 |
| **闭环校验 (Verification)** | 建立自动化的质量反馈链路 | 自动化校验脚本 |
| **产出定义 (Output)** | 规范交付摘要与风险评估格式 | 标准化交付报告 |

### 标准化工作流

1. **行为导向描述**：始终以最终用户的行为或系统状态的改变来定义目标。
2. **物理范围锁定**：明确列出需要 Codex 读取及写入的具体文件范围。
3. **注入调试信息**：提供准确的报错日志、测试失败堆栈或复现步骤快照。
4. **嵌入验证指令**：要求 Codex 在修改后主动执行 Lint、Build 或单元测试。
5. **强制风险自评**：引导 Codex 自查改动点，并主动报告可能引入的 Side Effects。

### 可复用提示词 (Prompt) 模板

```text
请协助我优化当前开发任务的指令。原始需求：[描述需求]。请将其重写为一个标准的 Codex 任务单，包含：项目背景、预期的逻辑行为、严格的修改范围、编码约束、用于验证的测试指令，以及最终的 Diff 评审摘要格式。
```

### 质量复核清单

- **信源一致性**：Prompt 中引用的 API 或依赖是否在当前代码库中真实存在。
- **职责透明度**：指令是否明确了哪些决策由模型完成，哪些需保留人工确认点。
- **可执行性验证**：提供的验证指令是否能在当前环境中直接运行并返回有效信号。
- **安全与合规**：指令中是否潜藏了泄露敏感信息或破坏访问控制的风险。

### 学习产出

完成本模块后，您应建立起属于自己的 Codex Prompt 资产库。建议在团队内部共享高效的任务模版，从而降低全员的 AI 协作摩擦。

## 实践增强方案

### 三阶段进阶练习

| 建议时长 | 练习任务 | 预期交付物 |
| --- | --- | --- |
| **30 分钟** | 快速扫描本页，将您上一个模糊的“帮我改代码”指令重写为结构化任务单。 | 优化后的 Prompt |
| **2 小时** | 针对一个涉及跨文件修改的复杂 Bug，设计并跑通一套带验证闭环的委派流程。 | 端到端协作记录 |
| **半天** | 为团队现有的 `CONTRIBUTING.md` 补齐一份《AI 提示词工程规范》。 | 团队协作规范 |

### 案例实操

**场景：** 您发现 Codex 在处理 CSS-in-JS 重构时总是改错全局主题变量。
**任务：** 重新设计重构指令，锁定变量作用域并增加视觉回归校验。
**产出：** 带有 Scope 限制的高质量 Prompt、验收标准、失败处理预案、原子化任务拆分路径。

### 进阶提示词包 (Prompt Pack)

1. “请将这段抽象的业务描述转化为具备‘上下文、行为、边界’三要素的 Codex 指令。”
2. “分析我提供的原始 Prompt，指出其中可能导致 Codex 产生幻觉或过度修改的逻辑断点。”
3. “为当前的后端重构任务增加一组具体的验收标准，并给出对应的 cURL 验证指令。”
4. “如果该任务执行失败，请设计一套引导 Codex 进行自我诊断与回滚的修复指令。”
5. “请为复杂的逻辑改动提炼出一套标准的交付汇报模版，重点突出对现有测试的影响。”

### 核心自测

- 我是否养成了“无边界、不委派”的 Codex 使用直觉？
- 我能否迅速识别出一个 Prompt 是否具备足够的“可验证性”？
- 在面对大规模代码库时，我是否掌握了通过 Context 注入提升准确率的技巧？
- 我是否建立了一套“任务拆解 -> 渐进式交付”的高阶协作模型？
- 我是否已经将 Prompt 优化能力沉淀为能够提升全队交付确定性的资产？

### 声明与边界

- 本内容旨在提供工程引导，应根据具体项目的复杂程度动态调整 Prompt 策略。
- 建议在非生产分支上对复杂的自动化指令进行充分验证。
- 引用时请注明官方信源链接。

## 实测笔记模板

> 记录您的提示词演进路径与交付效果对比，对核心业务数据进行脱敏。

### 提示词优化 (Prompt Iteration) 记录

- **初始任务**：如“把所有图标替换为新库”。
- **遇到的阻碍**：如“Codex 删除了部分非图标相关的 DOM 属性”。
- **优化核心**：锁定文件范围、增加“不要改动非图标属性”约束。
- **验证结论**：通过 `npm run build` 与人工 Diff 确认。

### 实践记录表

| 记录项 | 填写建议 |
| --- | --- |
| **学习动机** | 描述当前任务为何难以通过简单指令完成，以及优化的预期目标。 |
| **版本对比** | 记录“优化前”与“优化后”的 Prompt 全文，方便对比效果。 |
| **上下文优化** | 记录您向指令中补充了哪些关键的依赖信息或设计规范。 |
| **执行发现** | 记录在引入验证指令后，Codex 的自我纠偏表现。 |
| **质量信号** | 记录自动化指令反馈的通过率及人工 Review 的耗时变化。 |
| **可复用资产** | 总结沉淀下来的特定场景 Prompt 模版或正则表达式约束。 |
| **最终评估** | 评估 Prompt 结构的精细化程度与交付质量之间的正相关性。 |

### 深度复盘

1. 在本次实践中，哪一项约束条件对减少“非预期修改”起到了决定性作用？
2. 如何判断当前任务已经精细到了 Codex 可以“一次性跑通”的程度？
3. 哪一类背景信息的缺失最容易导致 Codex 产生严重的逻辑幻觉？
4. 如果让团队新手参考该 Prompt，还需要补充哪些操作层面的说明？
5. 基于本次实践，我将如何升级自己的“Prompt 工程规格化”手册？
