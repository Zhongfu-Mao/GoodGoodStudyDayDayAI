**说明：** 本文旨在梳理 Codex 在工程实践中的最佳适用任务类型。

## Codex 核心应用场景

| 任务类型 | 典型示例 |
| --- | --- |
| **故障修复 (Fixing)** | 解决构建/测试失败、类型错误或明显的逻辑 Bug。 |
| **增量开发 (Features)** | 快速构建小模块、UI 组件、API 端点或实用脚本。 |
| **工程维护 (Maintenance)** | 执行重命名、格式迁移、Frontmatter 批处理等重复性工作。 |
| **测试驱动 (Testing)** | 补全单元测试、回归测试用例及测试 Fixtures。 |
| **内容工程 (Content)** | 按 Schema 生成文档、自动索引及坏链检查。 |
| **流程自动化 (Automation)** | 编写 CI 步骤、工程脚本及重复性任务指令。 |

## 不建议直接委派的任务

对于**需求模糊、涉及复杂价值取舍、权限极端敏感、需要深度产品决策**或**缺乏闭环验证手段**的任务，不建议直接交由 Codex 处理。推荐先由开发者主导任务拆解，再针对明确的子任务进行委派。

## 完整版学习稿

### 学习定位

本页是 **Codex Use Cases** 的深度学习指南。其核心目标是帮助开发者建立一套“任务识别框架”，将抽象的 AI 能力转化为具体的工程产出。

### 学习目标

- 建立用例分类体系：Bug 修复、特性开发、测试补全、重构优化、文档维护及迁移。
- 为各类任务定义标准化的“输入-执行-验收”模型。
- 掌握识别“不可委派任务”的直觉，降低工程风险。

### 官方内容提炼

| 场景模块 | 核心重点 | 产出成果建议 |
| --- | --- | --- |
| **Bug fixing** | 聚焦复现步骤、错误日志及预期行为。 | 修复补丁 + 回归测试。 |
| **Feature work** | 明确功能需求、交互边界及技术约束。 | 功能实现 + 相关文档。 |
| **Tests** | 覆盖边界条件，遵循现有测试范式。 | 高覆盖率的测试脚本。 |
| **Refactor** | 明确重构目标及行为不变性。 | 逻辑等价的增量 Diff。 |
| **Docs** | 针对目标读者，提炼代码事实。 | README、API 规范、迁移指南。 |

### 推荐工作流

1. **类型识别：** 判断任务属于哪类典型用例。
2. **上下文准备：** 搜集该任务所需的各类代码、日志和文档。
3. **环境同步：** 确保 Codex 已理解相关的测试框架和编码规范。
4. **增量交付：** 要求其提供可审计的 Diff。
5. **双重验收：** 通过自动化测试与人工 Review 完成闭环。

### 实用 Prompt 模板

```text
请评估以下工程任务。首先判断其属于哪类 Codex 用例，并提供一个最小执行计划：
1. 需要检索的文件范围
2. 修改策略与步骤
3. 验证与测试方案
4. 潜在风险点及交付物定义
```

### 复核清单

- **事实性检查：** 输出是否仅基于已知项目上下文，杜绝“幻觉”导致的错误逻辑。
- **确定性标注：** 是否明确区分了“确定改动”与“建议尝试”的部分。
- **可执行性：** 是否提供了明确的验证指令，而非空洞的说明。
- **合规审查：** 是否符合团队代码规范及安全隐私政策。

## 学习增强工具包

### 针对性练习建议

| 时间 | 练习任务 | 预期产出 |
| --- | --- | --- |
| **30 分钟** | 对比当前项目，识别出 5 个最适合 Codex 处理的存量任务。 | 任务候选清单 |
| **2 小时** | 针对其中一个任务，记录完整的 Prompt 交互与修正过程。 | 实践案例报告 |
| **半天** | 构建一套适合所在团队的 Codex 应用手册（Playbook）。 | 团队协作指南 |

### 模拟实践案例

**背景：** 你需要为团队建立一份“Codex 适用手册”，明确哪些任务该交给 AI，哪些必须由人主导。
**任务：** 基于公司现有技术栈（如 React + NestJS），定义一套 Bug 修复和 API 开发的委派标准。
**产出：** 用例分级表、输入信息模板、验收流程及风险等级标注。

### 核心 Prompt Pack

1. “请将以下待办事项按工程难度和 AI 适用度进行分类。”
2. “针对 [特定任务类型]，请生成一个包含详细上下文的委派模板。”
3. “请为该任务定义一套闭环的验收标准（包括测试与 Review 要点）。”
4. “请识别此任务中涉及架构变更或核心逻辑的部分，并进行风险预警。”
5. “请辅助我制定一份团队引入 Codex 的灰度实施计划。”

## 实践记录模板

> **提示：** 重点记录“如何沟通”和“如何纠偏”，并确保护理后的记录不包含任何公司机密。

### 最小实践任务

- **目标：** 选择一个具备回归测试支撑的局部重构或功能点，体验委派全过程。
- **关键点：** 重点关注 Codex 对现有代码范式的模仿能力。

### 记录表

| 记录项 | 填写建议 |
| --- | --- |
| **学习动机** | 该用例解决了哪个实际痛点（如“测试覆盖率低”）。 |
| **上下文深度** | 提供了多少代码深度？是否提供了依赖项信息？ |
| **Prompt 迭代** | 如何通过追加“Constraints（约束）”来修复首次输出的问题。 |
| **幻觉记录** | 是否出现过虚构 API 或不匹配逻辑的情况？ |
| **验收结论** | 测试是否通过？Review 发现了哪些隐藏 Bug？ |
| **最佳实践** | 从本次尝试中提炼出的一条“通用指令”或“避坑准则”。 |
