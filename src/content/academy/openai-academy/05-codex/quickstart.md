## Codex 入门的核心要素

Codex 的入门重点不仅在于“让 AI 编写代码”，更在于学习如何精准描述工程任务，使其能在特定的项目上下文中高效执行、验证并报告结果。

## 任务单结构化建议

| 元素 | 编写要点 |
| --- | --- |
| **目标 (Goal)** | 明确是修复 Bug、新增功能还是重构优化。 |
| **范围 (Scope)** | 限定允许修改的目录或特定文件。 |
| **约束 (Constraints)** | 必须遵循现有代码风格，严禁无关的重构。 |
| **验证 (Verification)** | 明确需要运行的测试脚本或检查项。 |
| **交付 (Deliverables)** | 总结改动点、未完成项及潜在风险。 |

## 实践经验分享

在实际操作中，建议让 Codex 先**分析项目结构**，再进行文件修改。
- **对于内容类站点：** 任务可设定为新增草稿、补全 frontmatter、检查 schema 或运行 `npm run check`。
- **对于代码仓库：** 必须明确测试命令和验收标准。

## 完整版学习稿

### 学习定位

本页可作为 **Codex Quickstart** 的系统性学习参考。它面向首次将 Codex 引入本地代码库的开发者，核心不在于记忆术语，而在于将页面提供的能力、场景和边界转化为可标准化的工作方法。

### 学习目标

- 掌握从“打开库、提需求、审 Diff”到“完成验证”的开发节奏。
- 学会为 Codex 定义第一个“小而美”的明确任务。
- 避免在初期交给它影响范围过大、定义模糊的改造任务。

### 官方内容提炼

| 模块 | 核心重点 | 产出建议 |
| --- | --- | --- |
| **Select repo** | 选定目标仓库及分支。 | 明确当前工作区。 |
| **Define task** | 定义小步快跑的任务及验收标准。 | 产出清晰的 Prompt。 |
| **Let it inspect** | 坚持“先调研，后动手”的原则。 | 产出修改计划及影响范围。 |
| **Review diff** | 重点关注逻辑变化和潜在风险。 | 进行人工质量审查。 |
| **Verify** | 执行测试、构建及手动核查。 | 获取可合并的信心信号。 |

### 推荐工作流

1. **筛选：** 选择一个低风险的 Bug 或微小功能点。
2. **描述：** 明确预期行为、关联文件及约束条件。
3. **计划：** 要求 Codex 先提供实施方案，而非直接改代码。
4. **验证：** 实现后通过 Diff 和自动化测试进行双重验证。
5. **复盘：** 记录本次 Prompt 的优缺点，持续迭代。

### 常用 Prompt 模板

```text
请协助我在当前仓库中执行一项低风险任务：[描述任务内容]。
修改范围限定在：[指定文件/模块]。
完成后请运行：[测试/构建命令]。
最后请简要说明改动内容及可能存在的风险点。
```

### 复核清单

- **事实性检查：** 输出是否仅基于已知信息，严禁将推断当作事实。
- **透明度：** 是否明确标注了不确定性、推测点及需要人工决策的地方。
- **行动导向：** 是否提供了明确的下一步建议，而非仅生成说明文本。
- **合规性：** 是否符合团队、组织或行业的隐私与安全标准。

### 学习产出建议

完成本页学习后，建议沉淀出一份**可复用的实践手册**（包括 Prompt 模板和复核清单）。在后续实践中，不断追加真实案例、失败教训及优化后的 Prompt，构建个人的 AI 辅助开发知识库。

### 模拟实践案例

**背景：** 你需要利用 Codex 修复一个局部模块的 Bug，并运行单元测试。
**输入参考：** Bug 描述、复现步骤、关联文件路径、测试命令。
**预期产出：** 结构化的 Task Prompt、实施计划、Diff 结果、测试报告及风险自评。

### 常用 Prompt 组合 (Pack)

1. “请将此 Bug 描述转化为适合 Codex 执行的任务单。”
2. “在修改前，请先分析并列出关联的文件，暂不进行修改。”
3. “请实现最小化修复，并同步补齐回归测试用例。”
4. “请执行测试，并对失败或通过的原因进行深度解析。”
5. “请为本次修改生成一份简练的 Pull Request 总结。”

### 最小实践任务

- **场景：** Codex 任务委派。
- **建议任务：** 选择一个可回滚、逻辑清晰的微任务进行尝试。
- **关键约束：** 必须包含人工 Diff 审查、自动化测试验证及明确的权限控制。
