**说明：** 本文整理 Codex for Work 的进阶工作流。

## 三个关键词

| 能力 | 解决什么 |
| --- | --- |
| Automations | 定期重复任务不再完全靠手动 |
| Plugins and skills | 让 Codex 连接工具，并按你的流程工作 |
| Settings | 减少打扰，控制权限和默认行为 |

## 适合自动化的任务

- 每周整理资料
- 定期生成报告草稿
- 扫描仓库或文档变化
- 生成待办或 follow-up
- 检查固定格式内容

## 风险

自动化的前提是任务边界清楚。没有明确输入、输出、复核方式的流程，不应该自动跑。越能影响外部系统，越需要审批和日志。



## 完整版学习稿

### 学习定位

这一页可以当作 **Codex Automations, Plugins and Settings** 的系统学习稿。它面向想让 Codex 更贴合团队工具链和自动化场景的人，重点不是背官方术语，而是把页面里的能力、场景和边界转成可以反复使用的工作方法。

### 学习目标

- 理解设置、插件和自动化会改变 Codex 可做的事。
- 学会先设计权限和边界，再接入能力。
- 把自动化任务做成可观测、可停止、可审查的流程。

### 官方内容拆解

| 模块 | 学习重点 | 可产出材料 |
| --- | --- | --- |
| Settings | 默认行为、环境、权限 | 团队标准 |
| Plugins | 连接外部工具或专用能力 | 扩展动作面 |
| Automations | 周期性或触发式任务 | 报告、检查、维护 |
| Controls | 审批、日志、失败处理 | 安全运营 |

### 实操工作流

1. 列出团队最重复、输入输出最稳定的任务。
2. 判断是否需要插件或自动化。
3. 设置最小权限和输出报告。
4. 先人工触发运行几次。
5. 稳定后再考虑周期化。

### 可复用 Prompt

```text
请评估这个 Codex 自动化设想是否合理。请输出需要的设置/插件、权限范围、触发条件、人工审批点、日志和失败处理策略。
```

### 复核清单

- 输出是否只使用已提供或可追溯的信息，不把推断写成事实。
- 是否标出不确定性、待确认项和需要人工判断的地方。
- 是否给出可执行的下一步，而不是只生成漂亮文字。
- 是否符合团队、学校、公司或行业的隐私与合规要求。

### 学完应该留下什么

学完这一页，最好不要只留下摘要，而是留下 一份可复用的学习笔记、prompt 模板和实践清单。如果以后要补自己的课程心得，可以在这份材料后面继续追加：真实使用场景、失败案例、改进后的 prompt、以及哪些判断必须由人完成。

### 虚构案例

你要把 Codex 接入团队工具，但需要先定义设置、插件和自动化边界。 你可以把输入材料设定为：工具链、权限、数据敏感度、自动化任务、审批人。最后产出 插件需求表、自动化风险评估、设置清单。

### 原创 Prompt Pack

1. 请评估这个 Codex 插件需求是否必要。
2. 请列出自动化需要的最小权限。
3. 请设计设置清单，确保不会误触高风险动作。
4. 请定义自动化失败时的通知和回滚。
5. 请把插件/自动化试点写成实施计划。

## 亲测记录模板

> 这是读者可复制使用的实践记录模板。记录时建议保留方法、过程和复盘，隐藏敏感输入、账号信息、客户资料、未验证结论和不可公开的内部材料。

### 最小实测任务

- 场景类型：Codex 任务委派
- 建议任务：选择一个可回滚、范围清楚的小任务，让 Codex 完成并记录 diff 与验证
- 输入材料：任务说明、相关文件、约束、测试命令、验收标准
- 目标产物：任务 prompt、计划、改动摘要、验证结果、风险说明
- 关键边界：代码审查、测试结果、权限范围、不要接受未理解的改动

### 复盘问题

1. 这页内容在真实任务中最有用的一点是什么？
2. 第一次输出为什么不够好，是输入问题、模型问题，还是任务本身不清楚？
3. 哪个约束最能提升质量：角色、上下文、来源、格式、示例，还是评价标准？
4. 如果让朋友照着做，哪些步骤需要写得更明确？
5. 这次实测后，我会如何改写本文的个人心得部分？
