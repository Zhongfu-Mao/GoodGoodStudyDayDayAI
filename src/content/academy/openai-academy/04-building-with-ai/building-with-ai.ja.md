## 本モジュールが解決する課題

Building with AIの核心は、AIを単一のツールとして利用するのではなく、**持続可能な「システム」として構築すること**にあります。OpenAI Academyでは、この進展を以下の4つの柱で定義しています。

| 柱となる領域 | 学習の目的 |
| --- | --- |
| **Codex for builders** | Codexを活用し、実際のコーディングタスクや開発自動化ワークフローを高度化します。 |
| **Technical tracks** | AIシステムのアーキテクチャ選定から実装まで、ステップバイステップで習得します。 |
| **AI techniques** | 高度なプロンプト戦略や、AIと人間の効果的な協働技術を探求します。 |
| **Solution patterns** | 再利用可能な設計パターンを用いて、実務における複雑な課題を解決します。 |

本ロードマップは、Academy（学習区）とEngineering（実装区）を繋ぐ架け橋となります。Academyで手法を学び、Engineeringでその実装を再現・最適化するサイクルを目指します。

## ツール利用からシステム構築への成熟度モデル

AIの活用レベルは、以下の4つの段階に分けられます。

| レベル | 典型的な行動 | 主なリスク |
| --- | --- | --- |
| **1. ツール利用** | ChatGPTやCodexを単発のタスク（翻訳、要約など）に利用。 | 出力の不安定さ、手動でのコンテキスト管理。 |
| **2. ワークフロー化** | ProjectsやSkillsを活用し、反復的な協働タスクを構造化。 | プロセス境界の曖昧さ、評価の不足。 |
| **3. システム構築** | APIを呼び出し、製品や内部システムにAI能力を統合。 | 評価コスト、権限管理、遅延、コスト増。 |
| **4. パターン化** | 解決策をコンポーネント、スクリプト、Solution Packとして抽象化。 | 過度な抽象化、特定シーンへの過学習。 |

Building with AIの主戦場はレベル3と4、すなわち**「AIをシステムの一部として組み込む」**ことにあります。

## ビルダーが習得すべき5つのエンジニアリング能力

プロンプトエンジニアリングからシステムエンジニアリングへ移行するには、以下の能力が不可欠です。

1. **タスク設計 (Task Design)**：どの工程をAIが担い、どの工程を従来のプログラムや人間が担うべきかを定義する。
2. **コンテキスト設計 (Context Architecture)**：情報の検索（RAG）、ファイル連携、セッション状態の保持方法を設計する。
3. **ツール設計 (Tooling)**：モデルが検索、データベース、API、外部アプリケーションを操作できるようにする。
4. **評価設計 (Evaluation)**：テストデータセット、評価指標（Rubric）、回帰テストを確立し、品質を数値化する。
5. **運用設計 (Production Ops)**：コスト管理、権限、監査、セキュリティ、パフォーマンス監視を統合する。

## システム設計実務テンプレート

新しいAI機能を設計する際、まず以下の問いを埋めることから始めます。

| 項目 | 定義すべき内容 |
| --- | --- |
| **ユーザーの目的** | その機能によって、ユーザーは最終的に何を達成したいのか？ |
| **モデルの役割** | モデルはどのステップ（構造化、草案作成、検品など）を担うのか？ |
| **プログラムの役割** | 確定的な処理（バリデーション、権限チェック、DB保存）はどう行うか？ |
| **人間の役割** | どの接点で人間が承認（ファクトチェック、公開判断）を行うか？ |
| **評価方法** | どのようなテストスイートや評価指標で合格を判定するか？ |
| **失敗への備え** | 出力が不適切な場合、システムはどう振る舞い、どう人間に通知するか？ |

これらはそのままEngineeringセクションの記事テンプレートとして機能します。



## 完全版学習ノート

### 学習の位置づけ

本ページは **Building with AI 総覧** の学習用ガイドです。AIを「使う」側から「作る」側へとステップアップしたいビルダーを対象としています。単なる技術解説ではなく、要件定義から本番運用までのエンジニアリング・サイクルを習得することを目指します。

### 学習ゴール

- AI「システム」としての全体像（要件、データ、評価、運用）を理解する。
- Agents、RAG、Evals、本番最適化へと続く具体的な学習ルートを確立する。
- 全ての技術的な取り組みを、測定可能な「ビジネス価値」へと紐付ける。

### コンテンツの分解

| フェーズ | 学習の重点 | 期待される成果物 |
| --- | --- | --- |
| **Problem framing** | 課題定義、ターゲット、成功指標の策定。 | プロダクト・ブリーフ / 要件定義。 |
| **Architecture** | モデル、ツール、RAG、Agent構成の選定。 | システム構成図。 |
| **Evaluation** | テストセットの構築、評価基準の設計。 | 評価スイート / 品質レポート。 |
| **Production** | 遅延、コスト、セキュリティ、監視体制の構築。 | リリース・チェックリスト。 |
| **Iteration** | ログとフィードバックに基づく継続的改善。 | 改善ロードマップ。 |

### 実務へのアドバイス

1. **MVP（最小機能）から始める**：複雑な構成（RAGや複数Agent）に走る前に、最も単純な構成でコアタスクを完遂させます。
2. **評価主導開発**：ロジックを組む前に、何をもって「成功」とするかの評価セットを先に用意します。
3. **非機能要件を重視する**：遅延、コスト、プライバシーを「後付け」にせず、最初から設計に組み込みます。
4. **人間をループに（HITL）**：高リスクな判断や最終的なアウトプットには、必ず人間が介在できるポイントを設けます。
5. **データに基づく改善**：本番環境のログを分析し、プロンプトやモデルの弱点を特定して修正を繰り返します。
