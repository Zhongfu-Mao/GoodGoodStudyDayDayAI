# プロンプト文字列から始めない

多くの LLM アプリケーションの初版は、一つのプロンプトと一回の API 呼び出しだけで作られてしまいます。これはデモンストレーションには十分ですが、長期的な保守には適していません。真に反復改善が可能な「最小骨格」は、LLM 呼び出しを一連のエンジニアリング・ユニットとして扱います。つまり、入力と出力の契約（Contract）、実行パラメータ、エラー処理、トレースログ、コスト、そして評価サンプルをセットで管理するということです。

目標は、最初から巨大なプラットフォームを構築することではありません。すべての振る舞いを一つのブラックボックスな文字列に隠さないようにすることです。呼び出しが観測可能であればシステムは改善でき、出力が検証可能であれば安定性が増し、評価が再現可能であれば継続的な進歩が可能になります。

## 信頼できる呼び出しの最小構造

堅牢な呼び出しユニットには、少なくとも以下の7つの要素が必要です。

1. **タスク名（Task Name）**：今回の呼び出しが解決する具体的なタスク（例：`summarize_radar_item`）。
2. **入力スキーマ（Input Schema）**：フィールド、型、必須性、および長さ制限の定義。
3. **プロンプトテンプレート（Prompt Template）**：業務データと指示内容を混同しない、安定したテンプレート。
4. **モデル設定（Model Config）**：モデル名、Temperature、Max Tokens、およびツール設定。
5. **出力スキーマ（Output Schema）**：期待される形式（JSON、Markdown、特定のタグ、自然文など）。
6. **検証（Validation）**：解析失敗、欠損、長さ超過、引用不足などへの対応戦略。
7. **トレースログ（Trace Log）**：入力・出力の要約、トークン消費、遅延、エラー詳細、バージョン情報の記録。

これら7つを用意するだけで、「モデルが時々不安定だ」という曖昧な問題を、「どのレイヤーのロジックが不安定なのか」という具体的なエンジニアリング判断に分解できるようになります。

## エラー処理の分類設計

LLM 呼び出しの失敗には、さまざまなパターンがあります。ネットワーク異常、API レート制限、タイムアウト、出力形式の不備、内容の品質不足、回答不能、ツールの失敗、権限不足など、それぞれで対応策が異なります。

ネットワークエラーは再試行（Retry）で解決でき、形式エラーはモデルへの修正要求やパーサーによる部分修正が有効です。回答不能な場合は、モデルに無理やり答えさせるのではなく、明示的にそのステータスを返すべきです。権限失敗の場合は、直ちに処理を停止し人間に通知する必要があります。エラーの種類を明確に定義して初めて、信頼できる自動リトライとアラート体系が構築できます。

## トレースログ：事後ではなく設計に組み込む

トレース（Trace）がなければ、AI アプリケーションの失敗原因を説明することは不可能です。最小限のトレースには、全文を保存する必要はありませんが、リクエストのハッシュ、データ長、タスク名、プロンプトのバージョン、モデルのバージョン、トークン数、処理時間、検証結果、エラーの種類を含めるべきです。機密データを扱う場合は、匿名化の設計も必要です。

最も重要なのは、**「出力された結果を、当時の入力、テンプレート、モデル設定に正確に紐付けられること」**です。これができなければ、今日遭遇した失敗例（Bad Case）を明日再現し、改善に繋げることができなくなります。

## 実験の目標

この実験のゴールは、「モデルを一度呼び出す」という処理を、高信頼な安定した関数としてラップすることです。複雑なフレームワークは不要ですが、毎回の呼び出しが再現可能、検証可能、かつ集計可能である必要があります。完了後には以下の3つの成果物を得ることを目指します。

- 汎用的な `run_llm_task()` ラッパー関数。
- 典型的な `tasks/summarize_article.yml` タスク設定ファイル。
- 蓄積された `traces/llm-calls.jsonl` 実行ログ。

実験の題材には「サイト記事の要約」をお勧めします。Markdown を入力し、タイトル、3文の要約、推奨タグ、そして人間による確認が必要なリスク箇所を出力させます。このタスクはシンプルですが、入力、出力、検証、失敗、ログのすべてのプロセスを網羅できます。

## コードの骨格設計

プロンプトを業務ロジックの中にハードコーディングしてはいけません。タスクの設定を以下のように分離します。

```yaml
name: summarize_article
version: 1
model: gpt-5.4-mini
temperature: 0.2
max_output_tokens: 600
input_schema:
  path: string
  title: string
  body: string
output_schema:
  summary: string
  tags: string[]
  risks: string[]
  status: ok | needs_review | insufficient_input
```

ラッパー関数は、設定の読み込み、メッセージの組み立て、モデルの呼び出し、出力の検証という4つの職務のみを担当し、「記事を要約する」という具体的な業務ロジックは持たせません。業務ロジックを Task Config と Schema に留めることで、この関数を翻訳、抽出、分類、レビューなど他のタスクにも容易に転用できるようになります。

## 失敗注入テスト（Failure Injection）

信頼性は、正常系（Happy Path）だけでは測れません。意図的に失敗を誘発する、以下の5つのテストケースを用意してください。

1. **通常記事**：正常系の検証。
2. **空の本文**：入力チェックの検証。
3. **長すぎる本文**：切り詰めや圧縮ロジックの検証。
4. **フロントマターのタイトル欠損**：メタデータの堅牢性の検証。
5. **プロンプトインジェクション攻撃**：本文中に「以上のルールを無視せよ」などの指示を含め、防御策を検証。

それぞれの失敗を `insufficient_input` などの明確なステータスにマッピングします。実験の価値は「動くこと」ではなく、異常系に対してどれだけ確定的な処理ができるかにあります。

## チェックリスト

- 各呼び出しにタスク名、バージョン、モデル情報を記録しているか。
- 出力がスキーマ検証を通過した後にのみ、後続の業務ロジックへ渡されているか。
- 再試行（Retry）時に、単なるリピートではなく具体的なエラー情報をモデルに伝えているか。
- トレースログから、入出力の要約、エラー種別、所要時間を特定できるか。
- 「回答不能」や「入力不足」に対して明示的なステータスを設計しているか。
- ログ記録において、機密データの匿名化や長さ制限を行っているか。

## 試してみること

`run_llm_task()` ラッパー関数を用いて、サイト記事の要約タスクを実行します。まずは10件の入力サンプルと期待される出力フィールドを用意し、実行ごとに JSONL 形式のトレースを生成します。意図的にフィールド欠損、出力過長、回答不能の3つのパターンを発生させ、システムがそれらを汎用的なエラーではなく、正しく分類して処理できるかを確認してください。

実験後には、**「初回通過率」「再試行後の通過率」「人間による確認率」**の3つの指標を確認します。最初は小さなデータセットで構いません。それらが将来、プロンプトやモデル、スキーマを調整する際の重要な回帰テストのベースになります。
