# 最小 RAG に必要なもの

RAG（検索拡張生成）のデモを作るのは簡単です。ドキュメントを読み、Chunk に分け、Embedding を生成してベクトル検索を行い、その結果をプロンプトに流し込むだけです。しかし、実際に運用・保守が可能な「最小システム」には、引用、拒答（答えがない場合の処理）、評価（Eval）、そして観測性（Observability）が不可欠です。

目標はシステムの複雑さを追求することではなく、すべての回答を追跡可能にすることです。「根拠はどこにあるのか？」「なぜこの断片が検索されたのか？」「回答が間違っている場合、それはドキュメント不足か、検索の失敗か、リランキングの失敗か、あるいは生成段階のハルシネーション（幻覚）か？」を明確に判断できるようにします。

## データの準備

まずは小さなデータセットから始めましょう。例えばサイト内の20本の記事を選び、タイトル、パス、日付、タグ、本文を抽出します。分割（Chunking）の際、単純な固定文字数でのカットは避け、見出しの階層や出典パス情報を保持するようにします。各 Chunk には最低限、以下のメタデータを持たせます。

- `doc_id`
- `title`
- `path`
- `heading`
- `text`
- `date`
- `tags`

これらのメタデータは、後の検索、フィルタリング、引用生成、そしてデバッグのあらゆる場面で重要な役割を果たします。

## 検索とコンテキストの組み立て

第一段階は基本的なベクトル Top-k 検索で十分ですが、そこで立ち止まってはいけません。検索結果をモデルに渡す前に、断片を番号、タイトル、出典、本文を含む「読みやすいコンテキスト」として構造化します。プロンプトでは、「提示された断片のみに基づいて回答すること」を厳格に要求し、確証が得られない場合は「提供された資料からは確認できない」と明示させます。

コンテキストの組み立ては、想像以上に重要です。8つの Chunk を無秩序に並べるのと、テーマや時間、出典ごとに整理して提示するのとでは、モデルの生成精度が大きく変わります。モデルは従来のデータベースではありません。証拠（Evidence）の明確なレイアウトが必要です。

## 最小評価セット（Eval Set）

システムの有効性を検証するために、3つのカテゴリの質問を用意します。

1. **直接命中**：答えが単一の断片に明示されている。
2. **統合判断**：複数の記事を組み合わせて判断する必要がある。
3. **無回答**：提供された材料の中に答えが存在しない。

各カテゴリで最低10問ずつ用意します。評価時には、正しい断片が検索されたか、回答が正しく出典を引用しているか、答えがない場合に正しく拒答できたかを記録します。これにより、問題が検索（Retrieval）にあるのか生成（Generation）にあるのかを切り分けられます。

## 失敗時の処理

RAG の失敗時のレスポンスも標準化する必要があります。例えば、以下のような構造を返します。

```json
{
  "status": "insufficient_evidence",
  "answer": "",
  "citations": [],
  "missing": "提供された材料内では、該当する回答の根拠を確認できません"
}
```

これは単なる「申し訳ありませんが分かりません」という謝罪文よりも、プロダクト側のロジックで扱いやすい形式です。

## 実験の目標

この実験の目的は、単に「文書と会話できるデモ」を作ることではなく、**評価可能な**小型 RAG システムを構築することです。完了後には以下の成果物が残るようにします。

- `documents.jsonl`：正規化された文書データ。
- `chunks.jsonl`：メタデータ付きのテキストブロック。
- `retrieval_trace.jsonl`：各検索と回答のトレース記録。
- `eval_questions.jsonl`：固定のベンチマーク問題集。
- 失敗事例の分析表。

最初は小さなデータセットで始める方が、分割ロジック、検索精度、引用、拒答の問題を浮き彫りにしやすく、問題の特定も容易になります。

## プロジェクトの骨格

ロジックを分離し、見通しを良くするために以下のような構成を推奨します。

```text
rag-lab/
  data/documents.jsonl
  data/chunks.jsonl
  eval/eval_questions.jsonl
  traces/retrieval_trace.jsonl
  src/prepare.ts    # Markdown を構造化文書へ変換
  src/retrieve.ts   # 候補 Chunk の取得を担当
  src/answer.ts     # 候補 Chunk に基づく生成を担当
  src/evaluate.ts   # 結果の比較と評価を担当
```

このように責務を分けることで、システムが失敗した際にどのモジュールを修正すべきかが一目で分かります。

## 検索の実験

初版はベクトル Top-k 検索のみで、その記録を残すことから始めます。第二版でキーワード検索やメタデータフィルタリングを導入し、第三版でリランカー（Reranker）の追加を検討します。各ステップで同じ評価セットを用い、以下の指標を比較します。

- 正しい Chunk が Top-3 に入っているか。
- 正しい Chunk が Top-8 に入っているか。
- 回答が正しい出典を引用しているか。
- 答えがない場合に正しく拒答しているか。
- 資料外の情報（ハルシネーション）を混ぜていないか。

「なんとなく良い回答」よりも、これらの硬い指標こそが RAG の品質を支えます。

## 失敗パターンの分類

実験中に発生する失敗を、以下の5つに分類して記録してください。

1. **Chunk が短すぎる**：答えが分断されてしまい、情報が足りない。
2. **Chunk が長すぎる**：検索にはヒットするが、文脈にノイズが多くなる。
3. **Query が短すぎる**：意味的な表現が不足し、重要な制約を拾えない。
4. **Top-k が大きすぎる**：低品質な断片が混ざり、モデルが混乱する。
5. **プロンプトの制約不足**：引用が要求されず、根拠が追跡できない。

失敗を分類することで、Chunk 分割、検索ロジック、あるいはプロンプトのどこを直すべきかが明確になります。

## 受け入れ基準

初版は完璧である必要はありません。直接命中問題の Top-3 再現率（Recall）が 80% 以上、無回答問題の拒答率が 80% 以上、すべての有効な回答に最低1つの引用が含まれている、といった基準から始めましょう。

## 試してみること

サイトのコンテンツを使ってローカル RAG を構築し、`retrieval_trace.jsonl` を出力してみてください。質問、Top-k 断片、最終的な文脈長、回答、引用、人間によるラベルを記録します。これにより、Chunk やプロンプトを変更するたびに回帰テストが可能になります。

最後に、失敗した事例を `eval_questions.jsonl` にフィードバックします。RAG の評価セットは一度作って終わりではなく、実際の失敗から学び、育てていくものです。
