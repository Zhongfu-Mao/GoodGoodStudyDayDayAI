# Harness はモデル外側のエンジニアリングレイヤー

Agent の信頼性は、モデルそのものだけでなく、それがどのような実行環境に置かれているかによって決まります。この環境を「Harness（ハーネス）」と呼ぶことができます。Harness は、ツール、状態、コンテキスト、権限、ログ、評価、そして停止条件をモデルに提供する役割を担います。Harness のない Agent は、非常に聡明でありながら計器類を持たないパイロットのようなものです。Harness を備えて初めて、Agent はエンジニアリングチームが管理・運用可能な「システム」となります。

Harness の目的は Agent を自由にすることではなく、その自由を観測可能にし、制限をかけ、必要に応じて復旧できるようにすることにあります。

## ログは意思決定のプロセスを記録する

通常のアプリケーションログはリクエストとレスポンスを記録しますが、Agent のログでは各ステップの「意思決定」を詳細に追う必要があります。

- **現在の目標**
- **現在の状態のサマリー**
- **モデルが選択したアクション (Action)**
- **ツールへの入力 (Tool Input)**
- **ツール出力のサマリー**
- **検証結果**
- **人間による承認記録**
- **次の状態の予測**

これは単に「思考過程」を展示するためではなく、システムの挙動をデバッグするために不可欠です。なぜ Agent が特定のステップをスキップしたのか、なぜ同じ検索を繰り返したのか、あるいはなぜテストを実行しなかったのかを、トレース (Trace) から特定できるようにします。

## 承認は単なるポップアップではない

承認の仕組みは、リスクレベルに基づいて設計されるべきです。読み取り専用の検索は自動許可で問題ありませんが、機密ファイルの読み取りには確認を求め、ファイルの書き込み、メール送信、発注、データの削除といった高リスクな操作には必ず明示的な承認を必須とします。高リスクなアクションでは、変更の差分 (Diff)、実行の目的、理由、およびロールバック方法を提示する必要があります。

優れた承認ノードは、人間に「Agent が何をしようとしているのか」を推測させるのではなく、判断のための明確な材料を提供します。承認画面は少なくとも以下の問いに答えるべきです：「何をしようとしているか」「なぜそれが必要か」「影響範囲はどこまでか」「実行しなかった場合どうなるか」。

## リプレイで問題を再現可能にする

Agent のバグ修正において最も困難なのは「再現性の欠如」です。リプレイ (Replay) 機能があれば、ある実行時の入力、ツールの結果、モデルの設定、プロンプトのバージョン、および状態遷移を完全に保存できます。これにより、実際の外部システムを再度呼び出すことなく実行を再現し、どの段階で挙動が悪化したのかを正確に特定できます。

また、リプレイは評価 (Evaluation) にも活用できます。過去の成功・失敗のトレースを回帰テストセット (Regression Set) とし、プロンプトやツール、モデルを変更した際に再実行することで、システムの劣化（デグレード）を即座に検知できます。

## 停止条件は重要な安全機構

長時間のタスクを扱う Agent には、明確な停止条件が不可欠です：最大ステップ数、最大コストの上限、連続失敗回数、新しい情報が得られない回数、ユーザー入力待ち、リスクレベルの上昇、または目標の完了。停止条件のない Agent は「自動化」ではなく、制御不能な無限ループに陥るリスクを孕んでいます。

## 実験目標

本実験の核心は、高性能な Agent を構築することではなく、Agent の外側を支える「実行環境」を設計することにあります。最終的な成果物には以下の要素を含めます：

- **Trace Schema** (トレース・スキーマ)
- **ツール権限表**
- **承認マトリクス** (Approval Matrix)
- **Replay Fixture** (リプレイ用のテストデータ)
- **故障注入 (Fault Injection)** のサンプル

これらが整備されていない状態では、Agent の成功も失敗も「魔法」のように見えてしまいます。Harness の価値は、その魔法を検査可能な「エンジニアリング・プロセス」へと還元することにあります。

## Trace Schema

まずは JSONL 形式を採用し、1ステップにつき1行のログを記録するようにします。

```json
{
  "run_id": "run_001",
  "step": 3,
  "goal": "記事の Frontmatter を修復する",
  "state_summary": "2つの欠損フィールドを発見",
  "action": "read_file",
  "tool_input": {"path": "src/content.config.ts"},
  "tool_output_summary": "Schema の読み取りに成功",
  "approval": "auto_readonly",
  "status": "ok",
  "next": "Patch を生成する"
}
```

最終的な回答だけを記録するのではなく、中間ステップこそを重視します。特にツールの選択、ツールへの入力、および状態の更新内容は、デバッグにおいて最も重要な情報となります。

## 承認マトリクス (Approval Matrix)

承認レベルは以下の4段階に分類できます。

| レベル | アクションの例 | ポリシー |
| --- | --- | --- |
| **L0** | 公開インデックスの読み取り、ディレクトリ一覧の取得 | 自動許可 |
| **L1** | 一般ファイルの読み取り、読み取り専用のチェック実行 | 自動許可または簡易通知 |
| **L2** | ファイルの書き込み、Patch 生成、高コストなコマンド実行 | 人間による確認 |
| **L3** | 削除、コミット・プッシュ、メール送信、外部有料 API の呼び出し | 厳格な承認と影響範囲の表示 |

マトリクスは各ツールと紐付けるべきです。モデルはアクションを「要求」することはできますが、それを「許可」するかどうかは常に Harness 側が決定します。

## Replay Fixture

リプレイファイルには、ユーザーの依頼内容、プロンプトのバージョン、モデルの設定、各ステップのツール出力、承認の決定内容、および最終結果を保存します。これにより、外部システムに再度アクセスすることなく、特定の実行プロセスを完全に再現できます。

リプレイデータは評価 (Eval) の貴重なソースとなります。手作りのベンチマークよりも、実際の失敗トレースの方がはるかに価値があります。開発中や運用中に発生した失敗を、そのままリプレイ可能なサンプルとして蓄積していきましょう。

## 故障注入 (Fault Injection)

堅牢性を高めるため、最低でも以下の5つのパターンをシミュレートします。

1. **ツールが空の結果を返す**
2. **ツールの呼び出しがタイムアウトする**
3. **モデルが権限のないツールを要求する**
4. **連続するステップで新しい情報が得られない**
5. **書き込み直前の Diff が目標と一致しない**

各パターンの失敗に対し、再試行 (Retry)、ユーザーへの確認 (Ask User)、停止 (Stop)、エスカレーション (Escalate)、またはロールバック (Rollback) のいずれかの明確な処理へ移行するように設計します。失敗後に Agent が「独自の判断」で処理を続行し、制御不能になる状態を回避します。

## チェックリスト

- [ ] 各ステップに一意の `run_id` と `step` 番号が付与されているか。
- [ ] ツール呼び出しの直前に適切な権限チェックが行われているか。
- [ ] 承認画面は、アクションの内容、理由、および影響範囲を明示しているか。
- [ ] トレースログのみから、その時点のシステム状態を再構築できるか。
- [ ] 外部への副作用なしにリプレイを実行できるか。
- [ ] 最大ステップ数、コスト上限、および連続失敗回数の制限が設定されているか。

## 実施ガイダンス

まずは、ファイル編集 Agent の Harness について「ペーパーデザイン（設計図）」を作成してみましょう。モデルの実装は後回しで構いません。ツールセット、権限規則、ログのスキーマ、承認戦略、およびリプレイ形式を定義します。その後、実際のタスクを一つ選び、手動でトレースログを1行ずつ書いてシミュレーションを行います。このプロセスを通じて、どのような状態情報が欠けているかが明確になるはずです。

設計が完了したら、トレース・スキーマと承認マトリクスをプロジェクトドキュメントとして保存します。将来的に OpenAI Agents SDK、Claude Code、ADK、あるいは独自のループ実装のどれを採用したとしても、この Harness の設計思想は共通して活用できます。
