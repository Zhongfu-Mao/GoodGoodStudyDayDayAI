# 構造化出力が解く問題

LLM の出力が、後続のコード、データベース、自動化ワークフロー、あるいは UI 表示に組み込まれる場合、自然言語の曖昧さは大きな障害となります。システムが必要とするのは、確定的なフィールド、正確な型、厳密な列挙値（Enums）、そして予測可能なエラー状態です。構造化出力の目的は、単に「見た目が JSON である」ことではなく、**プログラムがその出力を安全かつ安定して消費できること**にあります。

エンジニアリングにおける典型的な失敗は、モデルが JSON を全く生成できないことではなく、境界条件で発生する小さなズレにあります。例えば、余計な説明文が混ざる、必須フィールドが欠落する、列挙値のスペルミス、数値が文字列として出力される、あるいは「答えがない」場合に無理やりもっともらしい値を捏造するといったケースです。これらは人間には些細なミスに見えても、プログラムにとっては致命的なエラー、あるいは静かに汚れたデータを蓄積させる原因となります。

## 出力契約（Output Contract）の定義

**まず Schema を書き、その後に Prompt を書きます**。Schema は業務上の境界を明確に表現する必要があります。

- どのフィールドが必須（Required）か。
- どのフィールドが Null を許容するか。
- 定義された列挙値（Enums）は何か。
- 配列の最大長はいくつか。
- 文字列の最大文字数はいくつか。
- 証拠不足などでタスクを完了できない場合、どう明示するか。

Schema に `status`（ステータス）や `confidence`（置信度）のような失敗を表現する項目がないと、モデルは不確かな入力に対しても、すべてを「成功」の結果として無理やりパッケージングしようとする傾向があります。

## 再試行（Retry）は単なる繰り返しではない

効果的な再試行には、具体的なエラーフィードバックを伴わせる必要があります。例えば、最初の出力に `source_url` フィールドが欠けていた場合、2回目のプロンプトは「前回の JSON 出力は検証に失敗しました。理由は `source_url` フィールドが欠落しているためです。修正した JSON のみを出力し、余計な説明は省いてください」と具体的に指示すべきです。単に同じリクエストを繰り返すのは、乱数に頼って運試しをしているに過ぎません。

また、再試行には必ず上限を設けます。上限を超えた場合は、直ちに「人間による確認待ち」としてマークする、失敗サンプルを保存する、あるいは保守的なデフォルト値を返すといった降格（Fallback）経路へ移行します。

## 修復戦略の階層化設計

効率を最大化するために、復旧プロセスを以下の3つのレイヤーに分けます。

1. **解析前のクレンジング（Pre-processing）**：Markdown のコードブロック（Code Fences）や前後の不要な説明文、不可視文字を自動的に取り除きます。
2. **決定的検証（Deterministic Validation）**：標準的な JSON パーサーと Schema バリデータを用い、フィールド、型、列挙値の整合性を判定します。
3. **モデルによる修復（Model-aided Repair）**：具体的なエラー内容と元の誤った出力をモデルに返し、形式の修正のみを行わせます。タスク全体を最初から再実行させる必要はありません。

この階層化により、単純な形式エラーで高価なフルモデル呼び出しを浪費することを防ぎ、複雑な論理エラーに対しても追跡可能な復旧経路を確保できます。

## 実験の目標

この実験のゴールは、単に「JSON を返してもらう」ことではなく、**レジリエンス（回復力）を備えた構造化出力のパイプライン**を構築することです。完了時には以下の成果物が得られるようにします。

- 厳密に定義された JSON Schema。
- 独立した決定的バリデータ（Validator）。
- 形式修復に特化した Retry Prompt。
- 典型的な異常ケースを含む失敗サンプル集。
- 初回通過率および修復成功率のレポート。

題材としては、**「Markdown 記事からのメタデータ抽出」**が適しています。実記事を入力とし、サイトのビルドフローに直接投入可能なオブジェクトを出力させます。Schema エラーがビルド失敗に直結するため、より厳格な業務境界の設計が求められます。

## Schema 設計のポイント

堅牢な Schema は、少なくとも「成功（ok）」、「要確認（needs_review）」、「処理不能（error）」の3つのステータスをサポートすべきです。

```json
{
  "status": "ok | needs_review | error",
  "title": "AI Developer Core：構造化出力、Retry、Recovery",
  "category": "engineering",
  "difficulty": "intermediate",
  "tags": ["AI Developer Core", "Structured Output"],
  "summary": "簡潔な一文要約",
  "risks": []
}
```

すべてのフィールドを自由記述（Free-text）にしないことが重要です。`category` や `status` は列挙型にし、`tags` の数や `summary` の長さには上限を設けます。`risks` は空配列を許容しますが、データ構造上の省略は禁止します。Schema が厳格であるほど、モデルによる形式エラーと、実務上の判断ミスを明確に区別できるようになります。

## 修復プロンプト（Retry）の設計

修復フェーズのプロンプトは、修復のみに極限まで集中させます。

```text
前回の出力は JSON Schema 検証に失敗しました。
エラー詳細：フィールド difficulty の値 "medium" は、定義された列挙値 [beginner, intermediate, advanced] に含まれていません。
修正した JSON オブジェクトのみを返してください。解説は不要です。
```

修復を試みてもなお失敗が続く場合は、速やかに処理を中止し、人間による介入フローへ移行します。無限リトライは避けてください。構造化出力システムで最も制御不能になりやすいのは、形式の修復が新たな「生成タスク」に化けてしまい、本来の意味から逸脱していくケースです。

## 重要な失敗パターンの観察

実験を通じて、以下の4つの失敗カテゴリを重点的に記録・観察してください。

- **構文エラー**：出力が JSON の文法に従っていない。
- **Schema エラー**：JSON の文法は正しいが、型や列挙値が定義と異なる。
- **業務ロジックエラー**：JSON は正しいが、抽出された内容が不正確、あるいは要約が不適切。
- **指示汚染エラー**：入力記事に含まれる悪意ある指示（プロンプトインジェクション等）によって出力形式が乱される。

前者の2つはエンジニアリング手法で自動解決可能ですが、後者の2つは評価（Eval）や人間によるレビューが不可欠です。これらを混同すると、「表面上の成功率」は高くても、実用的な品質が伴わないシステムになってしまいます。

## チェックリスト

- Schema に「失敗状態」の明示的な定義が含まれているか。
- バリデータはモデルのロジックから完全に独立しているか。
- 再試行回数は最大1〜2回に制限されているか。
- 修復用プロンプトは、業務ロジックの再実行ではなく形式修正に特化しているか。
- 失敗サンプルごとに、元の出力とエラー内容が保存されているか。
- 業務フローに投入されるオブジェクトは、すべて決定的検証を100%通過しているか。

## 試してみること

記事メタデータ抽出器を実装し、20本の正常な記事と、フロントマターを意図的に壊した5本の異常な記事でテストを行います。**「初回成功率」「修復後の成功率」「人間による介入が必要だった件数」**を集計してください。

レポートは単なる数字だけでなく、「どのフィールドが壊れやすいか」「タグ生成のハルシネーション率はいくつか」「形式は正しいが意味が間違っているケースはないか」を深掘りしてください。構造化出力の真の難しさは JSON の形式ではなく、そのオブジェクトが正しい業務上の意味を保持しているかどうかにあります。
