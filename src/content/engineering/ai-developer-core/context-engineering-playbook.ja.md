# Context Engineering とは

プロンプトエンジニアリング（Prompt engineering）が「タスクの伝え方」に注目するのに対し、コンテキストエンジニアリング（Context engineering）は「モデルがタスク実行時に何を見るべきか」に焦点を当てます。RAG、エージェント、コード支援、長文処理などの高度なタスクでは、単一のプロンプトよりも、文脈の選択・整理・更新戦略が最終的な品質を左右します。

どれほど強力なモデルであっても、古いステータス、重複した資料、無関係なログ、矛盾する指示、あるいは出典不明の検索結果を渡されれば、その出力は不安定になります。

## 6つの基本動作

第一に、**選択**。すべての情報をウィンドウに詰め込んではいけません。現在の判断に必要な情報のみを厳選し、古い履歴はステータスの要約（State Summary）へと変換します。

第二に、**圧縮**。長大な文書、ツール実行結果、会話履歴は適切に圧縮します。ただし、事実、決定事項、今後の予定、リスク、出典（Citations）などの重要情報は確実に保持し、単なる自然文の要約に留めないことが肝要です。

第三に、**整理**。目標、制約、入力、証拠（Evidence）、ツール結果、出力形式を明確に分離します。役割の異なる情報を一つの段落に混ぜてはいけません。

第四に、**キャッシュ**。変更のない長大な文脈はキャッシュ（Cache）を活用し、繰り返し発生するタスクではプロンプトのバージョンや検索結果を再利用します。キャッシュはコスト削減だけでなく、出力の変動を抑える効果もあります。

第五に、**隔離**。外部文書、Web、メール、ツール実行結果には、信頼できない指示（Prompt Injection 等）が含まれている可能性があります。これらはあくまで「データ」として扱い、システム指示（System Instructions）と混同されないよう構造的に隔離します。

第六に、**評価**。文脈戦略は定量的に比較可能でなければなりません。Top-k 数、要約方式、履歴の保持期間などを変更するたびに、同じタスクセットで回帰テストを行い、品質の変化を測定します。

## エージェントにおける文脈

エージェントの文脈は動的に増大します。ツールの呼び出しは新たなテキストを生み、失敗はログを蓄積させます。適切な状態管理（State Management）がなければ、エージェントは自らが生み出した履歴の海に溺れてしまいます。

より優れた方法は、以下のような構造化されたステータス（State）を維持することです。

```json
{
  "goal": "記事のメタデータを修復する",
  "done": ["スキーマを読み込んだ", "3件の欠損箇所を特定した"],
  "next": "フロントマターを修正する",
  "risks": ["本文の内容は変更しない"],
  "evidence": ["src/content.config.ts"]
}
```

モデルにはすべての過程を見せるのではなく、次の判断を下すために必要な「現在の状態」のみを提示すれば十分です。

## 実験の目標

この実験では、2つの文脈戦略を比較します。「全履歴をそのまま蓄積する戦略」と「構造化されたステータスを更新し続ける戦略」です。目的はどちらかが常に正しいと証明することではなく、どの情報を原文のまま残し、どの情報をステータスへと圧縮し、どのタイミングで再検索を行うべきかという判断基準を養うことにあります。

以下の4つの要素を成果物として残します。

- 2種類のプロンプト/コンテキスト・テンプレート
- 構造化ステータスのスキーマ（Schema）
- 多段階タスクの実行サンプル
- トークン数、失敗率、手動修正回数の比較データ

## Context Packet

各ステップでモデルに渡す情報を「コンテキスト・パケット（Context Packet）」として整理します。

```yaml
goal: 10本の記事から拡張可能なテーマを抽出する
constraints:
  - 原文を変更しない
  - 公開可能なテーマのみを抽出する
state:
  done:
    - 記事一覧を読み込んだ
  open_questions:
    - どのテーマを実装実験に回せるか
evidence:
  - title: AI Radar Daily 2026-04-20
    path: src/content/radar/daily-ai-radar-2026-04-20.md
    note: LLM 最適化スタックの情報を含む
output_contract:
  format: markdown_table
```

重要なのは、文脈の役割を明確に分けることです。モデルは目標（Goal）、制約（Constraints）、状態（State）、証拠（Evidence）、出力契約（Output Contract）を独立して認識します。長い会話履歴をただ漠然と読み進めるのではありません。

## 対照実験

対照 A：過去の全メッセージと全ツール実行結果を毎回すべて送信する。  
対照 B：構造化ステータス、必要な証拠、直近のツール結果のみを送信する。

同じタスクを5回実行し、入力トークン数、出力の重複、制約の不履行、手動修正の回数を比較します。全履歴送信は設計が容易ですが、高コストでノイズが蓄積しやすい傾向があります。構造化ステータスは設計コストがかかりますが、リプレイ（Replay）や評価（Eval）に適しています。

## 失敗のパターン

コンテキストエンジニアリングの失敗は、モデルの性能不足よりも、コンテキスト・パケットに必要な要素が欠けていることに起因する場合が少なくありません。

- **目標（Goal）の欠如**：モデルは単に続きを書くだけになります。
- **制約（Constraint）の欠如**：モデルは不必要に範囲を広げてしまいます。
- **証拠（Evidence）の欠如**：モデルは自らの記憶（学習データ）に基づいたハルシネーションを起こします。
- **状態（State）の欠如**：モデルは同じ作業を繰り返してしまいます。
- **出力契約（Output Contract）の欠如**：後続の工程へデータを渡せなくなります。

これら5つの項目に立ち返って確認することは、プロンプトを長くするよりも遥かに効果的です。

## チェックリスト

- このステップに原文が必要か、それともステータスだけで十分か。
- ツール実行結果は「信頼できないデータ」として適切に扱われているか。
- 完了事項（Done）、次工程（Next）、リスク（Risks）は明示されているか。
- 同じステータスを用いて、現在のステップを再現（Replay）できるか。
- 圧縮前後のトークン数の差を記録しているか。
- 戦略の変更を比較するための評価（Eval）指標を持っているか。

## 試してみること

「10本の記事からテーマを抽出し、要約を作成する」という多段階タスクを題材に選びます。全履歴をチャットに積む方式と、各ステップで構造化ステータスを更新する方式を実装し、トークン数、失敗率、一貫性を比較してください。

最後に `context_state.json` と `context_packet.md` を保存します。この2つは、将来エージェント・ハーネス（Agent Harness）を構築する際の重要な出発点となります。
