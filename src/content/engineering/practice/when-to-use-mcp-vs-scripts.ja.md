# MCP が必要な時、スクリプトで十分な時：AI ツール接続の判断基準

> 時点メモ：この記事は 2026-05-11 に確認した情報を前提にしています。MCP specification、Codex の MCP 設定、remote MCP tool、各クライアントの権限モデルは変化が速いため、実装前には公式ドキュメントを再確認してください。

MCP は「AI がツールを使うための標準プロトコル」と説明されがちです。正しい説明ですが、実務ではもう一段具体的に考える必要があります。その能力は、一回限りのスクリプトでよいのか、プロジェクト内の共通ラッパーにするのか、CLI や関数ツールで十分なのか、それとも MCP Server にするべきなのか。

すべてを MCP にすると、schema、認証、サービス運用、バージョン、エラー分類、権限説明が必要になります。逆にすべてをスクリプトのままにすると、Agent は毎回コマンドを読み、引数を推測し、出力を解釈し直すことになります。

![スクリプトから MCP への判断パス](/images/engineering/practice/mcp-vs-scripts-decision.svg)

## ツール接続は四つに分ける

一つ目は一回限りのスクリプトです。個人、低頻度、低リスクの作業に向いています。Markdown の frontmatter を検査する、特定 API の結果を一時的に CSV にする、といった用途です。

二つ目はプロジェクト内の共有ラッパーです。同じリポジトリで繰り返し使う処理に向いています。入力と出力を固定し、テストとログを持たせれば、自動化からも安全に呼べます。

三つ目は CLI または関数ツールです。検索、読み取り、生成、検証、変換のように、一回の明確な操作をモデルに渡す場合に向いています。軽い一方で、複数クライアントでの発見や権限管理は限定的です。

四つ目が MCP Server です。複数の Agent やクライアントから長期的に使う能力を、発見可能で構造化されたインターフェースとして提供したい時に向いています。

## 判断表

| 判断項目 | スクリプト寄り | MCP 寄り |
| --- | --- | --- |
| 頻度 | たまに手動実行 | 高頻度、長期、定期実行 |
| 利用者 | ひとり、単一リポジトリ | 複数人、複数 Agent |
| 権限 | ローカルで制御可能 | 認証、認可、監査が必要 |
| 入出力 | 人が読めればよい | schema が必要 |
| 失敗処理 | 人が判断できる | エラー種別と回復策が必要 |
| バージョン | 変更に気づきやすい | 互換性が必要 |
| 発見方法 | 文書や履歴 | クライアントが自動発見 |

一項目だけ MCP 寄りでも、すぐに MCP 化する必要はありません。少なくとも三つ以上が MCP 寄りなら、設計を始める価値があります。

## MCP の見えにくいコスト

MCP Server はコードではなく境界です。ツール名、説明、引数 schema、戻り値、認証、タイムアウト、ログ、バージョン、クライアント設定、降級方法を決める必要があります。

危ないのは、広すぎる能力をそのまま MCP にすることです。`execute_sql` はデータベース操作をほぼ丸ごと渡してしまいます。一方で `list_recent_orders(status, limit)` は能力を狭く保てます。MCP は安全性を自動で作るものではなく、安全な境界を表現する場所です。

そのため MCP と Skills は相性がよい組み合わせです。MCP は能力のインターフェースを提供し、Skill はいつ、どの順序で、失敗したらどうするかを説明します。

## MCP にしない方がよいケース

一回しか使わない、入出力がまだ変わり続けている、既存のプロジェクト内スクリプトで十分に検証できている、権限モデルが未定、任意 shell や任意 SQL を薄く包んでいるだけ。このような場合は MCP 化を急がない方が安全です。

特に最後のケースは注意が必要です。無制限の能力を MCP に包んでも、安全な能力にはなりません。むしろリスクが公式な顔をしてしまいます。

## MCP を検討すべきサイン

- 複数の Agent やクライアントが同じ能力を必要としている。
- ツールを prompt に埋め込むのではなく、実行時に発見させたい。
- 入出力が schema で表現できるほど安定している。
- 認証、認可、監査、データ境界が要件に含まれている。
- 失敗結果をモデルが解釈できる形で返したい。
- 特定の Harness からツール能力を切り離したい。

OpenAI Responses API では web search、file search、computer use、code interpreter、remote MCP が agentic loop の道具として扱われています。ツール抽象は重要になりますが、その分だけ境界設計も重要になります。

## 安定した導入順

最初はスクリプトで実タスクを通します。次にプロジェクト内の共有ラッパーにし、固定引数、固定出力、テスト、失敗コードを整えます。最後に、高頻度で安定し、複数クライアントに提供したいものだけ MCP に上げます。

この順序なら、「今日少し自動化したい」が、いつの間にか「保守が必要な小さなプラットフォーム」になる事故を避けられます。

## レイヤーモデル：一時的な操作からプロトコル化された能力へ

ツール接続は、スクリプトか MCP かの二択ではなく、四つの層で考えると判断しやすくなります。

第一層は個人操作です。特定ディレクトリの Markdown を一度だけ検査する、画像サイズを一覧化する、公開ページを一時的に読み込む、といった作業です。この層の品質は、再利用性ではなく、読めること、消せること、必要なら再実行できることです。個人操作をチーム API のように扱わないことが大切です。

第二層はリポジトリ内自動化です。処理は `scripts/`、テスト、コンテンツ生成パイプラインに入り、複数回使われます。引数、出力、失敗コード、最小テストが必要ですが、利用者はまだ主にそのリポジトリのメンテナーです。このサイトのソース確認、Radar 生成、画像資産チェックはこの層に近いものです。

第三層は Agent tool です。モデルが直接または Harness 経由で使うため、出力は解釈しやすく、エラーは次の行動を促せる必要があります。関数ツールでも CLI wrapper でも構いません。重要なのは、危険な能力を広く渡すのではなく、具体的な操作に狭めることです。

第四層がプロトコルサービスです。MCP Server は、ツールを発見可能にし、説明可能にし、複数クライアントから接続できるようにします。認証、監査、バージョン、権限もインターフェースの一部になります。社内ナレッジ、チケット、デザイン資産、デプロイ基盤、データ検索のように、長く使う能力群に向いています。

良い実務判断とは、能力をちょうどよい層に置くことです。低すぎると Agent は毎回使い方を推測し、高すぎると安定していない要求のためにプラットフォーム運用コストを払うことになります。

## 実践パス：このサイトの出典確認を例にする

たとえば「工程実践シリーズ」の公式情報を確認する作業を考えます。最初はスクリプトで十分です。URL を受け取り、ページタイトル、本文の要約、更新日らしき情報、引用できるリンクを Markdown で出す。目的は、実ページが取得しやすいか、ブラウザレンダリングが必要か、人の確認が必要な箇所はどこかを見つけることです。

同じ処理が繰り返されるなら、リポジトリ内の共通ラッパーにします。URL リストを入力し、source inventory を出力し、失敗時には `network_error`、`render_required`、`paywall_or_login`、`not_official_source` のように分類します。この段階ではまだ MCP でなくてよいでしょう。利用場所がこのサイトのコンテンツパイプラインに閉じているからです。

複数の Agent が同じ能力を必要とし始めたら、Agent tool として切り出します。記事を書く Agent、出典を校正する Agent、公開前 QA をする Agent が、同じ「公式ソース取得」「参照 URL 検証」「リンク確認」を使うなら、狭い tool 名と構造化された戻り値が必要になります。

さらに Codex、Claude Code、Gemini CLI、社内 Web UI など複数クライアントに提供したいなら、MCP Server の意味が出ます。Server は tool list、input schema、structured result、error classification、audit log を提供し、Skill は「どの順序で確認し、曖昧な情報をどう書くか」を説明します。

この流れでは MCP を軽視していません。むしろ、MCP に載せる価値のある能力を、先に実タスクで磨いてからプロトコル化しています。

## 反パターン：早すぎるプロトコル化、遅すぎる統制

早すぎるプロトコル化では、要求がまだ動いているのに server 名、transport、tool naming、deploy 方法を先に決めてしまいます。結果として、正式に見えるが安定して使われない MCP Server が残ります。schema は毎週変わり、クライアント設定はコピーされ、エラー処理は自然言語の補足に頼ることになります。

遅すぎる統制では、すでに複数 Agent がスクリプトを呼び、外部システムを読み書きし、公開や請求に影響しているのに、README と暗黙の引数しかありません。問題が起きた時、前回どの版を使い、どの引数を渡し、出力を誰が確認したか分かりません。

もう一つの罠は、MCP を安全な外皮だと思うことです。任意 shell、任意 SQL、任意ブラウザ操作を一つの MCP tool に包んでも安全にはなりません。プロトコル化すると、能力はむしろ見つけやすく、呼びやすくなります。安全は、狭い tool、明確な schema、最小権限、承認、ログから生まれます。

設計に迷ったら、次の問いを使います。明日、別のクライアントがこの tool に接続しても、私的な説明なしに何ができ、何ができず、失敗時にどうすればよいか分かるか。分からないなら、まだ共通ラッパーまたは関数ツールの段階です。

## 現在観測できる状態と確認方法

2026-05-11 時点で、MCP 公式仕様の Tools ページは、server が公開し、モデルまたはクライアントが呼び出す能力として tool を説明しています。tool には name、description、`inputSchema` があり、`outputSchema`、structured result、error marker、安全上の推奨も扱われます。クライアント側では、どの tool が AI に公開されているかをユーザーに示し、敏感な操作には確認を置くことが推奨されています。

OpenAI Responses API の文書でも、remote MCPs、web search、file search、computer use、code interpreter などが agent-like な流れの中で扱われています。今後、Agent workflow ではツール能力の組み合わせがより重要になります。ただしこれは、すべての自動化をすぐ MCP にするという意味ではありません。安定した能力のインターフェース設計が重要になる、という意味です。

実装前には三つを確認します。MCP specification の現在版で tools/list、tools/call、structuredContent、error handling、security considerations が変わっていないか。利用するクライアントの MCP 設定で、local server、remote server、認証、承認モデルがどう扱われるか。最後に、対象プラットフォームが remote MCP をどうサポートし、呼び出しログや制限をどう扱うか。

変化があった場合は、「この tool は常にこう動く」と書くのではなく、「現時点ではこう観測でき、確認するにはここを見る」と書く方が長持ちします。技術記事では、この書き方が読者の自己防衛にもなります。

## チェックリスト

- その能力は二つ以上のワークフローで使われているか。
- 引数と戻り値は schema 化できるほど安定しているか。
- エラーは分類できるか。
- 権限は元システムより狭くなっているか。
- 複数クライアントから自動発見する必要があるか。
- テストが破壊範囲を確認しているか。
- Skill やドキュメントで使い方の順序が説明されているか。
