# AI 搜索与浏览器自动化：从发现线索到可引用证据

> 时效边界：本文核验于 2026-05-11。OpenAI Responses API 已把 web search、file search、computer use、code interpreter 和 remote MCP 等能力放进统一的 agent-like 接口；Playwright、Chrome DevTools、浏览器插件和各类 AI 搜索产品也在快速变化。本文重点讨论工程流程，而不是某个工具的永久排名。

做 AI 工具研究时，最常见的问题不是找不到信息，而是找到了太多“像信息的东西”。搜索结果、聚合摘要、社交媒体截屏、文档旧版本、博客复述、产品页宣传、API 参考、GitHub README，都可能混在一起。

AI 搜索和浏览器自动化的价值，是把“我好像看到过”变成“我能说明事实来自哪里、何时核验、谁可以复查”。它们不是替代证据链，而是帮助建立证据链。

![AI 搜索与浏览器自动化证据链](/images/engineering/practice/search-browser-verification-pipeline.svg)

## 搜索负责发现，不负责定案

搜索工具擅长发现候选线索：某个产品是否发布、官方文档可能在哪、相关新闻是否存在、社区是否有使用反馈。它的输出通常是入口，不是结论。

尤其是时间敏感内容，不能只看搜索摘要。摘要可能混合旧信息和新信息，搜索结果排序也可能被 SEO、地理位置、个性化和缓存影响。对于 API 参数、价格、模型能力、法律政策、产品限制，搜索只能告诉你去哪里看，不能替你完成核验。

一个稳妥流程是：先用搜索缩小范围，再打开官方页面或原始来源，最后把结论写成“截至某日，官方文档显示……”而不是“网上说……”。

## 浏览器自动化负责确认真实页面

浏览器自动化适合处理搜索不能保证的事情：页面是否真的可访问，内容是否由 JavaScript 渲染，按钮状态是否变化，登录态下看到什么，图片是否加载，移动端布局是否重叠，下载链接是否工作。

Playwright 这类工具的优势是可复现。它可以固定 viewport、截图、录 trace、检查 selector、模拟点击。Chrome 插件或真实浏览器自动化的优势是能使用用户现有登录态和扩展环境。两者不是互相替代，而是服务不同层级。

如果目标是公开事实核验，优先官方文档和公开页面。如果目标是本地产品 QA，浏览器自动化就必须进入真实页面，检查真实 DOM、真实资源、真实截图。

## 证据链要保存四类信息

第一类是来源。最好是官方文档、规格、代码仓库、发布公告、价格页。聚合文章可以作为发现入口，但公开结论最好回到原始来源。

第二类是时间。文章里要写核验日期，尤其是模型、价格、API、权益、限制。来源清单也要有更新时间。

第三类是边界。哪些结论来自官方，哪些是从文档推断，哪些是实践经验，哪些可能因地区、账号、计划、权限不同而变化。

第四类是可复查材料。对于网页 QA，可以保留截图、trace、URL、命令输出摘要。对于内容文章，可以保留 source inventory。对于代码任务，可以保留测试命令和 build 结果。

## 不同工具的使用位置

| 能力 | 最适合 | 不适合 |
| --- | --- | --- |
| AI 搜索 | 找线索、找官方入口、确认是否有近期变化 | 直接当事实来源 |
| Web 抓取 | 读取静态页面、RSS、公开正文 | 处理复杂登录态和动态交互 |
| 浏览器自动化 | 真实渲染、点击、截图、登录态 QA | 大规模无节制抓取 |
| Computer use | 操作无法 API 化的桌面或网页 UI | 替代稳定 API |
| MCP 工具 | 把稳定外部能力结构化暴露给 Agent | 包装任意高风险操作 |

这张表的重点不是工具强弱，而是把发现、确认、执行、交付分开。

## 写作中的使用方法

写一篇 AI 工具档案，可以按下面顺序做：

1. 用搜索找到官方文档、发布公告、价格页和代码仓库。
2. 打开官方页面核对当前能力、限制、日期和示例。
3. 对社区经验只做补充，不把它当作官方承诺。
4. 把所有来源放进 `_sources` 或参考清单。
5. 正文写出时效边界和容易过期的部分。
6. 对关键页面做一次人工或浏览器截图 QA。

这能避免文章变成链接堆，也能避免把搜索摘要误写成事实。

## 站点 QA 中的使用方法

对本站这种静态站点，浏览器自动化更像发布前检查。构建通过不代表页面可读。还要看封面图是否加载、标题是否换行正常、移动端是否溢出、SVG 是否显示、内部链接是否带对 base path。

这里可以用 Playwright 截图，也可以用浏览器插件目视检查。关键是不要只相信代码意图。读者看到的是渲染结果，不是 frontmatter。

## 常见反模式

第一种是“搜索摘要即事实”。尤其在产品限制和价格上，这是最容易出错的做法。

第二种是“只抓 HTML 不看页面”。很多现代页面依赖 JavaScript、地区、登录态或实验开关。抓取成功不代表用户可见。

第三种是“截图没有上下文”。截图要能对应 URL、时间、viewport 和测试目的，否则只能当装饰。

第四种是“引用过多但无判断”。来源多不等于准确。准确来自优先级、交叉验证和边界说明。

## 分层模型：搜索、抓取、浏览器、证据、发布

可以把研究流程拆成五层，避免把工具能力混在一起。

第一层是搜索层。它负责发现候选入口，特别是当你不知道官方文档在哪里、产品是否改名、价格页是否迁移、GitHub 仓库是否存在时。搜索层的产物是候选 URL 和问题清单，不是最终结论。

第二层是抓取层。它负责读取公开页面、RSS、Markdown、API 文档或仓库文件，把原始材料转换成可处理文本。抓取层适合低交互、低风险、可重复的资料收集，但要尊重 robots、频率和站点负载。

第三层是浏览器层。它负责确认真实渲染和交互状态。很多事实只有浏览器能确认：图片是否加载、按钮是否禁用、移动端是否遮挡、登录态是否改变内容、文档是否由客户端渲染。Playwright 的截图和 trace 适合做可复现证据，真实 Chrome 自动化适合检查用户登录态和插件环境。

第四层是证据层。它把来源、日期、截图、trace、摘录边界、命令结果和推断说明组织起来。没有证据层，搜索和浏览器只是“看过”；有证据层，读者和维护者才能复查。

第五层是发布层。它把证据写成读者能理解的结论，同时删掉内部噪音。文章里不需要展示所有抓取日志，但需要说明时效边界、官方来源优先级和不确定结论的复核方法。发布层的责任是让内容既准确又可读。

这五层对应不同失败模式。搜索失败会漏线索，抓取失败会丢正文，浏览器失败会误判页面，证据失败会无法复查，发布失败会让读者被内部过程淹没。

## 实战路径：AI 工具档案如何核验

写一篇关于 AI 工具的深度文章，可以从问题清单开始，而不是从工具名字开始。比如研究 GPT-image-2，问题应该包括：当前官方能力是什么，支持哪些 API 路径，价格如何计算，是否支持编辑和参考图，哪些参数变化快，哪些能力与账号、地区或产品界面有关。

第一步用搜索找到官方文档、价格页、发布公告和 API 参考。搜索结果只负责找到入口，不直接写进正文。第二步打开官方页面，核对能力、参数、限制和示例。第三步做小规模真实实验，例如生成一张封面、调整质量参数、记录耗时和成本感受。第四步把变化快的信息写成“截至 2026-05-11，官方文档显示……；复核时请查看……”。第五步再补社区经验，但明确它只是实践反馈。

浏览器自动化进入两个位置。研究阶段，它可以帮助检查官方页面是否真的包含某段内容、价格页是否变化、文档页面是否需要脚本渲染。发布阶段，它可以打开本站最终页面，确认封面图、SVG、表格、长标题、移动端段落和内部链接都能正常显示。

如果需要引用截图，截图必须带上下文。至少要知道 URL、时间、viewport、测试目的和页面状态。没有这些信息，截图很容易从证据退化成装饰。

## 反例陷阱：搜索摘要、无上下文截图与无节制抓取

搜索摘要最大的风险，是它看起来像答案。对于“最新模型”“当前价格”“CLI 是否支持某功能”这类问题，摘要可能已经过期，也可能把多个产品线混在一起。正确做法是把摘要当作路标，然后回到官方页面和原始仓库。

无上下文截图也很危险。截图显示一个按钮存在，但不说明用户是否登录、账号是否有权限、页面是否在实验开关下、截图是否来自移动端或桌面端。截图要成为证据，必须和 URL、时间、viewport、步骤绑定。

无节制抓取则是工程伦理和稳定性问题。为了写一篇文章而高频抓取站点，既不必要，也可能给对方造成负担。能用官方文档索引、Markdown、RSS 或 API 时，不要用浏览器模拟大量页面访问；需要浏览器时，也要限制频率和范围。

还有一种隐蔽反例，是把社区经验写成官方事实。社区经验很有价值，尤其能暴露真实使用中的坑，但它应该被标注为经验观察。比如“有用户反馈某参数效果不稳定”不同于“官方限制是某参数不稳定”。前者是线索，后者需要官方依据或自己的可复现实验。

## 当前可观察状态与复核路径

截至 2026-05-11，OpenAI Responses API 文档把 web search、file search、computer use、code interpreter、remote MCPs 等工具列为统一接口下的能力，并强调多轮、工具调用和多模态支持。Playwright 官方文档提供截图能力和 trace viewer：截图可以保存页面、整页或元素；trace viewer 可以查看动作、DOM 快照、console、network 和错误信息。

这给工程实践一个很清晰的分工：AI 搜索负责把候选信息找出来，浏览器自动化负责验证真实页面和交互状态，trace 和截图负责让 QA 可复盘，source inventory 负责让文章事实可复查。

复核时可以按三条线走。产品事实线：回到官方文档、价格页、API reference 和 GitHub release。页面事实线：用 Playwright 或浏览器打开最终页面，保存截图或 trace，确认读者实际看到的内容。写作事实线：检查正文是否明确区分官方事实、实验观察、社区经验和推断。

如果工具能力发生变化，不要只改一句“支持/不支持”。应该同时更新来源清单、时效边界、文章正文和检查清单。变化快的内容最好给出复核路径，而不是让读者相信某个静态结论会长期有效。

## 真实实验：本站发布前的页面 QA

本站的工程实践专题不仅是 Markdown 文件。读者看到的是 Astro 构建后的页面，所以最后必须做页面 QA。一个可执行流程是：先跑内容检查，确认 frontmatter、内部链接和类型没有问题；再跑构建，确认静态页面生成；最后用浏览器打开桌面和移动端页面。

页面 QA 不只看“能打开”。要看封面图是否出现，SVG 是否有合适尺寸，长表格是否横向溢出，日文标题是否断行自然，移动端目录是否遮挡正文，代码块和列表是否把段落挤坏。对于图文并茂的文章，还要检查图片是否真的服务于理解，而不是只占位置。

Playwright 的价值在于可重复。可以固定几组 viewport，给代表性页面截图；如果失败，trace 能告诉你是 selector、资源、网络还是布局问题。人工目视仍然重要，因为“技术上可见”和“读起来舒服”不是同一件事。最稳的做法，是把自动截图作为第一道门，把人工快速浏览作为最后一道门。

对于双语站点，还要把语言差异纳入 QA。中文长句和日文假名汉字混排的换行方式不同，同一个卡片在两种语言下可能出现完全不同的密度。只检查中文页面，会漏掉日文标题溢出；只检查桌面，会漏掉移动端表格和图片说明的挤压。真正的浏览器验证，应该覆盖代表性语言和代表性 viewport。

最后还要把 QA 结果反馈回写作流程。如果截图显示表格过宽，就应该改正文结构或拆表；如果移动端封面压迫正文，就应该调整图片比例或页面组件；如果日文页面密度过高，就应该重写段落，而不是只调 CSS。浏览器自动化的意义不是制造一张漂亮截图，而是让内容、布局和资产形成闭环。

因此，截图不应该被看作最后的附件，而应该被看作内容编辑的一部分。它提醒作者：读者消费的是页面，不是 Markdown 源码。

## 查缺补漏清单

- 是否把搜索结果和事实来源分开？
- 是否优先打开官方页面或原始来源？
- 是否写明核验日期？
- 是否区分官方事实、推断和实践经验？
- 是否保留可复查 URL、截图、trace 或来源清单？
- 是否用真实浏览器验证了读者会看到的页面？
- 是否避免把浏览器自动化变成无节制抓取？
