# AIエンジニアリング実践マップ：モデル、ツール、プロトコル、Agent、ワークフローを分けて考える

> 時点メモ：この記事の製品情報は 2026-05-11 に確認しました。Codex、Claude Code、Gemini CLI、GPT-image-2、MCP クライアントの仕様や料金は変わりやすいため、実装前には公式ドキュメントで再確認してください。

AIの失敗は、よく「モデルが弱い」という言葉に集約されます。出力が不安定なら強いモデルに替える。Agent が変なツールを呼ぶなら prompt を長くする。画像生成の費用が読めないなら価格表を眺める。どれも一部は正しいのですが、多くの場合、問題は別の層にあります。

必要なのは、MCP、Skills、Agent、RAG、Evals、構造化出力、ブラウザ自動化、画像生成を同じ平面で比べることではありません。まず「この失敗はどの層で起きているのか」を見分けることです。

![AI エンジニアリング実践レイヤーマップ](/images/engineering/practice/ai-engineering-layer-map.svg)

## 1. タスクとユーザーワークフロー

最上位にあるのはモデルではなくタスクです。入力、出力、誰が確認するのか、失敗したらどう戻すのか。ここが曖昧なままでは、どれだけ良いモデルを使っても作業は揺れます。

たとえば「GPT-image-2 を整理する」だけでは実践タスクとして弱いです。「公式ドキュメントと現在の料金を確認し、能力、制限、API例、失敗例、再確認方法、画像ワークフローを含む日中両言語の記事を作る」と書くと、初めて検収可能になります。

## 2. コンテキストと知識

AIの品質は、モデルだけでなくコンテキストで大きく変わります。現在のコード、過去の判断、公式ドキュメント、料金ページ、失敗履歴、公開してはいけないローカル情報。これらをどう選ぶかが重要です。

全部を詰め込むとノイズになります。逆に、記憶だけで変化の速い事実を答えると古くなります。API、料金、制限、モデル名は、記事を書く日に再確認する対象です。一方で、権限境界、検証、ロールバックといった設計原則は長く使えます。

## 3. ツール、プロトコル、Skills

ツール層は外部能力をモデルに渡す場所です。ただし、渡すべきなのは無制限の権限ではなく、絞られた能力です。MCP、関数ツール、スクリプト、ブラウザ、メール、ファイルシステム、画像生成 API はすべて境界設計の対象です。

MCP の価値は「ツールを増やすこと」ではなく、ツールを自己記述的にし、入力と出力を構造化し、認証と権限を扱いやすくすることにあります。Skills の価値も長い prompt ではなく、繰り返し使う作業手順をトリガー、手順、資料、スクリプト、検証として残せることです。

## 4. Agent Harness

Agent Harness はモデルの外側にある実行環境です。いつ読むか、いつ書くか、いつ承認を求めるか、いつ止めるか、何をログに残すか、失敗をどう再現するかを決めます。

長い作業ほど Harness が重要になります。記事生成なら、どのソースを確認したか、どの画像を作ったか、どのファイルが対象か、どのユーザー変更を触ってはいけないかを管理する必要があります。コード作業なら、ブランチ、テスト、diff、ロールバックが必要です。

## 5. 評価と運用

最後の層は公開後の運用です。記事には事実確認があり、コードにはテストと CI があり、画像には視覚 QA と権利確認があります。自動化には失敗通知、Agent には回放可能なログと回帰セットが必要です。

ここがないと、改善は感覚になります。特に AI ツール記事では、どの情報が古くなりやすいか、読者がどこで再確認できるかを書いておく必要があります。

## このマップの使い方

新しい要件に出会ったら、次の順で確認します。

1. タスクに検収基準はあるか。
2. コンテキストは新しく、追跡可能で、過剰ではないか。
3. 必要なのは一回限りのスクリプトか、MCP ツールか、Skill か。
4. Agent には承認、ログ、停止条件、回放が必要か。
5. 完了後にどう検証し、公開し、更新するか。

この順番を守るだけで、モデルの問題ではないものをモデルで解決しようとする無駄が減ります。

## 実践パス：曖昧な要件を五層に分ける

たとえば「工程実践セクションを体系的に補う。MCP、Skills、Agents、AI ツールを含め、画像も入れ、正確で新しくする」という要件を考えます。一文としては自然ですが、実際には五つの層が混ざっています。

タスク層では、成果物を決めます。何本の記事か、どのテーマか、中国語と日本語を同期するか、長さの基準は何か、画像は何枚必要か、どの検証を通すか。ここが曖昧だと、Agent は目次だけ作って終えることも、無限に広げることもあります。

コンテキスト層では、何を根拠にするかを決めます。公式文書、既存の AI Developer Core、`.codex/AGENTS.md`、公開ルール、画像ディレクトリ、build command は重要です。コミュニティ情報は発見には使えますが、公式根拠の代わりにはしません。

ツール層では、どう実行するかを決めます。Markdown は patch で編集し、事実は公式資料で確認し、カバーは画像生成で作り、正確な図は SVG にし、ページは build と screenshot で確認します。

Harness 層では、実行を安全にします。branch、dirty file、分割編集、`npm run check`、dev server、Playwright の権限などを管理します。これは記事本文ではありませんが、納品品質を左右します。

運用層では、最後に監査します。長さ、構造、日本語同期、画像表示、build、未完了項目の報告を確認します。この層まで通って初めて「完了」と言えます。

## 反例：層を混ぜる

一つ目は、コンテキスト不足をモデル不足と誤解することです。記事の情報が古いなら、より強いモデルではなく、公式情報の再確認が必要です。

二つ目は、タスク不明確をツール不足と誤解することです。「深さが足りない」は、MCP を追加する問題ではなく、長さ、構造、読者体験の基準が足りない問題かもしれません。

三つ目は、検証不足を prompt 不足と誤解することです。Agent が build を忘れるなら、prompt を長くするより、Skill やチェックリストに検証を入れる方が安定します。

四つ目は、運用不足を一回の努力で解決しようとすることです。記事が一度良くても、source inventory、画像命名、内部リンク、日本語同期、build 検証が続かなければ維持できません。

五つ目は、概念だけで終えることです。MCP、Skills、Agent という言葉は便利ですが、読者が必要なのは、いつ使うか、どう落とすか、どこで失敗するか、どう確認するかです。

## 現在観測できる状態と確認方法

2026-05-11 時点で観測できる大きな流れは、主要プラットフォームが model、tool、protocol、filesystem、browser、long-running task、skill、automation を Agent Harness として束ね始めていることです。OpenAI Responses API は web search、file search、computer use、code interpreter、remote MCP、image generation を同じ tool framework で扱います。Codex Skills は progressive disclosure によって再利用 workflow を管理します。MCP specification は tool discovery、call、schema、structured result、security considerations を定義しています。

ただし具体機能は変わりやすいので、この記事では永久結論にはしません。確認する時は、公式文書で現在の model、tool、protocol、price、permission を見ます。次に小さな実タスクで tool call、失敗、検証を記録します。最後に安定した経験を記事、Skill、AGENTS.md、test に残し、変わりやすい情報は「確認日 + 再確認方法」として書きます。

この地図自体も固定ではありません。新しい tool や model が出た時は、まず五層のどこを変えるのかを確認します。モデルだけが変わるのか、tool interface が変わるのか、Harness の承認やログが変わるのかを分けると、流行に引っ張られずに更新できます。

個人で読む時も同じです。新しい AI 製品を見たら、すぐ導入可否を決めるのではなく、どの層の問題を解いているかを言語化します。文章生成なのか、外部 tool なのか、browser QA なのか、workflow memory なのか。層が分かると、既存の仕組みと置き換えるべきか、補完するべきかが見えます。

## 読者向けセルフチェック

チームで「AI が不安定」と感じたら、次を確認します。

タスク層：検収基準はあるか。失敗時の戻し方はあるか。人間の確認が必要な操作は明示されているか。

コンテキスト層：公式情報は最新か。公開内容と非公開資料を分けているか。出典を追跡できるか。

ツール層：tool は広すぎないか。schema、error type、output truncation、permission level はあるか。

Harness 層：log、approval、stop condition、replay はあるか。ユーザーの未提交変更を守っているか。

運用層：test、build、screenshot、QA、source inventory、更新計画はあるか。

答えられない層が、次に補う場所です。すぐに「モデルを変える」と考えない方が、結果的に早く安定します。

## 例：同じ失敗を五層で直す

「Agent が記事を書いたが、品質が足りない」という失敗を考えます。五層で見ると、修正方法は変わります。

タスク層の問題なら、長さ、必要な章、核心テーマ、日本語同期、画像、検証を明文化します。基準がなければ、Agent は「十分深い」を推測するしかありません。

コンテキスト層の問題なら、公式文書、価格ページ、既存実践、古くなった結論を補います。新しい事実がなければ、正確な記事は書けません。

ツール層の問題なら、長さは `wc -m`、公式確認は docs、ページ確認は screenshot のように、判断を支える道具を使います。

Harness 層の問題なら、何本ずつ編集するか、どの command を走らせるか、dirty file をどう守るか、いつ止まるかを決めます。

運用層の問題なら、prompt-to-artifact checklist を作り、要求をファイル、章、command、screenshot に対応させます。

このように、実践マップは概念図ではなく、失敗時の診断道具です。

## 保守パス：マップをプロジェクト資産にする

マップは記事に書くだけでは弱いです。タスク層は issue template や品質基準に、コンテキスト層は `_sources` や用語表に、ツール層は script、MCP、browser QA command に、Harness 層は `AGENTS.md` や Skill に、運用層は CI、checklist、screenshot、completion audit に落とします。

これらがあると、次の Agent や人間は同じ背景を毎回説明されなくても動けます。工程実践の価値は、一回だけ良くすることではなく、次回をより簡単に正しくすることです。

## チェックリスト

- モデル問題とワークフロー問題を分けているか。
- 長い作業に検収条件があるか。
- 変化しやすい事実に確認日を書いているか。
- 公開記事とソースメモを分けているか。
- ツールは必要最小限の能力だけを公開しているか。
- 停止、ロールバック、人間の介入経路があるか。
- テスト、ビルド、事実確認、QA で公開可能性を示せるか。
