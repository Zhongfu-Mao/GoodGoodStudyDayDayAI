# AI 検索とブラウザ自動化：発見から引用できる証拠へ

> 時点メモ：この記事は 2026-05-11 に確認した情報を前提にしています。OpenAI Responses API は web search、file search、computer use、code interpreter、remote MCP などを agent-like な統一インターフェースに含めています。Playwright、Chrome DevTools、ブラウザ拡張、AI 検索製品も変化が速いため、ここでは工程の考え方に絞ります。

AI ツールを調べる時、難しいのは情報が見つからないことではなく、「情報に見えるもの」が多すぎることです。検索結果、要約、SNS のスクリーンショット、古い文書、ブログの再説明、製品ページ、API reference、GitHub README が混ざります。

AI 検索とブラウザ自動化の価値は、「どこかで見た気がする」を「どこに書かれていて、いつ確認し、誰が再確認できるか」に変えることです。

![AI 検索とブラウザ自動化の証拠链](/images/engineering/practice/search-browser-verification-pipeline.svg)

## 検索は発見、結論ではない

検索ツールは候補の発見に向いています。製品が発表されたか、公式文書がどこにあるか、関連ニュースがあるか、コミュニティで話題になっているかを探せます。

しかし時間に敏感な内容では、検索要約だけを根拠にしてはいけません。要約は古い情報と新しい情報を混ぜることがあります。検索順位も SEO、地域、個人化、キャッシュに影響されます。API パラメータ、価格、モデル能力、法務、製品制限では、検索は入口を示すだけです。

安定した流れは、検索で範囲を絞り、公式ページや原典を開き、結論を「何年何月何日時点で公式文書では」と書くことです。

## ブラウザ自動化は実ページの確認

ブラウザ自動化は、検索では保証できないことを確認します。ページが本当に開けるか、JavaScript で描画されるか、ボタン状態が変わるか、ログイン状態で何が見えるか、画像が読み込まれるか、モバイルで崩れないか、ダウンロードリンクが動くか。

Playwright の強みは再現性です。viewport、スクリーンショット、trace、selector、クリックを固定できます。実ブラウザや Chrome 拡張の強みは、ユーザーのログイン状態や拡張環境を使えることです。どちらが上ではなく、確認したい層が違います。

公開事実の確認なら、公式文書と公開ページを優先します。ローカル製品 QA なら、実際にレンダリングされた DOM、画像、スクリーンショットを見る必要があります。

## 証拠链に必要な四つの情報

一つ目は出典です。公式文書、仕様、コードリポジトリ、発表、価格ページを優先します。まとめ記事は入口として使えますが、公開結論は原典に戻すべきです。

二つ目は時点です。モデル、価格、API、権利、制限については記事内に確認日を書きます。

三つ目は境界です。公式事実、文書からの推論、実務経験、地域やアカウントやプランで変わる可能性を分けます。

四つ目は再確認材料です。Web QA ならスクリーンショット、trace、URL、コマンド結果の要約。記事なら source inventory。コードならテストと build 結果です。

## 能力ごとの使い分け

| 能力 | 向いていること | 向いていないこと |
| --- | --- | --- |
| AI 検索 | 手がかり、公式入口、最近の変化の発見 | そのまま事実根拠にする |
| Web 取得 | 静的ページ、RSS、公開本文 | 複雑なログインや動的操作 |
| ブラウザ自動化 | 実レンダリング、クリック、スクリーンショット、QA | 大量で無制限な取得 |
| Computer use | API 化できない UI 操作 | 安定 API の代替 |
| MCP tool | 安定した外部能力を構造化して Agent に渡す | 任意の高リスク操作を包む |

重要なのは、発見、確認、実行、納品を分けることです。

## 記事作成での流れ

AI ツールの記事を書くなら、まず検索で公式文書、発表、価格ページ、コードリポジトリを探します。次に公式ページを開いて、能力、制限、日付、例を確認します。コミュニティ経験は補助として扱い、公式の約束とは書きません。出典は `_sources` や参考リストに残し、本文には時点と古くなりやすい部分を明示します。

これにより、記事はリンク集ではなく、検証された整理になります。

## サイト QA での流れ

静的サイトでは、ブラウザ自動化は公開前チェックです。build が通っても、読者の画面が読みやすいとは限りません。カバー画像、改行、モバイル、SVG、内部リンク、base path を確認します。

Playwright のスクリーンショットでも、ブラウザ拡張での目視でも構いません。大切なのは、コードの意図ではなく、読者が見る結果を確認することです。

## よくある反パターン

検索要約をそのまま事実にすること。HTML を取得しただけでページ確認とみなすこと。URL、時点、viewport のないスクリーンショットを証拠扱いすること。引用が多いだけで判断がないこと。どれも、AI を使った調査で起きやすい失敗です。

正確さは情報量ではなく、優先順位、交差確認、境界説明から生まれます。

## レイヤーモデル：検索、取得、ブラウザ、証拠、公開

調査の流れは五つの層に分けられます。道具を混ぜると、どこで事実確認したのか分からなくなるからです。

第一層は検索です。公式文書がどこにあるか、製品名が変わったか、価格ページが移動したか、GitHub repository が存在するかを探します。検索層の成果物は候補 URL と確認すべき問いであり、結論ではありません。

第二層は取得です。公開ページ、RSS、Markdown、API docs、repository file を読み、処理しやすいテキストへ変換します。低インタラクションで再実行可能な資料収集に向いていますが、robots、頻度、相手サイトへの負荷を考える必要があります。

第三層はブラウザです。実際のレンダリングと操作状態を確認します。画像が表示されるか、ボタンが無効化されているか、モバイルで隠れないか、ログイン状態で内容が変わるかは、ブラウザで見ないと分かりません。Playwright の screenshot と trace は再現性が高く、実 Chrome 操作はログイン状態や拡張環境の確認に向いています。

第四層は証拠です。出典、確認日、スクリーンショット、trace、引用範囲、コマンド結果、推論の説明を整理します。この層がなければ、検索とブラウザ操作は「見た気がする」で終わります。

第五層は公開です。証拠を読者に伝わる結論へ変換し、内部ログや試行錯誤を整理します。公開記事にはすべての取得ログを載せる必要はありませんが、時点、公式出典の優先順位、不確実な情報の確認方法は必要です。

この分け方を使うと、検索漏れ、取得失敗、表示誤認、証拠不足、読みづらい公開文という異なる失敗を別々に扱えます。

## 実践パス：AI ツール記事をどう確認するか

AI ツールの記事を書く時は、名前からではなく問いから始めます。たとえば GPT-image-2 なら、現在の公式能力、API 経路、料金計算、編集や参照画像、変化しやすいパラメータ、アカウントや地域に依存する可能性を確認します。

最初に検索で公式文書、価格ページ、発表、API reference を探します。検索結果は入口であり、本文の根拠ではありません。次に公式ページを開き、能力、パラメータ、制限、例を確認します。さらに小さな実験を行います。実際にカバー画像を生成し、quality を変え、所要時間や費用感を記録する、といったものです。

変化しやすい内容は、「2026-05-11 時点で公式文書では」と書きます。読者が後で確認できるように、どのページを見るべきかも残します。コミュニティの経験は最後に補足として扱い、公式の約束とは分けます。

ブラウザ自動化は二箇所で使います。調査段階では、公式ページが本当にその記述を含むか、価格ページが変わっていないか、JavaScript rendering が必要かを確認します。公開段階では、このサイトの最終ページを開き、カバー画像、SVG、表、長い見出し、モバイル表示、内部リンクを確認します。

スクリーンショットを証拠にするなら、URL、時点、viewport、目的、状態を一緒に残します。それがないスクリーンショットは、証拠というより装飾に近くなってしまいます。

## 反パターン：検索要約、文脈のないスクリーンショット、過剰取得

検索要約は、答えに見えることが最大の危険です。「最新モデル」「現在価格」「CLI がこの機能を持つか」のような問いでは、要約が古かったり、複数製品を混ぜたりします。要約は標識であり、結論は公式ページや原典で確認します。

文脈のないスクリーンショットも危険です。ボタンが存在しているように見えても、ログイン状態、アカウント権限、実験フラグ、モバイルかデスクトップかが分からなければ、証拠として弱いままです。スクリーンショットは URL、時点、viewport、手順と結びつけて初めて証拠になります。

過剰取得は、安定性と倫理の問題です。一つの記事を書くために高頻度でサイトを巡回する必要はありません。公式 index、Markdown、RSS、API があればそちらを使い、ブラウザが必要な時も範囲と頻度を絞ります。

コミュニティ経験を公式事実のように書くのも避けます。利用者の報告は実務上とても役立ちますが、「利用者がこう感じた」と「公式制限がこうである」は別です。前者は手がかり、後者には公式根拠または再現可能な実験が必要です。

## 現在観測できる状態と確認方法

2026-05-11 時点で、OpenAI Responses API 文書は web search、file search、computer use、code interpreter、remote MCPs を統一インターフェースの tool として扱い、multi-turn、tool call、multimodal support を説明しています。Playwright 公式文書では、ページ全体や要素の screenshot、そして action、DOM snapshot、console、network、error を確認できる trace viewer が説明されています。

ここから、工程上の役割分担が見えます。AI 検索は候補を見つける。ブラウザ自動化は実ページと操作状態を確認する。trace と screenshot は QA を復盤可能にする。source inventory は記事の事実を再確認可能にする。

確認は三本線で行います。製品事実は公式文書、価格ページ、API reference、GitHub release に戻ります。ページ事実は Playwright またはブラウザで最終ページを開き、スクリーンショットや trace を残します。文章事実は、公式事実、実験観察、コミュニティ経験、推論が区別されているかを確認します。

tool の能力が変わった時は、「対応 / 非対応」を一文だけ直すのではなく、source inventory、時点メモ、本文、チェックリストを一緒に更新します。変わりやすい情報は、静的な断言よりも確認方法を残す方が読者にとって安全です。

## 実験：公開前ページ QA

このサイトの工程実践シリーズは Markdown だけではありません。読者が見るのは Astro build 後のページです。最後には、content check、build、ブラウザ確認を通す必要があります。

ページ QA では「開ける」だけでは足りません。カバー画像が表示されるか、SVG のサイズが適切か、長い表が横にはみ出さないか、日本語タイトルが自然に折り返すか、モバイルで目次が本文を隠さないか、コードブロックやリストが段落を壊していないかを見ます。画像が理解を助けているかも確認します。

Playwright は再現性のために役立ちます。viewport を固定し、代表ページを screenshot し、失敗時には trace で selector、resource、network、layout のどこが原因かを見ます。一方で、人の目による最後の確認も必要です。技術的に表示されることと、読みやすいことは同じではありません。

## チェックリスト

- 検索結果と事実出典を分けているか。
- 公式ページや原典を開いているか。
- 確認日を書いているか。
- 公式事実、推論、実務経験を分けているか。
- URL、スクリーンショット、trace、source inventory を残しているか。
- 読者が見る実ページをブラウザで確認したか。
- ブラウザ自動化を無制限な取得に使っていないか。
