# Codex、Claude Code、Gemini CLI：不要比谁聪明，要比工作流

> 时效边界：本文核验于 2026-05-11。各 CLI 的模型、权限、插件、MCP、价格和速率限制更新很快，本文不做永久排名，只给工作流比较框架。

讨论 AI Coding Agent 时，最容易滑向一个问题：谁更聪明？这个问题有趣，但不够工程化。真实项目里，Agent 不只是回答问题，它会读仓库、改文件、跑命令、生成图片、访问浏览器、处理 Git，甚至触发外部系统。此时“聪明”只是基础，真正决定可用性的，是工作流。

同一个模型，如果没有明确的权限、日志、验证和回滚，仍然可能把事情做糟。一个稍弱的模型，如果被放进更稳的 Harness，也可能更适合团队项目。

![Agent CLI 工作流矩阵](/images/engineering/practice/agent-cli-workflow-matrix.svg)

## 四类任务，不要混在一起比较

第一类是读代码。目标是理解结构、定位风险、回答问题。这类任务要求上下文检索强，输出引用清楚，最好不要轻易改文件。

第二类是改代码。目标是实现小功能或修 bug。这类任务要求 patch 范围可控，能跑测试，能解释 diff，能避开用户已有修改。

第三类是长任务。目标可能是内容批量迁移、自动化搭建、跨文件重构、素材生成。它要求计划、状态管理、分批验证和中途恢复。

第四类是外部副作用。包括 push、发邮件、改日历、调用付费 API、删除资源、部署生产环境。这类任务默认需要审批和审计。

如果一个工具在读代码时表现很好，不代表它适合外部副作用。如果一个工具能快速改文件，也不代表它适合无人值守长任务。

## Codex 的优势场景

Codex 的强项在于工程执行环境：文件系统、shell、补丁、浏览器、Git、图片生成、MCP、技能和自动化可以形成一套较完整的工作台。对需要“读仓库、改文件、验证、生成资产、整理最终结果”的任务，它的工作流很自然。

但这也意味着 Codex 的质量高度依赖仓库规则。`AGENTS.md`、审批策略、sandbox、允许命令、分支习惯、验证命令都很重要。没有这些边界，能力越多，越需要约束。

## Claude Code 的优势场景

Claude Code 通常适合深度代码理解、重构讨论、较长上下文下的工程推理。它的价值不在于“替代所有工具”，而在于把复杂代码库里的意图、风险和修改路径讲清楚。

在使用时，重点应看它如何处理项目指令、权限、命令执行、MCP、slash commands、计划和 review。对于团队来说，Claude Code 也适合承担“先读懂，再建议”的角色，而不是每次都直接放手写入。

## Gemini CLI 的优势场景

Gemini CLI 的重要位置在于 Google 生态、开源仓库、Gemini 模型能力以及和 ADK / Google Cloud / Workspace 相关的实验路径。它适合用来观察 Google Agent 生态如何组织工具、上下文和命令行工作流。

如果任务依赖 Google Cloud、ADK、Gemini API 或 Workspace 资料，Gemini CLI 往往值得纳入比较。但同样不要只看模型回答，要看它的权限模型、工具配置、MCP 支持、日志和验证方式。

## 一个更实用的比较表

| 维度 | 应该问的问题 |
| --- | --- |
| 上下文 | 它如何读取仓库？如何避免塞入无关文件？ |
| 计划 | 它是否能先计划、分批执行、遇到歧义停下来？ |
| 修改 | 它如何展示 diff？能否避开用户未提交修改？ |
| 工具 | 它支持哪些本地命令、浏览器、MCP、插件或 Skills？ |
| 审批 | 写入、删除、push、发邮件、付费 API 是否有明确确认？ |
| 验证 | 它是否会跑测试、构建、UI QA，并读取结果？ |
| 恢复 | 长任务失败后，是否能从状态继续？ |
| 运营 | 能否沉淀为自动化、Skill、项目规则或 CI 守门？ |

## 官方资料应该怎么看

比较 Codex、Claude Code、Gemini CLI 时，不应该只看首页宣传，也不应该只看社交媒体 demo。更可靠的读法是拆成四类官方资料。

第一类是配置和权限文档。它告诉你工具如何限制文件系统、命令、网络、MCP、插件、hooks、项目级配置和用户级配置。比如 Codex 的 `config.toml` 里有 sandbox、approval policy、MCP server、skills、agents、web search 等配置面；Claude Code 文档也把 settings、permissions、sandboxing、hooks 和插件配置放在一起；Gemini CLI 的仓库文档则更适合观察它的命令、扩展和 Google 生态连接方式。配置文档比功能介绍更能暴露工具的工程边界。

第二类是工具调用文档。它回答 Agent 能不能访问 shell、浏览器、MCP、文件、搜索、IDE、GitHub、云服务，以及这些工具是否有确认提示、日志和可禁用开关。工具越多，越要看权限，而不是只看能力。

第三类是自动化和长任务文档。它回答任务能否恢复、是否支持非交互执行、是否有超时、是否能沉淀为 skill / command / hook / automation。一次对话里表现好，不等于能跑一夜；能跑一夜，也不等于失败后好恢复。

第四类是价格、速率和账号限制。模型、额度、计划、地区和组织策略变化很快，文章里不应该写成永久判断。更好的写法是：“截至某日，可观察到的官方配置面包括这些；具体模型和额度请按这个路径复核。”

## 分层模型：模型、Harness、项目规则、团队流程

AI Coding CLI 的能力可以分成四层。

模型层决定理解和生成能力。它影响代码推理、长上下文、语言质量和复杂问题分解。但模型层很少单独决定交付质量，因为工程任务还要读仓库、改文件、跑命令和处理失败。

Harness 层决定工具如何被使用。文件编辑是不是 patch 化？shell 是否 sandbox？危险命令是否审批？浏览器能不能截图？MCP 是否支持 allowlist？长任务是否有状态和日志？同一个模型放进不同 Harness，表现会非常不一样。

项目规则层决定 Agent 是否懂本地约束。`AGENTS.md`、测试命令、分支规则、发布红线、标签规范、内容风格、保密边界，都会影响结果。没有项目规则，Agent 只能按通用经验做事；有项目规则，它才能像团队成员一样工作。

团队流程层决定输出如何进入生产。是否需要 PR review？谁批准 push？失败是否会转成自动化 guardrail？重复任务是否沉淀为 Skill？如果团队流程缺位，再好的 CLI 也只能制造一次性的局部成果。

因此，工具选择不是“模型 A 还是模型 B”，而是“这四层哪一层最弱”。如果最弱的是项目规则，换模型没用；如果最弱的是验证，换 CLI 也没用；如果最弱的是外部权限边界，就先收紧审批。

## 实战路径：给一个任务选工具

假设任务是“给本站工程实践专题扩写 18 篇中日文章，并保证官方资料、图片、构建和目视 QA”。这不是普通聊天任务，它同时包含内容生产、事实核验、文件修改、图片资产、构建验证和浏览器检查。

第一步，先判断是否需要本地仓库能力。需要读写 Markdown、图片和 source inventory，就必须选择能安全操作本地文件的工具。

第二步，判断是否有外部事实。涉及 OpenAI、Anthropic、Google、MCP、Playwright，就必须能访问官方资料，且能在文章里写明核验日期和复核路径。

第三步，判断是否有资产生成。需要封面图，就要有图像生成能力或清晰的外部生成流程；需要精确图表，就要能编辑 SVG 或代码。

第四步，判断是否有验证。静态站点不能只写文件，还要跑 `npm run check`、带 base path 的 build，必要时用浏览器截图看真实页面。

第五步，判断是否有发布副作用。commit、push、PR、部署都属于更高风险动作。工具必须尊重审批边界，尤其是本仓库“未经确认不 push”的规则。

按这条路径看，Codex 适合作为主执行工具，因为它的本地文件、shell、图片生成、浏览器 QA 和 goal tracking 能连成闭环。Claude Code 可以适合作为深度审稿或重构建议工具。Gemini CLI 可以在 Google 生态、ADK 或 Gemini 相关资料上做交叉验证。这个结论不是永久排名，而是针对任务结构的选择。

## 反例陷阱：用一次演示给工具贴标签

第一个陷阱是 demo 偏差。一个工具在小仓库里 30 秒修好 bug，不代表它能处理脏工作树、长任务、发布红线和多语言内容。演示通常避开了权限、回滚、成本和失败恢复。

第二个陷阱是把“回答得好”当成“执行得好”。解释代码和修改代码是两类能力。修改代码还要尊重 diff、测试、格式、用户未提交修改和 CI。

第三个陷阱是忽略外部副作用。能自动发邮件、push、部署、删除资源的工具看起来强大，但如果没有审批和日志，团队会很难接受它进入生产流程。

第四个陷阱是用单一指标排名。速度、成本、上下文、模型质量、工具能力、权限、安全、可审计性之间会互相拉扯。个人探索阶段可以偏速度；团队生产阶段应偏可控和可回放。

第五个陷阱是忽略本地化和内容工程。一个工具能写英文技术说明，不代表能写适合日本读者的日文工程文章；能生成代码，不代表能生成发布级别的图片和页面排版。

## 团队落地：把比较结果变成规则

工具比较最终要回到团队规则，而不是停在“我喜欢哪个”。比较完以后，至少应该沉淀三类材料。

第一类是项目级说明。把仓库的发布红线、测试命令、分支策略、保密边界、内容风格写进 `AGENTS.md` 或等价文件。这样无论使用哪个 Agent，都先读同一套本地规则。

第二类是任务级 Skill。把重复工作流写成 Skill，例如内容扩写、发布前检查、图片资产生成、PR review、CI 修复。Skill 的价值是让工具差异变小：只要 Agent 能读懂并执行步骤，它就能进入稳定流程。

第三类是验证级 gate。把“感觉不错”改成命令和截图：`npm run check`、build、UI screenshot、链接检查、来源清单审计、diff 范围检查。工具可以换，gate 不要轻易换。

团队真正需要的不是一个永远最强的 CLI，而是一套能吸收工具变化的工作流。今天某工具强，明天另一个工具补上 MCP、浏览器或自动化能力，团队不必推倒重来；只要任务边界、项目规则和验证 gate 稳定，替换工具就像替换执行者，而不是重写工程制度。

还有一个很现实的落点：不要把所有工具都要求成“全能主力”。团队可以明确主执行工具、审稿工具、资料复核工具和一次性实验工具。这样既能利用不同生态的长处，又不会让每个项目成员在每次任务前重新比较工具。工具评估的终点，是减少选择成本。

## 当前可观察状态与复核路径

截至 2026-05-11，可观察到的稳定结论是：主流 AI Coding CLI 正在从“聊天式代码助手”转向“带工具、权限、项目规则和自动化能力的 Agent Harness”。但具体模型、价格、速率、插件、MCP 支持和权限默认值变化很快，不应写成永久结论。

复核时建议按这个顺序：

1. 查每个工具的官方设置/权限文档，而不是只看产品首页。
2. 查 MCP、hooks、plugins、skills、slash commands 或 extensions 的当前支持范围。
3. 在一个真实仓库里做同一任务：读代码、改一处文件、跑测试、处理失败、生成最终汇报。
4. 记录它是否尊重未提交修改、是否需要审批、是否能解释 diff、是否能恢复中断。
5. 最后再比较成本、速度和主观体验。

这样得到的结论会比“某工具更聪明”慢一点，但更能指导真实工程实践。

## 如何选择

个人学习阶段，可以选择一个主工具，再用另一个工具做 review。团队项目阶段，优先选择能稳定执行项目规则的工具。自动化阶段，重点不是交互体验，而是日志、恢复和失败通知。内容工程阶段，还要考虑图像、音频、浏览器和来源核验能力。

最稳的策略不是押注一个工具，而是把工作流写清楚。只要任务、边界和验证清楚，工具可以替换；如果这些不清楚，换工具只是换一种失败方式。

## 查缺补漏清单

- 是否把读代码、改代码、长任务和外部副作用分开评估？
- 是否为每类任务规定默认权限？
- 是否要求 Agent 在改文件前确认范围？
- 是否跑了真实测试，而不是只读了代码？
- 是否记录长任务状态，避免中途丢失？
- 是否把重复经验沉淀为 Skill 或 AGENTS.md？
- 是否避免用一次 demo 结果推导永久排名？
