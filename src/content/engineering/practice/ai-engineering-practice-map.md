# AI 工程实践地图：模型、工具、协议、Agent 与工作流怎么分层

> 时效边界：本文的产品事实核验于 2026-05-11。涉及 Codex、Claude Code、Gemini CLI、GPT-image-2、MCP 客户端能力和价格限制的细节，后续都应以官方文档为准。

很多 AI 工程问题看上去都像“模型不够聪明”。生成结果不稳定，是不是该换更强模型？Agent 乱调用工具，是不是 prompt 写得不够长？图像生成成本失控，是不是 API 价格太高？这些问题当然可能和模型有关，但更常见的情况是：我们把不同层的问题揉在一起了。

如果没有一张地图，MCP、Skills、Agents、RAG、Evals、结构化输出、浏览器自动化、图像生成工具都会变成一堆热词。真正可维护的 AI 工程实践，要先回答一个朴素问题：**这个系统失败时，应该改哪一层？**

![AI 工程实践分层地图](/images/engineering/practice/ai-engineering-layer-map.svg)

## 第一层：任务与用户工作流

最上层不是模型，而是任务。一个任务至少要说清楚四件事：输入是什么，输出是什么，谁来验收，失败后怎样恢复。没有这层，后面的技术都会漂。

例如“整理 GPT-image-2”不是一个足够工程化的任务。更好的表达是：基于官方文档、当前价格和真实使用场景，产出一篇可发布的双语长文，包含能力边界、成本估算、API 最小样例、失败案例、复核路径和图片工作流模板。这样一来，模型只是执行者之一，验收标准已经被人定义好了。

在团队里，这一层通常对应产品文档、编辑规范、PRD、任务卡、验收清单。个人项目里，它可以只是一个 Markdown，但也必须明确。否则 Agent 会把“尽量好”理解成无限探索，把“系统整理”理解成链接堆砌，把“发布”理解成马上推送。

## 第二层：上下文与知识

AI 结果差，很多时候不是模型弱，而是上下文不对。上下文包括当前代码、历史决策、官方文档、价格页、真实用户反馈、之前失败案例，以及哪些信息不能进入公开页面。

这层最容易犯两个错误。第一个错误是把所有资料一股脑塞进上下文。上下文越多不一定越好，模型会被噪声稀释。第二个错误是只靠记忆回答变化很快的问题，比如 API 参数、产品限制、价格和计划权益。对于这类内容，正确做法是把事实分成两类：长期稳定的工程原则，以及写作当天必须重新核验的产品事实。

本站已经有一个很好的本地实践：来源清单放在 `_sources`，读者页面写原创整理，不搬运原文。这让内容既能追溯，又不会变成资料复制。

## 第三层：工具、协议与 Skills

工具层负责把外部能力交给模型，但“交给模型”不等于“把系统权限交出去”。MCP、函数工具、脚本、浏览器、邮件、文件系统、日历、图片生成 API，本质上都是能力边界。

MCP 的价值不只是多一个协议。它让工具可以自描述，让输入输出可以结构化，让权限和认证有共同约定。Skills 的价值也不是把 prompt 写长，而是把可重复工作流沉淀成触发条件、步骤、脚本、参考资料和验证方式。

这一层的核心问题是：工具是否足够窄？输入是否足够明确？输出是否可检查？错误是否可分类？权限是否可以被 Harness 拦截？如果一个工具叫 `run_shell(command)`，它对模型来说几乎是无限自由；如果它叫 `list_recent_posts(category, limit)`，系统边界就清楚得多。

## 第四层：Agent Harness

Agent Harness 是模型外侧的执行壳。它决定什么时候读文件、什么时候改文件、什么时候需要审批、什么时候停止、日志记录什么、怎样回放一次失败。没有 Harness 的 Agent 是一段对话；有 Harness 的 Agent 才像一个可运营系统。

长任务尤其依赖 Harness。一个写文章 Agent 要知道哪些来源已经查过，哪些事实还没核验，哪些图片已经生成，哪些文件属于本轮任务，哪些用户修改不能碰。一个代码 Agent 要知道当前分支、测试命令、构建环境、diff 范围和回滚方式。

所以比较 Codex、Claude Code、Gemini CLI，不应该只问“谁更聪明”。更有用的问题是：它们各自如何处理计划、工具权限、上下文发现、文件修改、审批、并行、日志和验证。

## 第五层：评测与运营

AI 工程的最后一层不是上线，而是可持续运营。文章需要事实复核，代码需要测试和 CI，图片需要版权和视觉 QA，自动化需要失败告警，Agent 需要回放样本和回归集。

这层决定系统能不能长期存在。没有评测，prompt 的改进只是一种感觉；没有运营，工具能力会随着产品更新而慢慢失真。尤其是 AI 工具档案，价格、能力和限制变化很快，文章里必须写出“如何复核本文结论”，让读者知道哪些部分最容易过期。

## 如何使用这张地图

遇到一个新需求时，可以按顺序问：

1. 任务是否有清楚的验收标准？
2. 所需上下文是否新鲜、可追溯、不过量？
3. 需要的是一次性脚本、MCP 工具，还是可复用 Skill？
4. 这个 Agent 是否需要审批、日志、停止条件和回放？
5. 完成后怎样验证、发布、监控和更新？

如果答案卡在第一层，就不要急着写工具。如果答案卡在第二层，就先补来源和检索。如果答案卡在第三层，再考虑 MCP 或 Skills。如果答案卡在第四层，才讨论 Agent Harness。如果答案卡在第五层，说明你不是缺能力，而是缺运营纪律。

## 实战路径：把一个模糊需求拆成五层

假设需求是：“把工程实践部分系统补起来，包含 MCP、Skills、Agents、AI 工具，还要图文并茂、时效准确。”这句话听起来清楚，其实它同时包含五层。

任务层要先把“系统补起来”翻译成可验收产物：多少篇文章、哪些主题、中文和日文是否同步、每篇长度多少、是否需要图片、是否要构建验证。没有这一步，Agent 可能只写一个目录，也可能无限扩展。

上下文层要决定哪些资料进入判断。官方文档、仓库已有 AI Developer Core 内容、`.codex/AGENTS.md`、已有发布规则、图片资源目录、构建命令都属于上下文。社交媒体讨论可以帮助发现问题，但不能替代官方依据。

工具层要决定如何行动。需要读写 Markdown，就用文件和 patch；需要事实核验，就查官方文档；需要封面，就用图片生成；需要精确图解，就写 SVG；需要验证页面，就用 build 和浏览器截图。每个工具只解决自己的问题。

Harness 层要管理执行过程。比如先建分支、避开无关 dirty file、分批编辑、每批跑 `npm run check`、保留 dev server 状态、遇到 Playwright 沙箱问题按审批路径处理。这些不是文章内容，却决定任务能否安全完成。

运营层要做最后审计。文章是否达到长度、结构是否完整、日文是否同步、图片是否显示、构建是否通过、未完成项是否如实报告。只有这层通过，才可以说“完成”。

这就是地图的用法：不是把概念摆出来，而是用它拆任务、定位缺口、安排执行顺序。

## 反例陷阱：把层级混在一起

第一种陷阱是把上下文问题误判成模型问题。比如文章事实过期，不一定是模型不聪明，而是没有重新查官方资料。解决方法不是换模型，而是把“涉及产品能力必须重新核验”写进流程。

第二种陷阱是把任务问题误判成工具问题。用户说“深度不够”，不一定需要 MCP 或自动化，可能只是验收标准没有明确到长度、结构和读者体验。

第三种陷阱是把工具问题误判成 prompt 问题。Agent 总是忘记跑构建，不一定是 prompt 不够强，而是应该把构建命令放进 Skill 或发布前检查脚本。

第四种陷阱是把运营问题误判成一次性努力。一次文章写好不代表专题可维护。来源清单、图片命名、内部链接、标签分类、日文同步和构建验证都需要持续规则。

第五种陷阱是只做概念层内容。MCP、Skills、Agent 这些词读起来很现代，但读者真正需要的是“什么时候用、怎么落地、哪里会出错、如何复核”。地图如果不能指导行动，就只是概念海报。

## 当前可观察状态与复核路径

截至 2026-05-11，可观察到的 AI 工程趋势是：主流平台正在把模型、工具、协议、文件系统、浏览器、长期任务、技能和自动化组合成 Agent Harness。OpenAI Responses API 把 web search、file search、computer use、code interpreter、remote MCP 和 image generation 放进统一工具框架；Codex Skills 通过 progressive disclosure 管理可复用工作流；MCP specification 明确了工具发现、调用、schema、结构化结果和安全建议。

这些事实变化很快，因此本文不把具体产品能力写成永久结论。复核时应按三步走：

1. 打开对应官方文档，确认当前模型、工具、协议、价格和权限。
2. 在本仓库或一个小样例里跑真实任务，记录工具调用、失败和验证结果。
3. 把稳定经验写入文章、Skill、AGENTS.md 或测试，把变化快的信息写成“截至日期 + 复核路径”。

这比记住某个工具的当前功能更重要。工具能力会变，分层诊断方法可以留下来。

## 读者自测：你的系统卡在哪一层

如果团队经常说“AI 不稳定”，可以用这组问题自测。

任务层：每个请求是否有验收标准？有没有说明失败后怎么恢复？有没有说明哪些动作需要人工确认？

上下文层：事实是否来自最新官方资料？是否把私密材料和公开内容分开？是否能追溯来源？

工具层：工具是否过宽？是否有 schema、错误分类、输出截断和权限等级？是否把一次性脚本和长期 MCP 区分开？

Harness 层：执行过程是否有日志、审批、停止条件和回放？是否保护用户未提交修改？

运营层：是否有测试、构建、截图、人工 QA、source inventory、版本更新计划？

哪一层回答不上来，就优先补哪一层。不要直接跳到“换更强模型”。

## 案例：同一个失败在五层里的不同修法

以“Agent 写完文章后质量不够”为例，五层会给出完全不同的修法。

如果是任务层问题，修法是补标准：每篇目标字数、必须有哪几个章节、哪些主题算核心、日文是否同步、图片是否必需。没有这些，Agent 只能猜“足够长”和“足够深”是什么意思。

如果是上下文层问题，修法是补证据：官方文档在哪里、价格页是否最新、仓库已有实践怎么引用、哪些旧结论已经过期。模型没有拿到新事实，就不可能写出准确内容。

如果是工具层问题，修法是补工具：需要统计长度，就用脚本或 `wc -m`；需要核验官方资料，就用官方文档搜索；需要检查页面，就用浏览器截图。不要让模型凭感觉判断“应该够了”。

如果是 Harness 层问题，修法是补执行边界：每批改几篇、改完跑什么检查、如何处理无关 dirty file、什么时候停止、什么时候汇报。没有 Harness，长任务很容易在中途失去状态。

如果是运营层问题，修法是补审计：建立 prompt-to-artifact checklist，把每个要求映射到文件、章节、命令和截图证据。只有审计能防止“努力很多但没有达标”。

这个案例说明，AI 工程地图不是概念分类，而是故障诊断工具。失败时先定位层级，再选修法。

## 维护路径：把地图变成项目资产

一张地图如果只停留在文章里，价值有限。更好的做法是把它落实到项目资产。

任务层可以变成 issue 模板、goal 描述、内容质量标准。上下文层可以变成 `_sources`、术语表、官方资料索引。工具层可以变成脚本、MCP、浏览器 QA 命令。Harness 层可以变成 `AGENTS.md`、Skill、审批规则。运营层可以变成 CI、检查清单、发布前截图和完成审计。

当这些资产存在时，新人或 Agent 不需要重新理解所有背景，也不需要靠记忆复现流程。工程实践的目标不是让某一次任务做得漂亮，而是让下一次任务更容易做对。

## 查缺补漏清单

- 是否把“模型问题”和“流程问题”分开判断？
- 是否为每个长任务写出了验收标准？
- 是否标注了时间敏感事实的核验日期？
- 是否把公开内容和本地来源清单分离？
- 是否让工具只暴露必要能力，而不是任意系统权限？
- 是否有失败后的停止、回滚或人工接管路径？
- 是否能用测试、构建、事实抽查或人工 QA 证明结果可发布？
