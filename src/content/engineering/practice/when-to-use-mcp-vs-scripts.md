# 什么时候需要 MCP，什么时候只要脚本：AI 工具接入的取舍

> 时效边界：本文核验于 2026-05-11。MCP specification、Codex MCP 配置、远程 MCP 工具和各客户端权限模型仍在快速演进，落地前请复查官方文档。

MCP 很容易被讲成“让 AI 调工具的标准协议”。这句话没错，但不够工程化。真正要判断的是：一个能力到底应该是临时脚本、项目内封装、CLI 命令、函数工具，还是 MCP Server？

如果所有外部动作都直接升级成 MCP，团队会很快背上维护负担。你需要写 schema、处理认证、维护服务、管理版本、记录错误，还要解释每个工具的权限边界。反过来，如果所有能力都停留在脚本，Agent 每次都要重新读命令、拼参数、猜输出，长任务就会越来越脆。

![从脚本到 MCP 的判断路径](/images/engineering/practice/mcp-vs-scripts-decision.svg)

## 先把工具分成四种形态

第一种是一次性脚本。它适合单人、低频、低风险任务，比如把一批 Markdown 的 frontmatter 检查一遍，或者把某个接口结果转成临时 CSV。一次性脚本不需要被模型“发现”，只需要人知道怎么运行、失败后能重跑。

第二种是项目内共享封装。它适合重复出现但仍然只服务一个仓库的能力，比如本站的 `fetch-url.mjs`。它比临时脚本更稳定，有固定输入输出，也能被自动化复用，但它不一定需要成为一个协议服务。

第三种是 CLI 或函数工具。它适合明确的单次动作：搜索、读取、生成、校验、转换。函数工具可以直接暴露给模型，CLI 可以由 Harness 决定何时调用。它们的好处是轻，坏处是跨客户端复用和权限治理有限。

第四种才是 MCP Server。它适合把一组能力作为长期接口暴露给多个 Agent 或客户端。MCP 的价值在于工具自描述、结构化输入输出、可发现、可认证、可由客户端统一治理。换句话说，MCP 解决的是“能力产品化”的问题，不是“这次能不能跑通”的问题。

## 一个实用判断表

| 判断问题 | 更像脚本 | 更像 MCP |
| --- | --- | --- |
| 调用频率 | 偶尔手动运行 | 高频、长期、自动触发 |
| 使用者 | 单人或单仓库 | 多人、多客户端、多 Agent |
| 权限 | 低风险、本地可控 | 需要认证、授权、审计 |
| 输入输出 | 人读就够 | 需要稳定 schema |
| 失败处理 | 人可以现场判断 | 需要错误类型和恢复建议 |
| 版本 | 改坏了容易发现 | 需要兼容和迁移 |
| 发现方式 | 文档或命令历史 | 客户端自动发现工具 |

如果一行偏向 MCP，不代表必须升级。至少三行同时偏向 MCP，才值得开始设计协议化边界。

## MCP 的隐藏成本

MCP Server 一旦上线，就不只是代码。它会变成系统边界。你要决定工具名字、描述、参数 schema、错误返回、认证方式、超时策略、日志字段、版本兼容、客户端配置和降级路径。

很多失败不是协议问题，而是工具设计问题。一个叫 `execute_sql` 的工具会把数据库权限几乎全交出去；一个叫 `list_recent_orders(status, limit)` 的工具则把能力收窄到可审计范围。MCP 不会自动让工具安全，它只是给你一个可以表达安全边界的位置。

这也是为什么 MCP 和 Skills 经常需要配合。MCP 提供能力接口，Skill 提供工作流说明。比如 MCP Server 暴露 `fetch_source`, `extract_article`, `validate_links`，Skill 说明什么时候用这些工具、按什么顺序用、失败后如何降级、最后跑什么检查。

## 什么时候不要用 MCP

不要为了“看起来先进”而用 MCP。下面这些情况更适合脚本或普通封装：

1. 任务只有一次，结果可人工检查。
2. 输入输出还没有稳定，频繁变化会拖累 schema。
3. 能力只在一个仓库里使用，现有脚本已经有测试和日志。
4. 权限风险很高，但还没有明确的授权模型。
5. 工具本身是对任意 shell、任意 SQL、任意浏览器操作的薄封装。

最后一种尤其危险。把无限能力套进 MCP 并不会变成安全能力，只会把风险包装得更正式。

## 什么时候应该认真考虑 MCP

如果一个能力同时满足这些条件，就该进入 MCP 设计：

- 多个客户端或 Agent 都需要调用同一组能力。
- 工具需要在运行时被发现，而不是写死在 prompt 里。
- 输入输出已经足够稳定，可以用 schema 表达。
- 认证、授权、审计和数据边界是需求的一部分。
- 失败结果需要被模型理解，而不是只返回一段不可解析的 stderr。
- 团队希望把工具能力从某个具体 Harness 里解耦出来。

OpenAI Responses API 已经把远程 MCP、web search、file search、computer use、code interpreter 等工具放在同一类 agentic loop 里理解。这说明工具抽象会越来越重要，但也说明边界设计会越来越重要。

## 最小落地路径

比较稳的路径是三步。

第一步，先写脚本，把真实任务跑通。不要在需求还含糊时先设计协议。脚本阶段的目标是发现真实输入、真实错误和真实验收标准。

第二步，抽成项目内共享封装。给它固定参数、固定输出、测试样例和失败码。这个阶段最能暴露工具是否值得长期维护。

第三步，再升级为 MCP。把高频、稳定、可复用、可授权的能力做成工具，把工作流说明放进 Skill 或项目指南，把敏感操作交给 Harness 审批。

这条路径慢一点，但不会把“我今天需要自动化一下”过早变成“我现在要维护一个平台”。

## 分层模型：从临时动作到协议能力

可以把工具接入放在四层里看，而不是在“脚本”和“MCP”之间二选一。

第一层是个人动作层。这里的工具只需要服务一次明确任务，例如本地批量改 frontmatter、临时下载一个页面、把一个目录里的图片尺寸列出来。它的质量标准不是复用，而是可读、可删、可重跑。这个阶段最重要的是不要把个人动作伪装成团队接口。

第二层是仓库自动化层。脚本已经进入 `scripts/`、测试命令或内容流水线，被多人或多次任务复用。它要有参数说明、稳定输出、失败码和最小测试，但调用者仍然主要是本仓库的维护者。本站的内容抓取、雷达生成、图片资产检查，更接近这一层。

第三层是 Agent 工具层。工具开始被模型直接或间接调用，输出要能被模型解析，错误要能指导下一步。这个阶段可以是函数工具、CLI 包装，也可以是 Harness 内建能力。关键不是协议名称，而是工具是否把危险能力收窄成明确动作。

第四层才是协议服务层。MCP Server 让工具可发现、可描述、可由不同客户端连接，也让认证、审计、版本和权限成为接口的一部分。它适合长期维护的能力集合，例如公司内部知识库、工单系统、设计资产库、部署平台、数据查询服务。到了这一层，工具已经不只是“帮我做事”，而是团队的一段基础设施。

这四层没有绝对优劣。好的工程实践，是让能力停在刚好合适的层级。过低会让 Agent 每次都临时猜用法，过高会让团队为尚未稳定的需求支付平台成本。

## 实战路径：以本站内容生产为例

假设要做“工程实践专题”的资料核验。最开始，脚本足够了：给定 URL，抓取页面标题、正文摘要、更新时间和可引用链接，输出 Markdown 片段。这个阶段的目标是看真实网页是否容易抓、哪些站点需要浏览器渲染、哪些内容必须人工确认。

如果这个动作会反复出现，可以升级为仓库封装：统一输入 URL 列表，输出 source inventory，失败时标注 `network_error`、`render_required`、`paywall_or_login`、`not_official_source` 等类型。此时还不必做 MCP，因为调用者只是在本站内容流水线里复用它。

当多个 Agent 都需要这个能力，例如写文章的 Agent、校对来源的 Agent、做发布 QA 的 Agent 都要调用同一组“读取来源、抽取引用、验证链接、生成来源清单”能力，就可以进入工具层。工具名应该是 `fetch_official_source`、`validate_reference_url` 这种窄接口，而不是 `browse_anything`。

当这个能力不再只服务本站，而是希望 Codex、Claude Code、Gemini CLI 或内部 Web 控制台都能使用同一套 source verification 工具，MCP 才真正有意义。MCP Server 可以暴露工具列表、输入 schema、结构化返回、错误分类和审计日志。Skill 则描述工作流：先找官方来源，再核对时效边界，再把不确定信息写成“当前可观察状态 + 复核路径”。

这个例子里，升级顺序不是因为 MCP 不重要，而是因为 MCP 值得承载的是已经被验证过的能力。先让真实任务把接口打磨出来，再协议化，成本最低。

## 反例陷阱：过早协议化与过晚治理

过早协议化的典型表现，是需求还在变，团队已经开始争论 server 名字、transport、工具命名规范和部署方式。最后得到的是一个很正式但没人稳定使用的 MCP Server。schema 每周变化，客户端配置到处复制，错误处理靠自然语言补丁，维护者反而被协议细节拖住。

过晚治理则相反。脚本已经被多个 Agent 调用，已经会读写外部系统，已经影响发布或账单，但仍然只有一段 README 和一堆隐含参数。出了问题以后，没人知道上一次用的是什么版本、传了什么参数、输出是否经过校验。这时再补 MCP 或工具治理，成本会明显更高，因为你要同时清理历史行为和当前需求。

还有一种常见陷阱，是把 MCP 当作安全外壳。比如把任意 shell、任意 SQL、任意网页操作包装成一个 MCP 工具，然后认为“有协议就安全”。事实正好相反：协议会让能力更容易被发现和调用，如果能力本身没有收窄，风险会被放大。安全来自更窄的工具、明确的输入 schema、最小权限、审批和日志，不来自工具名称。

判断是否进入 MCP 设计时，可以问一个更硬的问题：如果明天另一个客户端接入这个工具，它是否能在不读你私下说明的情况下知道能做什么、不能做什么、失败后怎么办？如果答案是否定的，先回到仓库封装或函数工具，把行为收窄。

## 当前可观察状态与复核路径

截至 2026-05-11，MCP 官方规范的 Tools 页面把工具定义为由 server 暴露、由模型或客户端调用的能力；工具需要名称、描述、`inputSchema`，也可以有 `outputSchema`、结构化结果、错误标记和安全建议。规范同时强调客户端应该让用户知道暴露了哪些工具，并在敏感操作上保留确认能力。

OpenAI 的 Responses API 文档也把 remote MCPs、web search、file search、computer use、code interpreter 等能力放在统一的 agent-like 接口里描述。这说明未来的 Agent workflow 会越来越依赖“工具能力的可组合性”。但这不是说所有自动化都应该立即 MCP 化，而是说稳定工具的接口设计会越来越重要。

落地前建议复核三处官方资料。第一，MCP specification 当前版本，确认 tools/list、tools/call、structuredContent、error handling 和 security considerations 是否有变化。第二，所用客户端的 MCP 配置文档，确认本地 server、远程 server、认证和审批模型。第三，目标平台的工具调用文档，确认是否支持远程 MCP、是否有额外限制、是否会记录调用日志。

如果复核结果发生变化，文章里的永久结论不应该改成“某工具现在一定支持某能力”，而应该改成“当前可观察状态是……，复核方法是……”。这类写法比功能清单更耐用，也更符合真实工程实践。

最后还要把复核责任写进仓库流程。MCP 工具一旦被多个客户端使用，来源、版本、权限和失败样本就不应该只存在于某个人的聊天记录里，而应该进入 source inventory、Skill、AGENTS.md 或工具 README。协议化的真正收益，是让能力可以被团队接手。

## 查缺补漏清单

- 这个能力是否已经被至少两个工作流复用？
- 参数和返回值是否稳定到可以写 schema？
- 错误是否能分类，而不是只靠人读日志？
- 权限是否比原始系统能力更窄？
- 是否需要多个客户端自动发现同一工具？
- 是否有测试样例证明工具没有扩大破坏面？
- 是否有 Skill 或文档说明工具应如何组合使用？
