# 长任务 Agent 的边界：日志、审批、停止条件和回放

> 时效边界：本文核验于 2026-05-11。Codex、Claude Code、Gemini CLI、OpenAI Agents SDK 和各类自动化 Harness 的权限、并行、日志与审批能力都在演进，本文不做永久功能排名，只讨论长任务边界的工程原则。

长任务 Agent 最危险的误解，是把它当成“能聊更久的模型”。真正的长任务 Agent 不只是上下文更长，而是要能在复杂任务里持续前进，同时让人知道它做了什么、为什么做、什么时候需要停、失败后怎么接手。

这不是 prompt 能单独解决的问题。它属于 Harness：执行壳、工具系统、权限系统、日志系统、验证系统共同形成的边界。

![长任务 Agent 的边界循环](/images/engineering/practice/long-agent-boundary-loop.svg)

## 目标要可交付，不要只写方向

“整理工程实践专题”是方向。“新增中日同步文章、生成封面和 SVG、更新来源清单、跑检查和构建、保留无关 dirty file”才是可交付目标。

长任务开始时，Agent 必须知道验收物是什么。否则它会把探索当进展，把补充当完成，把局部通过当整体通过。目标最好同时包含产物、范围、验证和禁区。

产物是要生成什么文件。范围是哪些目录属于本次任务。验证是跑哪些命令、看哪些页面。禁区是哪些文件不能碰、哪些操作必须审批。

## 检查点让任务可恢复

长任务一定会遇到中断、上下文压缩、工具失败、构建失败、用户插话。没有检查点，Agent 只能凭记忆继续；有检查点，后续执行者可以从事实继续。

检查点不需要复杂。它可以是任务清单、已完成文件列表、生成资产路径、已核验来源、当前失败原因、下一步计划。关键是要让状态可读、可接手、可验证。

对于内容生产，检查点至少包括：哪些文章已写，哪些语言已同步，哪些图片已生成，哪些官方来源已核验，哪些页面已目视检查。对于代码任务，则包括：已修改模块、测试结果、未解决风险、无关脏文件。

## 审批不是打断，而是系统边界

长任务经常需要工具。读文件、写文件、跑测试、访问网页、生成图片、提交代码、推送远端、发送邮件，这些动作的风险不同。一个成熟 Harness 会把它们分成可自动执行、需自动审核、需用户确认、禁止执行几类。

审批的意义不是让 Agent 变慢，而是把不可逆动作从普通步骤里分离出来。比如本仓库规则明确：没有当前会话授权不能 `git push`。这不是流程繁琐，而是保护发布边界。

更细的审批还可以针对 MCP、浏览器、邮件、文件系统和 shell 命令。权限越接近外部世界，越需要有审计和确认。

## 日志要记录“可复盘事实”

长任务日志不是聊天记录的压缩版。它应该记录可复盘事实：读了哪些关键文件、用了哪些来源、改了哪些路径、跑了哪些命令、命令结果如何、哪些决策来自用户、哪些是假设。

好的日志能回答三类问题：

1. 如果结果错了，错在事实、判断、工具还是验证？
2. 如果要恢复，应该从哪个检查点继续？
3. 如果下次重复同类任务，哪些步骤可以变成 Skill 或脚本？

日志也要克制。公开文章里不应该出现内部抓取日志、失败备注、本地路径和工具细节；这些应该留在执行报告、source inventory 或本地工作记录里。

## 停止条件必须提前写出

长任务最需要的不是“永不放弃”，而是知道什么时候停。常见停止条件包括：

- 用户的新指令与原计划冲突。
- 出现破坏性操作，需要确认。
- 事实无法通过官方来源核验。
- 构建或测试失败，且失败原因不属于本次改动。
- 工作树有无关改动，继续会误伤。
- 生成内容达不到可发布标准，需要人工选择方向。

停止不是失败。它是把控制权交还给人，让系统不要在不确定中越走越远。

## 回放样本让改进变得真实

如果一个 Agent 工作流会反复运行，就应该保留回放样本。样本可以是一次成功任务、一次失败任务、一次用户中途改口、一次外部来源不可用、一次构建失败。

回放样本的作用是验证改进是否真的有效。你修改 prompt、Skill、MCP 工具或审批规则后，可以用旧样本重跑，观察是否更少误判、更快停止、更清楚汇报。

没有回放，Agent 改进很容易变成印象工程。一次表现好，不代表系统稳定；一次表现差，也不一定说明模型退化。样本能把感觉变成证据。

## 长任务 Agent 的最小工程标准

一个可运营的长任务 Agent，至少应该具备：

- 明确目标和禁区。
- 可恢复检查点。
- 工具权限和审批层级。
- 关键事实日志。
- 失败分类和停止条件。
- 完成前验证命令。
- 完成后差异范围报告。

模型越强，这些边界越重要。因为更强的模型更会主动推进，也更容易在没有边界时做出看似合理但越权的动作。

## 分层模型：目标、状态、权限、证据、交接

长任务可以拆成五层。每一层都要有可检查的边界，不能只靠模型“应该知道”。

第一层是目标层。它回答“完成时应该出现什么”。目标不能只写方向，而要写产物、语言、目录、长度、质量标准、验证命令和明确禁区。内容任务尤其需要把“写完”改成“达到哪些读者标准、有哪些来源、哪些页面可访问”。

第二层是状态层。它回答“现在做到哪里”。状态要能在上下文压缩、进程中断、用户插话后恢复。一个好的状态记录会列出已完成项、未完成项、当前失败、下一步和风险，而不是只说“继续处理中”。

第三层是权限层。它回答“哪些动作可以自动做，哪些动作必须确认”。读文件、写草稿、运行本地检查和浏览公开文档，风险不同；推送远端、删除文件、发送邮件、修改生产配置、调用付费 API，必须进入更高审批。

第四层是证据层。它回答“为什么相信结果”。证据可以是官方来源、命令输出、截图、trace、diff、构建日志、字数统计、链接检查。长任务不能只报告意图，因为意图无法证明页面真的可读、文章真的达标、测试真的通过。

第五层是交接层。它回答“如果我现在停下，别人怎么接手”。交接不是最后才写，而是贯穿任务。长任务越长，越需要把中间状态做成可读事实，否则下一轮只能重新探索。

这五层合起来，才是长任务 Agent 的工程边界。模型能力负责推理和生成，Harness 负责让推理落在可控轨道里。

## 实战路径：把长内容任务拆成可恢复批次

以本站专题建设为例，一个长任务常常同时包含资料核验、中文写作、日文改写、图片生成、内部链接、来源清单、构建和页面 QA。如果只给一句“把专题写好”，Agent 很容易先写几篇看起来不错的文章，然后漏掉长度、时效边界、日文同步或可视化验证。

更稳的做法，是把目标拆成可恢复批次。第一批建立目录、frontmatter、source inventory 和视觉资产，验证站点能识别新内容。第二批补齐中文核心文章，先保证问题背景、分层模型、实战路径、反例陷阱、检查清单和延伸阅读完整。第三批做日文版本地化改写，检查不是机械直译。第四批统一时效边界和来源表达。第五批再跑 check、build 和浏览器截图。

每个批次都要留下证据。比如字数用 `wc -m`，标题结构用 `rg`，构建用 `npm run build`，页面用 Playwright 或浏览器截图。这样一旦中断，后续执行者不需要相信上一轮的自我评价，可以直接看文件和命令结果。

长任务还要允许“局部完成但整体未完成”。例如三篇文章达标、三篇还没有达标，这时应该报告差距，而不是因为目录已经生成就说完成。成熟的 Agent 应该能承认中间态，并继续推进到真正验收。

## 反例陷阱：把长上下文误认为长任务能力

长上下文能装下更多资料，但不能自动带来项目管理能力。一个模型可以记住很多文件，却仍然可能忘记用户最新指令、忽略无关 dirty file、把官方资料和社区经验混在一起，或者在没有截图的情况下声称页面没问题。

另一个陷阱是“连续工作幻觉”。Agent 一直在输出，就像一直有进展；但如果没有检查点和验证，输出可能只是更多文本。长任务最重要的不是不断产生内容，而是不断缩小未完成差距。

第三个陷阱是“完成口径漂移”。任务开始时要求 6,000-9,000 中文字、图文并茂、中日同步、官方资料核验；执行到后面，Agent 只记得“写了文章、跑了 check”。这不是模型不努力，而是目标没有被持续对照。解决方法是把完成口径做成审计清单，在最后逐项打勾。

第四个陷阱是“权限疲劳”。长任务中审批很多，Agent 可能倾向于把边界模糊化，或者用户因为频繁确认而放松警惕。比较好的设计是把审批分级：低风险动作自动执行，高风险动作集中请求，发布动作永远明确确认。

## 当前可观察状态与复核路径

截至 2026-05-11，OpenAI Codex 文档已经把配置、sandbox、approval、Skills、MCP、浏览器和应用能力放在同一套产品文档里描述；OpenAI Responses API 把 web search、file search、computer use、code interpreter 和 remote MCPs 等能力放进 agentic loop。Claude Code、Gemini CLI、Google ADK 等生态也都在快速演进各自的工具、权限和自动化能力。

这些变化说明一个趋势：长任务 Agent 不会只依赖模型窗口，而会依赖工具系统、权限边界、工作流资产和可观测日志。也正因为这些能力变化快，文章不应该写成“某 CLI 永远比某 CLI 更适合长任务”，而应该写成“当前可观察到的能力边界是什么，以及团队如何复核”。

复核路径可以固定为四步。第一，查看所用 Agent 平台的官方配置与安全文档，确认 sandbox、approval、MCP、Skills 或 hooks 的当前行为。第二，用一个低风险本地任务做真实实验，记录工具调用、失败模式和恢复方式。第三，检查是否能导出或回放日志、trace、diff、命令输出。第四，把这些结果写进团队的本地指南，而不是只放在个人记忆里。

如果官方文档与本地行为不一致，优先相信本地实验能暴露的问题，但公开文章里要把它写成“在某环境观察到”，不要扩展成全局结论。长任务工程最怕把一次成功包装成通用规律。

## 运营清单：让 Agent 能被持续改进

如果一个长任务 workflow 会重复使用，就应该像运营系统一样维护它。每次运行后，记录本次目标、耗时、工具失败、用户中途改口、最终验证和遗留问题。三到五次之后，就能看出哪些步骤应该变成 Skill，哪些命令应该脚本化，哪些审批可以合并，哪些停止条件需要提前。

回放样本也要分类型保存。至少保留一次顺利完成样本、一次来源无法核验样本、一次构建失败样本、一次用户改变范围样本、一次无关脏文件干扰样本。改 prompt 或 Skill 以后，用这些样本检查 Agent 是否更早发现风险、更少越权、更清楚交付。

最后要维护一个“完成前审计”。它不是形式主义，而是防止长任务在最后几分钟丢掉标准：目标是否全部覆盖，文件是否都在范围内，官方来源是否写明日期，日文版是否同步，图片是否可见，命令是否真的跑过，未完成事项是否诚实说明。只有这张表过了，长任务才算真正结束。

这类审计最好由产物驱动，而不是由 Agent 的自我感觉驱动。内容任务看真实文件、字数、标题、来源和截图；代码任务看 diff、测试、构建和运行页面；自动化任务看调度状态、日志和最近一次执行结果。证据越具体，后续维护者越容易判断这次完成是否可靠。

长任务还有一个容易被忽略的运营指标：人是否愿意再次把同类任务交给它。如果每次都需要人工重做结论、清理越界修改、补跑验证，说明 Agent 只是生产了中间材料，还没有形成可靠工作流。真正可运营的长任务系统，应该让人更愿意提高任务上限，而不是更担心收尾成本。

这也是为什么长任务的完成报告要简短但有证据。它不需要复述每一步思考，而要告诉人：完成了哪些产物，哪些命令通过，哪些来源重新核验，哪些风险还存在。这样的报告才方便进入下一轮协作。

如果报告只写“已完成”，下一次协作仍然要从头确认；如果报告把证据和遗留风险说清楚，用户就能把注意力放在判断质量和调整方向上。这种信任不是礼貌措辞建立的，而是靠一次次可复核交付建立的。长期看，好的 Agent 不是让人少看一眼，而是让人看得更准、更快、更安心。

## 查缺补漏清单

- 目标是否写成可验收产物？
- 是否知道哪些文件或系统不能碰？
- 是否在长任务中留下可恢复检查点？
- 是否把发布、删除、发送、付费等动作放进审批边界？
- 日志是否记录了关键来源、命令和决策？
- 是否有明确停止条件？
- 是否能用样本回放验证 workflow 改进？
