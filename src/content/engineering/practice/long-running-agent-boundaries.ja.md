# 長時間 Agent の境界：ログ、承認、停止条件、リプレイ

> 時点メモ：この記事は 2026-05-11 に確認した情報を前提にしています。Codex、Claude Code、Gemini CLI、OpenAI Agents SDK などの権限、並列実行、ログ、承認機能は変化が速いため、ここでは恒久的な機能比較ではなく工程原則を扱います。

長時間 Agent を「長く会話できるモデル」と考えると危険です。本当に必要なのは、複雑な作業を進めながら、人がいつでも何をしたか、なぜしたか、いつ止めるべきか、失敗後にどう引き継ぐかを理解できる仕組みです。

これは prompt だけでは解けません。実行環境、ツール、権限、ログ、検証を含む Harness の問題です。

![長時間 Agent の境界ループ](/images/engineering/practice/long-agent-boundary-loop.svg)

## 目標は納品物として書く

「工程実践シリーズを整理する」は方向です。「中日対応の記事を追加し、カバー画像と SVG を用意し、source inventory を更新し、check と build を通し、無関係な dirty file を触らない」は納品目標です。

長時間タスクの開始時、Agent は成果物、範囲、検証、禁止事項を知る必要があります。そうでなければ、探索を進捗と誤解し、部分的な成功を完了と誤解します。

## チェックポイントで回復できるようにする

長時間タスクでは、中断、文脈圧縮、ツール失敗、ビルド失敗、ユーザーの追加指示が必ず起きます。チェックポイントがなければ、次の実行者は記憶に頼るしかありません。

チェックポイントは大げさでなくて構いません。完了したファイル、生成した資産、確認済みの出典、現在の失敗理由、次の作業を書いておくだけでも、復旧性は大きく上がります。

コンテンツ作業なら、どの記事を書いたか、どの言語が同期済みか、どの画像が生成済みか、どの公式情報を確認したか、どのページを目視したかを残します。コード作業なら、変更したモジュール、テスト結果、未解決リスク、無関係な dirty file を残します。

## 承認は邪魔ではなく境界

長時間 Agent は多くのツールを使います。ファイル読み書き、テスト、Web、画像生成、commit、push、メール送信など、リスクはそれぞれ違います。成熟した Harness は、自動実行できる操作、レビューが必要な操作、ユーザー確認が必要な操作、禁止操作を分けます。

承認は速度を落とすためではなく、不可逆な操作を通常ステップから分離するためにあります。このリポジトリでは、現在の会話で明示的な許可がない限り `git push` しないというルールがあります。これは面倒な手続きではなく、公開境界の保護です。

## ログは復盤できる事実を残す

長時間タスクのログは、会話の要約ではありません。読んだ重要ファイル、使った出典、変更したパス、実行したコマンド、結果、ユーザー決定、仮定を残すものです。

良いログは、結果が間違った時に事実、判断、ツール、検証のどこで間違ったかを調べられます。復旧する時にどこから続けるべきかも分かります。同じタスクが繰り返されるなら、どの部分を Skill や script にすべきかも見えてきます。

ただし公開記事には内部ログ、ローカルパス、ツール失敗メモを出しません。それらは実行報告や source inventory に置くべきです。

## 停止条件を先に決める

長時間 Agent に必要なのは「諦めないこと」ではなく、「止まるべき時に止まること」です。

典型的な停止条件は、ユーザー指示の衝突、破壊的操作、公式情報で確認できない事実、今回の変更と無関係なビルド失敗、無関係な dirty file、生成物の方向性を人が選ぶ必要がある場合です。

停止は失敗ではありません。不確実な状態で進みすぎないために、人へ制御を戻すことです。

## リプレイサンプルで改善を測る

繰り返し実行する Agent workflow には、リプレイサンプルが必要です。成功例、失敗例、ユーザーが途中で方向を変えた例、外部情報が取れなかった例、ビルドが失敗した例を残します。

prompt、Skill、MCP tool、承認ルールを変更した後、古いサンプルで再実行すると、改善が本物か分かります。サンプルがなければ、Agent 改善は印象に寄りがちです。

## 最小基準

長時間 Agent には、少なくとも明確な目標と禁止範囲、復旧可能なチェックポイント、ツール権限と承認階層、重要事実ログ、失敗分類、停止条件、完了前検証、完了後の差分報告が必要です。

モデルが強くなるほど、この境界は重要になります。強いモデルは自律的に進める力があるため、境界がないと、もっともらしい越権行動をしやすくなるからです。

## レイヤーモデル：目標、状態、権限、証拠、引き継ぎ

長時間タスクは五つの層に分けられます。どの層も、モデルが「分かっているはず」に任せず、確認できる境界として扱います。

第一層は目標です。完了時に何が存在するべきかを定義します。成果物、言語、ディレクトリ、長さ、品質基準、検証コマンド、触ってはいけない範囲まで書きます。コンテンツ作業では特に、「書いた」ではなく「読者基準、出典、表示確認まで満たした」と定義する必要があります。

第二層は状態です。今どこまで進んでいるかを示します。文脈圧縮、プロセス中断、ユーザーの追加指示があっても戻れるように、完了項目、未完了項目、現在の失敗、次の一手、リスクを残します。

第三層は権限です。何を自動で実行でき、何に承認が必要かを決めます。ファイル読み取り、草稿作成、ローカル check、公開文書の閲覧は比較的低リスクです。一方で push、削除、メール送信、本番設定変更、課金 API の呼び出しは高い承認境界に置くべきです。

第四層は証拠です。なぜ結果を信じてよいのかを示します。公式出典、コマンド結果、スクリーンショット、trace、diff、build log、文字数、リンク確認が証拠になります。意図だけでは、ページが読めることも、記事が基準に届いたことも、テストが通ったことも証明できません。

第五層は引き継ぎです。今止まっても、次の実行者がどう続けるかを示します。引き継ぎは最後に書くものではなく、タスク中ずっと更新するものです。長い作業ほど、中間状態を事実として残す価値が高くなります。

この五層がそろって、長時間 Agent の工程境界になります。モデルは推論と生成を担い、Harness はその推論を制御可能な軌道に載せます。

## 実践パス：長いコンテンツ作業を回復可能なバッチにする

このサイトのシリーズ制作では、公式情報の確認、中国語記事、日本語版、画像生成、内部リンク、source inventory、build、ページ QA が同時に発生します。「シリーズを良くして」とだけ渡すと、数本の記事はそれらしく仕上がっても、長さ、時点メモ、日本語同期、表示確認が抜けやすくなります。

安定した進め方は、回復可能なバッチに分けることです。最初のバッチでディレクトリ、frontmatter、source inventory、画像資産を作り、サイトが新コンテンツを認識するか確認します。次のバッチで中国語記事を深め、問題背景、レイヤーモデル、実践パス、反パターン、チェックリスト、関連資料をそろえます。さらに日本語版を本地化し、時点メモと出典表現をそろえ、最後に check、build、ブラウザ確認を行います。

各バッチには証拠が必要です。文字数は `wc -m`、見出しは `rg`、build は `npm run build`、ページ表示は Playwright やブラウザのスクリーンショットで確認します。中断後の実行者は、前の Agent の自己評価ではなく、ファイルとコマンド結果から続けられます。

また、長時間タスクでは「一部完了、全体未完了」を正直に扱う必要があります。三本の記事が基準に届き、三本がまだなら、その差分を報告して進めるべきです。ディレクトリが存在することと、全体が完成していることは別物です。

## 反パターン：長い文脈を長時間能力と誤解する

長い context window は多くの資料を保持できますが、プロジェクト管理能力そのものではありません。モデルは多くのファイルを覚えていても、最新のユーザー指示を落としたり、無関係な dirty file を触ったり、公式情報とコミュニティ経験を混ぜたり、スクリーンショットなしに「表示は問題ない」と言ってしまうことがあります。

もう一つの罠は「動き続けているから進んでいる」という錯覚です。Agent がずっと出力していても、チェックポイントと検証がなければ、未完成の差分が減っているとは限りません。長時間タスクに必要なのは、出力量ではなく、未達成項目を確実に減らすことです。

三つ目は完了基準の漂流です。開始時には 6,000-9,000 文字、図解、日中同期、公式情報確認が条件だったのに、最後には「記事を作り、check した」だけになってしまう。これを避けるには、完了基準を最後の監査リストとして残し、項目ごとに証拠を対応させます。

権限疲れにも注意が必要です。長時間タスクでは承認が多くなり、Agent もユーザーも境界を曖昧にしたくなります。低リスク操作は自動化し、高リスク操作はまとめて確認し、公開や送信の操作は常に明示確認にする、という分級が有効です。

## 現在観測できる状態と確認方法

2026-05-11 時点で、OpenAI Codex の文書は config、sandbox、approval、Skills、MCP、ブラウザ、アプリ機能を一連の製品文書として扱っています。OpenAI Responses API では web search、file search、computer use、code interpreter、remote MCPs が agentic loop の tool として説明されています。Claude Code、Gemini CLI、Google ADK なども、それぞれ tool、権限、自動化の能力を更新し続けています。

ここから見える傾向は、長時間 Agent が単なる長い会話ではなく、ツールシステム、権限境界、ワークフロー資産、観測可能なログに依存するということです。だからこそ、「ある CLI が永遠に最適」とは書かず、「現時点で観測できる能力と、チームがどう確認するか」を書くべきです。

確認手順は固定できます。まず利用する Agent platform の公式設定・安全文書を読み、sandbox、approval、MCP、Skills、hooks の現在の動作を確認します。次に低リスクのローカルタスクで実験し、tool call、失敗、復旧方法を記録します。さらにログ、trace、diff、コマンド結果をどこまで残せるかを確認します。最後に、その結果をチームのローカルガイドへ反映します。

公式文書と手元の挙動が食い違う場合、公開記事では「特定環境で観測した」と書き、全体結論へ広げないことが重要です。一回の成功を一般法則に見せることが、長時間 Agent 運用では最も危険です。

## 運用チェック：改善できる Agent にする

繰り返し使う workflow は、運用対象として扱います。毎回、目標、所要時間、tool failure、ユーザーの方向転換、最終検証、残課題を記録します。数回たまると、どの部分を Skill 化し、どのコマンドを script 化し、どの承認をまとめ、どの停止条件を早く出すべきかが見えてきます。

リプレイサンプルも種類ごとに残します。順調に完了した例、出典が確認できない例、build が失敗した例、ユーザーが範囲を変えた例、無関係な dirty file がある例。prompt や Skill を変えたあと、これらで再検証すると改善が本物か分かります。

最後に、完了前監査を持ちます。これは形式ではありません。長い作業の終盤に基準を落とさないための装置です。目標をすべて覆っているか、ファイルは範囲内か、公式出典と日付があるか、日本語版が同期しているか、画像は見えるか、コマンドは本当に実行したか、未完了事項を正直に書いたか。ここを通って初めて、長時間タスクは完了と言えます。

## チェックリスト

- 目標は検証可能な成果物として書かれているか。
- 触ってはいけないファイルやシステムが明確か。
- 復旧できるチェックポイントがあるか。
- push、削除、送信、購入などは承認境界に入っているか。
- ログは出典、コマンド、判断を残しているか。
- 停止条件があるか。
- サンプルで workflow 改善を再検証できるか。
